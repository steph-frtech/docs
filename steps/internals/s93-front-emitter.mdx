## Implémentation

S93 ajoute l'**émetteur de front-end de l'app émise** : à partir d'un `FrontSpec` (le projet + les entités, chacune avec ses attributs scalaires S35, ses blobs S72 et ses relations S71 ; + les controls, chacun lié à une operation avec ses fixtures control-spec), il **projette** tout le front. Le package est `back/runtime/frontemit`.

**Les émetteurs (purs, totaux, byte-stables).**

- `EmitFront(spec)` → le bundle complet en ordre canonique : `emitIndex` (la page de navigation `gen/<projet>/web/index.tsx`, un lien par entité), un `emitEntityForm` par entité (ordre canonique des noms), et `emitControls`. Chaque artefact porte le header protégé `// CODE GENERATED BY AIDOS — DO NOT EDIT. source: <hash>` + son `OutputHash`.
- `emitEntityForm(projet, entité)` → un `<form method="post" action="/<entité>">` (la **même route** que le serveur S87 émet) : un `<input>` par attribut scalaire (la table close `scalarInput` : string→text, int→number, bool→checkbox, timestamptz→datetime-local), l'identifiant **exclu** (assigné côté serveur) ; **un `<input type="file">` par blob** (avec `accept` = la liste close des MIME autorisés et `enctype="multipart/form-data"`) ; **un `<select name="<rel>_id">` par relation** (multiple pour une N-N). Un champ requis porte `required`.
- `emitControls(spec)` → la verticale control+action en **vrais boutons** (ordre canonique). Chaque bouton porte `data-aidos-invoke="<operation>"` (le lien control→action S11, action-capable) et `data-aidos-fixture` = un capteur JSON `{name, op, rows:[{given,visible,enabled}]}` : le bouton **est le capteur de sa propre control-spec**.
- `EmitBundle(spec)` → la concaténation byte-identique de tous les artefacts sous un bandeau — la surface de la reproductibilité (« même Kernel → bundle byte-identique »).

**Le déterminisme.** `SourceHash(spec)` = `records.Hash(records.Canonicalize(body))` sur un corps re-sérialisé en ordre canonique (entités/controls par nom, attributs en ordre source) — **réutilise S02**, jamais forké. Pas d'horloge, pas de RNG, pas de chemin absolu, newlines `\n`. Même cut → octets identiques, indépendant de l'ordre d'entrée.

**Le mur + l'honnêteté.** Un `FrontSpec` malformé → un `blockreason.BlockReason` typé (la forme S13) avec un `how_to_fix` non vide ; un **bouton sans operation liée** est un déclencheur orphelin **refusé** (`ErrControlNoOp`), jamais deviné ; jamais un panic, jamais un champ/route/bouton inventé. L'émetteur ne lit que des sources et n'écrit que des projections sous la ligne.

**Le MCP `aidos-front-emitter`** (`back/mcp/front-emitter`, ADR 0009) expose `emit_front` · `emit_bundle` · `front_hash` — purs, n'écrivent rien. **Le twin TS** `front/web/lib/front-emitter.ts` reflète les émetteurs et alimente la route **action-capable** `/front-emitter` : basculer blob/relation → émettre, voir le bundle + la source du formulaire + les boutons-capteurs, et **soumettre un vrai formulaire généré** (texte + checkbox + upload de fichier + select de relation) contre `/api/emitted-submit` — le datastore stand-in qui valide le blob contre la liste MIME + le plafond S72 et assigne un id serveur.

**Les miroirs.** rapid (`frontemit_property_test.go`) : bundle **byte-identique** et indépendant de l'ordre d'entrée ; **chaque control porte sa fixture** (op + chaque `given`) ; FN02-pur (aucun binding mutable de module) ; chaque entité a exactement un formulaire, chaque blob devient un `type="file"`. Fixture (`frontemit_fixture_test.go`) : le cut `order` (scalaire + blob + relation) rend texte/checkbox/file/select et poste vers `/order` ; et la **PARITÉ** capteur ↔ `control.EvalState` — les lignes `{visible,enabled}` du capteur égalent exactement l'évaluation du control-spec noyau sur le même `given` (le capteur ne dérive jamais de la verticale). fast-check (`front-emitter.test.ts`, 5/5) côté twin ; Playwright (`front-emitter.spec.ts`, 5/5) côté écran, dont la soumission réelle avec upload blob.

**OpenQuestion OQ-S93-datastore** (forward-dependency, exception bootstrap §6). Le datastore live de l'app émise (Doltgres/Postgres, ADR 0006) est une dent ultérieure — pas un service tournant dans le Workbench. `/api/emitted-submit` est donc un **stand-in en mémoire** qui exerce la même forme de soumission (multipart + validation blob + id serveur) ; quand le runtime émis arrive, le formulaire poste vers la route API émise. OpenQuestion documentée, pas un résidu rouge.

## Méta

S93 est un **émetteur de plus** dans la matrice kind × target, sur le **plan de l'app émise** (Hono/TS, ADR 0040), mais sur la face **front** — là où S90 émet l'API et S87 le serveur. Il tranche **OQ-0040-front** (la décision forcée de la roadmap, ligne 289) : le front émis est **Hono JSX/SSR**, pas une SPA client sur `hc`. La justification est de déterminisme et de réutilisation : un formulaire rendu côté serveur est byte-stable et agnostique (Playwright pilote du HTML simple), il réutilise le runtime Hono **déjà émis** (pas de second toolchain), et il est bootable sans étape d'hydratation/bundler.

La **parité capteur ↔ `control.EvalState`** est le miroir qui ferme la verticale : si la fixture embarquée dans le bouton divergeait de la sémantique du control-spec noyau (S11 + `expr`), le mirror passe rouge. C'est l'application de la loi de complétude au plan UI — un bouton sans control-spec vivante, ou une control-spec sans bouton rendu, serait un **monstre**. Le bouton-comme-capteur (le `data-aidos-fixture`) est exactement ce qui interdit le « capability headless » (§6 step 7) : aucune capacité n'existe sans un contrôle exécutable depuis l'écran qui la porte.

## Méta-méta

S93 illustre le **déterminisme-first** sur le plan de l'émetteur de front : tout ce qui *peut* être une fonction pure l'**est** — le rendu (une projection de l'AST), le mapping scalaire→input (une table close), le routage du formulaire (la même règle que le serveur), le capteur (une sérialisation canonique de la fixture). Aucun LLM n'entre dans l'émission ; le seul « jugement » (la visibilité/activation du bouton) est délégué à l'interpréteur `expr` du noyau, lui-même déterministe et faisant autorité — le capteur s'aligne dessus, jamais l'inverse. Le miroir de reproductibilité (même `FrontSpec` → octets identiques) est la garantie auto-vérifiante que rien d'opaque ne s'est glissé.

Et S93 respecte le **mur** sans exception : un émetteur lit des sources du Kernel et écrit des projections sous la ligne ; la soumission du formulaire écrit dans un datastore sous la ligne, jamais le noyau/mirrors/fitness. Il n'invente aucune route, aucun champ, aucune règle métier, et n'écrit jamais une vérité. La porte vers le noyau reste `idée → miroir → /goal → approbation humaine` ; S93 n'en franchit aucune.
