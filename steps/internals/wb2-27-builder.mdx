## Implémentation

**Le twin pur `lib/v2/builder.ts`** (ADR 0057, étendu au cycle de vie complet par l'ADR 0058, puis à l'échelle d'environnements et à la couverture totale par l'ADR 0059) — PUR & TOTAL & DÉTERMINISTE (pas d'horloge, pas d'aléa, pas d'E/S, pas de LLM) :

- `INTENT_KINDS` : le **jeu clos** des intentions — `capturer_idee · greffer · promouvoir · generer · deployer · delta · impacter · interroger · ouvrir` (**9** : le cycle de vie ENTIER d'une appli + la navigation totale). Tout ce que le chat sait faire, déclaré, rien d'autre.
- `ENV_LADDER = ["test", "staging", "prod"]` : l'**échelle d'environnements** — DÉCLARÉE, close, **ORDONNÉE**. Étendre l'échelle = déclarer un barreau (une donnée), jamais coder un cas.
- `classifyIntent(text) → IntentCandidate[]` : l'**algorithme lexical déclaré** — tokens pliés (NFD, minuscules, ≥ 3 chars), `LEXICONS` par intention (verbes **forts** +2, indices **faibles** +1, déclarés au-dessus de la ligne, jamais appris — §8), **tous** les kinds retournés, triés score ↓ puis ordre déclaré (stable). Ce classement EST « les types de réponse possibles ».
- `understand(state, text) → Understanding` : « **l'attente** » — `comprise` (un candidat net en tête), `ambigue` (égalité en tête à score > 0 : **détectée et remontée**, jamais tranchée en silence), `incomprise` (score 0 : jamais une invention). Total. **Plus la règle DÉCLARÉE « l'impératif de navigation commande »** : un message dont le PREMIER token est `ouvre`/`ouvrir`/`navigue` est TOUJOURS l'intention `ouvrir`, avant tout score — parce que `ouvrir` est le seul intent dont la charge utile **cite le vocabulaire des autres** (les titres d'écrans contiennent « idée », « goal », « déployer »…) ; sans elle, la loi de couverture serait fausse. Déterministe, épinglée au miroir.
- `applyIntent(state, text) → {state, events, impacts}` : le **réducteur PUR event-sourcé** — même `(état, message)` → même `(état', événements, impacts)` ; le journal (`state.log`) est **append-only** (§9). « La réponse » = `BuilderEvent` (jeu clos : `idee_capturee · arbre_greffe · kernel_propose · impact_calcule · etat_lu · app_generee · deploiement · delta_calcule · ecran_ouvert · refus` — UN kind `deploiement` portant son champ `env` **remplace** le couple `deploiement_test`/`deploiement_prod` de l'ADR 0058) ; « les impacts » = `BuilderImpact[]` — la **vague calculée**, jamais estimée.
- `initBuilderState(extraScreens?)` : l'arbre `seedComposes()` (un **seul** produit racine, ADR 0055), idées/kernels/journal vides, `envs = {test: null, staging: null, prod: null}`, et `screens` = le **registre V2 (`SCREENS`, WB2-25) TOUJOURS couvert** + les écrans V1 **injectés en données** (`extraScreens` — l'inventaire vient du scan serveur, jamais codé en dur).

**Le cycle de vie (ADR 0058 + 0059) — générer · l'échelle · le réel · le delta · ouvrir** :

- `emitApp(state) → AppProjection` : **GÉNÈRE l'app** — une **PROJECTION PURE** des kernels proposés, **jamais stockée**, toujours **recalculée** : une entité par kernel (nommée du grain feuille de sa coordonnée `scale`), une route par entité, et `version = app:<hash FNV-1a des versions de kernels triées>` — **le contenu décide, jamais l'horloge** (même état → même app, même version). Phrase canonique : « **génère l'application** » → `app_generee` (refus si aucun kernel : rien à projeter).
- `BuilderState.envs` : `Record<EnvName, Deployment | null>` sur `ENV_LADDER` — un `Deployment` = `{version, kernelVersions[]}` (la base du calcul de delta). Les environnements vivent **dans l'état event-sourcé**, pas dans une infra.
- **LE CLIQUET GÉNÉRALISÉ** (`case "deployer"`, le barreau parsé du message — le PLUS HAUT nommé, défaut `test`) : « **déploie l'application en test | staging | prod** » ; déployer au **barreau i** est **REFUSÉ** (`refus` explicable, portant son `env`) tant que le barreau i−1 ne porte pas **CETTE version exacte** (`envs[ladder[i-1]].version !== emitApp(state).version`) — chaque barreau, dans l'ordre, toujours ; et toute **nouvelle promotion ré-arme CHAQUE barreau supérieur** (la version d'app change → toute l'échelle au-dessus du test re-devient refusée tant que la nouvelle version ne l'a pas regravie).
- **LE DÉPLOIEMENT RÉEL (ADR 0052)** : `deployRealAction()` (`app/v2/builder/actions.ts`) **RÉUTILISE `deployStack()` de `/ai-lab`** (réémission best-effort `aidosappemit` + `docker compose up -d` sur la stack fixe, URL live Traefik) — **jamais un second chemin de déploiement**. L'écran gate le bouton sur `envs.prod !== null` (le sommet de l'échelle in-model) ; **le clic humain EST l'approbation**. Le mur : une action au-dessous de la ligne, aucune écriture-vérité. L'émission réelle depuis les kernels in-model reste une OpenQuestion (S45).
- **LE DELTA** (`case "delta"`) : « **montre le delta depuis la prod** » (ou un autre barreau) → `delta_calcule`, impacts = **les kernels hors de l'ensemble déployé** (différence d'ensembles sur `kernelVersions` — 0 écart juste après un déploiement, N après N promotions) ; sans déploiement, le delta est **total** (tout est écart), jamais une erreur. Compté, jamais estimé.
- **LE DELTA AU GRAIN CODE (ADR 0056 × 0058)** : `codeDeltaFor(kernels, tree, codeNodes, codeEdges) → CodeDelta[]` — pour chaque kernel d'écart, les **fonctions exactes** ancrées sur sa coordonnée (`anchorSymbols`, top-3 `AnchorSuggestion {nodeId, name, file, score}`) et la **taille de la vague** de rouge code (`impactOf` de la meilleure ancre). PURE & TOTALE & DÉTERMINISTE : graphe de code vide → ancres vides, jamais une erreur.
- **OUVRIR — la couverture totale** : `resolveScreen(screens, text) → ScreenRef | null` — score lexical contre l'**inventaire déclaré** (+3 par token du slug de route, +1 par token de libellé, départage stable par route) ; **aucune accroche → null** (fail-closed, jamais une route inventée). Phrase canonique : « **ouvre l'écran code** » → `ecran_ouvert` (ref = `/v2/code`) ; introuvable → `refus`. **LA LOI DE COUVERTURE** est au miroir : ∀ écran du registre V2, « ouvre \<titre\> » résout vers SA route.

**La composition des twins (pas de fork)** : l'arbre vivant vient de `lib/v2/composition` (`growComposes`, `placeIntent`, `positionOf`, `nodeByPath`) ; la capture délègue à `composeIdea` (`lib/v2/idea`) — **le niveau, la facette et l'échelle sont PRIS DU NŒUD D'ATTACHE** ; la promotion délègue à `promoteIdea` (`lib/v2/goal`) → un `ProposedKernel` (version `k:…` content-adressée, ChangeSet **DRAFT**, `wroteKernel=false`) ; l'ancrage code délègue à `anchorSymbols`/`impactOf` (`lib/v2/code-graph`, ADR 0056) ; l'inventaire d'écrans V2 vient de `lib/v2/screens` (WB2-25).

**L'exception gatée `app/v2/builder/actions.ts`** : `reformulateAction(message)` — server action qui appelle le **CLI `claude --model claude-fable-5`** (`execFile`, le précédent `/ai-lab`, ADR 0054) avec un prompt qui déclare le jeu clos et exige `{"text":"…"}` JSON. La phrase réécrite **repasse dans le MÊME pipeline** `understand`/`applyIntent` — le LLM **propose**, le code **re-juge** (§6/§8). Toute panne → `null` : repli sur les chips déterministes.

**Le miroir `lib/v2/builder.test.ts`** (Vitest + fast-check) : **29 tests verts** —

1. le jeu des intentions est **déclaré et clos** (les 9 — le cycle de vie entier + la navigation totale) ;
2. **l'ÉCHELLE D'ENVIRONNEMENTS est déclarée, close, ordonnée** (le cliquet généralisé) ;
3. ∀ texte : `classifyIntent` **total, déterministe**, candidats ⊆ jeu clos, triés score ↓ ;
4. « l'attente » : un message clair est **compris** (le bon kind en tête) ;
5. l'**ambiguïté est détectée**, jamais tranchée en silence (deux verbes forts → `ambigue`) ;
6. un texte sans accroche est **incompris** (jamais une invention) ;
7. ∀ (état, texte) : `applyIntent` **déterministe** — même entrée → même état', mêmes événements, mêmes impacts ;
8. ∀ : le journal est **append-only** (le préfixe d'événements intact) ;
9. GREFFER : « greffe pommes sous app/catalogue » fait pousser l'arbre **là** ;
10. CAPTURER : une idée naît **placée** (niveau/facette/échelle pris du nœud d'attache), `hasMirror=false` ;
11. PROMOUVOIR : « promeus la dernière idée » → un kernel **proposé** (DRAFT, `wroteKernel=false`) ;
12. PROMOUVOIR sans idée → un **refus**, jamais un kernel inventé ;
13. IMPACTER : « quel impact si je modifie app/paiement » → la **vague du sous-arbre** ;
14. **LE MUR (∀ messages)** : pour toute suite de messages, aucune intention ne produit **jamais** une écriture-vérité — re-prouvé sur la grammaire **étendue à 9** ;
15. INTERROGER : total — l'état est **lu** ;
16. GÉNÉRER sans kernel → **refus** (rien à projeter, jamais une invention) ;
17. GÉNÉRER après promotion → `app_generee`, version content-adressée **STABLE** (même état → même `app:<hash>`) ;
18. DÉPLOYER en test sans kernel → **refus** (rien à déployer) ;
19. **∀ barreau > 1 : SAUTER UN BARREAU EST REFUSÉ** (prod directe, staging directe, test→prod sans staging) ;
20. **le chemin légal test → staging → prod** — la MÊME version monte chaque barreau ;
21. **LE CLIQUET RE-MORD sur TOUTE l'échelle** : une promotion invalide chaque barreau supérieur ;
22. DELTA sans aucun déploiement : le delta est **total** (tout est écart), jamais une erreur ;
23. DELTA après la prod = **0 écart** ; une nouvelle promotion → **1 kernel d'écart** ;
24. **LA LOI DE COUVERTURE : ∀ écran du registre V2, « ouvre \<titre\> » résout vers SA route** ;
25. les **écrans V1 injectés** sont atteignables aussi (l'inventaire est une donnée, pas du code) ;
26. ∀ texte : `resolveScreen` est **total et déterministe** ; aucune accroche → `null` (jamais une invention) ;
27. ouvrir un écran introuvable → **refus** (fail-closed) ;
28. `codeDeltaFor` : un kernel d'écart s'**ANCRE sur ses fonctions** (nom lexical) + la taille de sa vague ;
29. `codeDeltaFor` : **TOTAL & DÉTERMINISTE** — graphe de code vide → ancres vides, jamais une erreur.

**L'écran `/v2/builder`** (`app/v2/builder/page.tsx` + `BuilderClient.tsx`, enregistré dans `lib/v2/screens.ts` — la cohérence WB2-25 reste verte) : la page serveur passe les libellés i18n (`v2Builder`, fr/en) et injecte l'inventaire V1 scanné ; le client est **du rendu + l'état d'écran event-sourcé** (tours append-only, `BuilderState` réduit par `applyIntent`). Chaque tour rend visibles le chat (`v2-builder-chat`), « l'attente » (`v2-builder-attente`), « les types de réponse possibles » (`v2-builder-candidates`/`v2-builder-candidate`, **cliquables**), « la réponse » (`v2-builder-events` — un `deploiement` affiche son barreau ; un `ecran_ouvert` devient une **puce de navigation** `v2-builder-open-screen` vers sa route), « les impacts » (`v2-builder-impacts`/`v2-builder-impact`), le bouton Claude (`v2-builder-claude`), les suggestions canoniques (`v2-builder-suggestion` — dont « génère l'application », « déploie l'application en test », « … en staging », « … en prod », « montre le delta depuis la prod », « ouvre l'écran code »), l'entrée (`v2-builder-input`/`v2-builder-send`) ; et les panneaux d'état : l'arbre vivant (`v2-builder-tree`), les idées (`v2-builder-ideas`), les kernels proposés (`v2-builder-kernels`, badge DRAFT), l'app projetée (`v2-builder-app`), **l'échelle d'environnements entière** (`v2-builder-envs` — une carte par barreau de `ENV_LADDER`, boutons qui ENVOIENT la phrase canonique), **le déploiement réel** (`v2-builder-real-deploy` : le bouton `v2-builder-deploy-real` **gaté sur `envs.prod`**, l'URL live `v2-builder-real-url`), **le delta au grain code** (`v2-builder-code-delta`, ancres `v2-builder-code-anchor` cliquables vers `/v2/code`), le journal (`v2-builder-log`). **Les boutons d'écran ENVOIENT des messages canoniques** — chacun compose la phrase et la repasse par le même pipeline : le chat reste l'**unique source de gestes**, l'écran n'a **aucun pouvoir que le twin n'a pas** (la seule exception est le geste humain du déploiement réel — une action ADR 0052 au-dessous de la ligne, pas une intention du twin). Thème ccup (ADR 0010), bilingue (ADR 0011), note du mur (`v2-builder-wall-note`).

## Méta

**Pourquoi une grammaire fermée et pas un agent.** « Un chat qui fait tout » est le cas d'école du déterminisme-first (§6/§8) : comprendre une phrase **semble** être une tâche de LLM, mais classer un message contre neuf intentions à lexiques déclarés est une **fonction pure** — donc elle DOIT être du code, et le code est l'autorité. Les extensions successives (ADR 0058 puis 0059) en sont la preuve par l'acte : le cycle de vie, l'échelle, la navigation totale = des lexiques + des réductions + des tests de plus — jamais « le modèle improvisera ».

**L'échelle est une donnée, la loi est une.** L'ADR 0058 avait DEUX cas (test, prod) ; l'ADR 0059 les remplace par UNE loi paramétrée sur `ENV_LADDER` : le barreau i exige le barreau i−1, ∀ i. Le staging n'a pas ajouté un `case` — il a ajouté un **élément de tableau**, et le miroir le prouve **∀ barreau** (une propriété, pas trois exemples). C'est la forme générale du cliquet : déclarer l'ordre, prouver la loi, et laisser la donnée s'étendre.

**L'app n'existe pas, elle se recalcule.** `emitApp` ne fabrique aucun artefact : la « génération » est une projection des vérités proposées, et sa version `app:<hash>` ne dépend que d'elles. C'est la parade structurelle au build divergent : il n'y a **nulle part** où un build périmé pourrait vivre. Le même geste rend le cliquet vérifiable — comparer `envs[i-1].version` à la version **recalculée** suffit, aucun registre d'artefacts à consulter.

**Le déploiement réel a trois portes, et aucune n'est un agent.** L'échelle in-model (le bouton ne s'arme qu'au sommet — le cliquet est la condition d'armement), le clic humain (l'approbation est un GESTE, jamais une heuristique), et le pipeline ADR 0052 réutilisé (`deployStack` — jamais un second chemin docker). Le chat séquence et prouve ; l'humain approuve ; le pipeline exécute. La frontière in-model / réel reste une OpenQuestion honnête (S45 : émettre l'app née des kernels du chat, pas la stack fixe).

**La couverture totale tient sur une règle déclarée — et sur son pourquoi.** `resolveScreen` ne suffit pas : « ouvre l'écran goal » accrocherait `promouvoir`, parce que **les titres d'écrans citent le vocabulaire de la grammaire**. La règle « l'impératif de navigation commande » (premier token `ouvre`/`ouvrir`/`navigue` ⇒ `ouvrir`) est la pièce qui rend la LOI DE COUVERTURE vraie — et elle est déclarée dans le code, commentée avec son pourquoi, épinglée au miroir. Une règle de désambiguïsation est une **vérité déclarée**, jamais un arbitrage silencieux.

**Le LLM propose, le pipeline juge.** `reformulateAction` est l'unique entrée du modèle, et sa sortie n'est **pas une commande** : c'est un texte qui repasse par `understand`/`applyIntent`. La surface d'autorité du LLM est exactement **zéro** — même étendue au déploiement réel et à la navigation, la grammaire ne lui ouvre rien.

**Composer les twins, pas les redonder.** Le builder n'a ni table de niveaux, ni logique de greffe, ni promotion, ni ancrage code, ni registre d'écrans à lui : il **appelle** `composition`, `idea`, `goal`, `code-graph`, `screens`. Une seule source par vérité de calcul — corriger `placeIntent` corrige le wizard ET le chat, corriger `anchorSymbols` corrige `/v2/code` ET le delta du chat, sans divergence possible.

## Méta-méta

**Le chat total est la forme finale de l'écran unique — et il reste sous la grammaire.** Depuis WB2-00, chaque écran V2 rend UN concept exécutable ; WB2-27 les rend tous **adressables par la langue**, jusqu'au déploiement réel et jusqu'à la navigation elle-même (« ouvre l'écran… » : le chat contient désormais le Workbench entier). Mais la leçon est inversée par rapport au réflexe industriel : on ne met pas un LLM devant le produit, on met une **grammaire** devant le LLM. Le jeu clos des intentions est au chat ce que le jeu clos des niveaux est à la verticale : la condition pour que « tout faire » reste **prouvable**.

**Le cycle de vie est un cliquet, à toutes les échelles — et le cliquet se généralise en se déclarant.** Le KRD avance dent par dent (red → green → stable) ; l'ADR 0058 a montré que le déploiement a la même forme ; l'ADR 0059 montre que cette forme **se paramètre** : la même loi, ∀ barreau d'une échelle déclarée. Le même mot — cliquet — désigne la même structure au grain des vérités (le ratchet des miroirs) et au grain des environnements, et y ajouter un barreau est un acte de **déclaration**, pas de code. Ce n'est pas une métaphore : c'est la même égalité content-adressée qui juge, à chaque étage.

**La couverture est une loi, pas une démo.** « Le chat sait tout faire » serait une promesse marketing s'il n'y avait pas un **registre déclaré** (WB2-25) et une **propriété ∀ dessus** (la loi de couverture). C'est le motif `ui-completeness` du §6 retourné : non plus « toute capacité a un écran », mais « tout écran a une phrase ». Les deux directions ferment la boucle — rien de caché derrière l'interface, rien d'inatteignable depuis la langue.

**La réponse est un événement, l'impact est une vague — le KRD parle au présent.** `applyIntent` ne « répond » pas : il **réduit** — exactement la forme `state → command → events` des fixtures Operation (N2). Le jour où le builder se branche sur le store réel (S31/S33, OpenQuestion), ses tours deviendront des fixtures rejouables telles quelles — déploiements et navigations compris.

**Le mur en ∀ est le seul mur qui compte pour un chat.** Un chat a un espace d'entrées **infini** ; la seule preuve qui le couvre est une **propriété** : ∀ suite de messages, aucune écriture-vérité — et aucune exécution d'infrastructure depuis le twin (`deploiement` est un événement ; le docker/Traefik réel reste derrière le bouton gaté ADR 0052, hors du réducteur). C'est le test 14 du miroir, re-prouvé à chaque extension de la grammaire.

## Place dans le cliquet KRD

WB2-27 grave la dent « **un chat, une grammaire fermée — et tout le cycle de vie dedans, jusqu'au réel** » : il consomme les phases stables de WB2-03/ADR 0055 (l'arbre `composes` vivant), WB2-11 (la promotion `promoteIdea` → DRAFT), WB2-22/ADR 0052 (le pipeline de déploiement gaté, **réutilisé** par `deployRealAction`), WB2-26/ADR 0056 (l'ancrage code, croisé dans `codeDeltaFor`) et WB2-25 (le registre des écrans, l'assiette de la loi de couverture). Sa construction a cliqueté red → green trois fois — le miroir (14 tests, ADR 0057), son extension au cycle de vie (22 tests, ADR 0058), puis l'échelle, le réel, le grain code et la couverture totale (**29 tests**, ADR 0059) rouges d'abord, verts ensuite. Les OpenQuestions de l'ADR 0059 (des labels V1 enrichis — un registre V1 déclaré ; l'émission réelle in-model → docker, S45 ; des environnements par projet) rejoignent celles des ADR 0057/0058 encore ouvertes (le store Postgres réel S31/S33, fusionner `/ai-lab`) — l'exception bootstrap (§6), documentée, jamais des échecs. Le mur reste intact : le chat **propose** — la promotion réelle passe par idée → miroir → `/goal` → approbation humaine, et le déploiement réel par l'échelle, le clic humain et le pipeline gaté.
