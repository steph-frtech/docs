## Implémentation

**Le twin pur `lib/v2/builder.ts`** (ADR 0057, étendu au cycle de vie complet par l'ADR 0058) — PUR & TOTAL & DÉTERMINISTE (pas d'horloge, pas d'aléa, pas d'E/S, pas de LLM) :

- `INTENT_KINDS` : le **jeu clos** des intentions — `capturer_idee · greffer · promouvoir · generer · deployer · delta · impacter · interroger` (**8**, le cycle de vie ENTIER d'une appli). Tout ce que le chat sait faire, déclaré, rien d'autre.
- `classifyIntent(text) → IntentCandidate[]` : l'**algorithme lexical déclaré** — tokens pliés (NFD, minuscules, ≥ 3 chars), `LEXICONS` par intention (verbes **forts** +2, indices **faibles** +1, déclarés au-dessus de la ligne, jamais appris — §8), **tous** les kinds retournés, triés score ↓ puis ordre déclaré (stable). Ce classement EST « les types de réponse possibles ».
- `understand(state, text) → Understanding` : « **l'attente** » — `comprise` (un candidat net en tête), `ambigue` (égalité en tête à score > 0 : **détectée et remontée**, jamais tranchée en silence), `incomprise` (score 0 : jamais une invention). Total.
- `applyIntent(state, text) → {state, events, impacts}` : le **réducteur PUR event-sourcé** — même `(état, message)` → même `(état', événements, impacts)` ; le journal (`state.log`) est **append-only** (§9). « La réponse » = `BuilderEvent` (jeu clos : `idee_capturee · arbre_greffe · kernel_propose · impact_calcule · etat_lu · app_generee · deploiement_test · deploiement_prod · delta_calcule · refus` — `deploiement_propose` est **SUPPRIMÉ**, remplacé par le couple test/prod) ; « les impacts » = `BuilderImpact[]` — la **vague calculée**, jamais estimée.
- `initBuilderState()` : l'arbre `seedComposes()` (un **seul** produit racine, ADR 0055), idées/kernels/journal vides, `envs = {test: null, prod: null}`.

**Le cycle de vie (ADR 0058) — générer · déployer · delta** :

- `emitApp(state) → AppProjection` : **GÉNÈRE l'app** — une **PROJECTION PURE** des kernels proposés, **jamais stockée**, toujours **recalculée** : une entité par kernel (nommée du grain feuille de sa coordonnée `scale`), une route par entité, et `version = app:<hash FNV-1a des versions de kernels triées>` — **le contenu décide, jamais l'horloge** (même état → même app, même version). Phrase canonique : « **génère l'application** » → `app_generee` (refus si aucun kernel : rien à projeter).
- `BuilderState.envs` : `{test: Deployment | null, prod: Deployment | null}` — un `Deployment` = `{version, kernelVersions[]}` (la base du calcul de delta). Les environnements vivent **dans l'état event-sourcé**, pas dans une infra.
- **LE CLIQUET D'ENVIRONNEMENTS** (`case "deployer"`, l'environnement parsé du message — `/\bprod(uction)?\b/` sinon test) : « **déploie l'application en test** » exige ≥ 1 kernel → `deploiement_test` ; « **déploie l'application en prod** » est **REFUSÉ** (`refus` explicable) tant que `state.envs.test.version !== emitApp(state).version` — **test d'abord, toujours** ; et toute **nouvelle promotion ré-arme la porte** (la version d'app change → la prod re-devient refusée tant que la nouvelle version n'a pas repassé le test).
- **LE DELTA** (`case "delta"`) : « **montre le delta depuis la prod** » (ou « … depuis le test ») → `delta_calcule`, impacts = **les kernels hors de l'ensemble déployé** (différence d'ensembles sur `kernelVersions` — 0 écart juste après un déploiement, N après N promotions) ; sans déploiement, le delta est **total** (tout est écart), jamais une erreur. Compté, jamais estimé.

**La composition des twins (pas de fork)** : l'arbre vivant vient de `lib/v2/composition` (`growComposes`, `placeIntent`, `positionOf`, `nodeByPath`) ; la capture délègue à `composeIdea` (`lib/v2/idea`) — **le niveau, la facette et l'échelle sont PRIS DU NŒUD D'ATTACHE** ; la promotion délègue à `promoteIdea` (`lib/v2/goal`) → un `ProposedKernel` (version `k:…` content-adressée, ChangeSet **DRAFT**, `wroteKernel=false`). L'impact code (`lib/v2/code-graph`, ADR 0056) est composé **côté écran** sur le graphe extrait.

**L'exception gatée `app/v2/builder/actions.ts`** : `reformulateAction(message)` — server action qui appelle le **CLI `claude --model claude-fable-5`** (`execFile`, le précédent `/ai-lab`, ADR 0054) avec un prompt qui déclare le jeu clos et exige `{"text":"…"}` JSON. La phrase réécrite **repasse dans le MÊME pipeline** `understand`/`applyIntent` — le LLM **propose**, le code **re-juge** (§6/§8). Toute panne → `null` : repli sur les chips déterministes.

**Le miroir `lib/v2/builder.test.ts`** (Vitest + fast-check) : **22 tests verts** —

1. le jeu des intentions est **déclaré et clos** (les 8 — le cycle de vie entier) ;
2. ∀ texte : `classifyIntent` **total, déterministe**, candidats ⊆ jeu clos, triés score ↓ ;
3. « l'attente » : un message clair est **compris** (le bon kind en tête) ;
4. l'**ambiguïté est détectée**, jamais tranchée en silence (deux verbes forts → `ambigue`) ;
5. un texte sans accroche est **incompris** (jamais une invention) ;
6. ∀ (état, texte) : `applyIntent` **déterministe** — même entrée → même état', mêmes événements, mêmes impacts ;
7. ∀ : le journal est **append-only** (le préfixe d'événements intact) ;
8. GREFFER : « greffe pommes sous app/catalogue » fait pousser l'arbre **là** ;
9. CAPTURER : une idée naît **placée** (niveau/facette/échelle pris du nœud d'attache), `hasMirror=false` ;
10. PROMOUVOIR : « promeus la dernière idée » → un kernel **proposé** (DRAFT, `wroteKernel=false`) ;
11. PROMOUVOIR sans idée → un **refus**, jamais un kernel inventé ;
12. IMPACTER : « quel impact si je modifie app/paiement » → la **vague du sous-arbre** ;
13. **LE MUR (∀ messages)** : pour toute suite de messages, aucune intention ne produit **jamais** une écriture-vérité — re-prouvé sur la grammaire **étendue à 8** ;
14. INTERROGER : total — l'état est **lu** ;
15. **GÉNÉRER sans kernel → refus** (rien à projeter, jamais une invention) ;
16. **GÉNÉRER après promotion → `app_generee`**, version content-adressée **STABLE** (même état → même `app:<hash>`) ;
17. **DÉPLOYER en test sans kernel → refus** (rien à déployer) ;
18. **LA PROD DIRECTE EST REFUSÉE** : jamais la prod sans que CETTE version soit passée en test ;
19. **le chemin légal test → prod** (même version) — les deux environnements portent la version ;
20. **LE CLIQUET RE-MORD** : une nouvelle promotion invalide la prod — il faut REPASSER par le test ;
21. **DELTA sans aucun déploiement** : le delta est **total** (tout est écart), jamais une erreur ;
22. **DELTA après la prod = 0 écart** ; une nouvelle promotion → **1 kernel d'écart**.

**L'écran `/v2/builder`** (`app/v2/builder/page.tsx` + `BuilderClient.tsx`, enregistré dans `lib/v2/screens.ts` — la cohérence WB2-25 reste verte) : la page serveur passe les libellés i18n (`v2Builder`, fr/en) ; le client est **du rendu + l'état d'écran event-sourcé** (tours append-only, `BuilderState` réduit par `applyIntent`). Chaque tour rend visibles le chat (`v2-builder-chat`), « l'attente » (`v2-builder-attente`), « les types de réponse possibles » (`v2-builder-candidates`/`v2-builder-candidate`, **cliquables**), « la réponse » (`v2-builder-events`), « les impacts » (`v2-builder-impacts`/`v2-builder-impact`), le bouton Claude (`v2-builder-claude`), les suggestions canoniques (`v2-builder-suggestion` — dont les phrases du cycle de vie : « génère l'application », « déploie l'application en test », « … en prod », « montre le delta depuis la prod »), l'entrée (`v2-builder-input`/`v2-builder-send`) ; et les panneaux d'état : l'arbre vivant (`v2-builder-tree`), les idées (`v2-builder-ideas`), les kernels proposés (`v2-builder-kernels`, badge DRAFT), le journal (`v2-builder-log`). **Les boutons d'écran ENVOIENT des messages canoniques** — chacun compose la phrase et la repasse par le même pipeline : le chat reste l'**unique source de gestes**, l'écran n'a **aucun pouvoir que le twin n'a pas**. Le déploiement réel (docker/Traefik) reste le pipeline gaté ADR 0052 (`/v2/deploy`, WB2-22), **lié depuis l'écran**. Thème ccup (ADR 0010), bilingue (ADR 0011), note du mur (`v2-builder-wall-note`).

## Méta

**Pourquoi une grammaire fermée et pas un agent.** « Un chat qui fait tout » est le cas d'école du déterminisme-first (§6/§8) : comprendre une phrase **semble** être une tâche de LLM, mais classer un message contre huit intentions à lexiques déclarés est une **fonction pure** — donc elle DOIT être du code, et le code est l'autorité. L'extension au cycle de vie (ADR 0058) en est la preuve par l'acte : trois intentions de plus = trois lexiques + trois réductions + huit tests — jamais « le modèle improvisera ».

**L'app n'existe pas, elle se recalcule.** `emitApp` ne fabrique aucun artefact : la « génération » est une projection des vérités proposées, et sa version `app:<hash>` ne dépend que d'elles. C'est la parade structurelle au build divergent : il n'y a **nulle part** où un build périmé pourrait vivre. Le même geste rend le cliquet vérifiable — comparer `envs.test.version` à la version **recalculée** suffit, aucun registre d'artefacts à consulter.

**Le cliquet d'environnements est une loi, pas une convention.** « Test d'abord » n'est pas un conseil de pipeline : c'est un refus **calculé** (`envs.test.version === emitApp(state).version`, l'égalité content-adressée), prouvé par propriété — y compris le **ré-armement** (toute promotion change la version, donc rouvre la porte). Le refus est un événement explicable, la même honnêteté que les `BlockReason` du mur.

**Le LLM propose, le pipeline juge.** `reformulateAction` est l'unique entrée du modèle, et sa sortie n'est **pas une commande** : c'est un texte qui repasse par `understand`/`applyIntent`. La surface d'autorité du LLM est exactement **zéro** — même étendue au déploiement, la grammaire ne lui ouvre rien.

**Composer les twins, pas les redonder.** Le builder n'a ni table de niveaux, ni logique de greffe, ni promotion à lui : il **appelle** `composition`, `idea`, `goal`. Une seule source par vérité de calcul — corriger `placeIntent` corrige le wizard ET le chat, sans divergence possible.

## Méta-méta

**Le chat total est la forme finale de l'écran unique — et il reste sous la grammaire.** Depuis WB2-00, chaque écran V2 rend UN concept exécutable ; WB2-27 les rend tous **adressables par la langue**, jusqu'au déploiement. Mais la leçon est inversée par rapport au réflexe industriel : on ne met pas un LLM devant le produit, on met une **grammaire** devant le LLM. Le jeu clos des intentions est au chat ce que le jeu clos des niveaux est à la verticale : la condition pour que « tout faire » reste **prouvable**.

**Le cycle de vie est un cliquet, à toutes les échelles.** Le KRD avance dent par dent (red → green → stable) ; l'ADR 0058 montre que **le déploiement a la même forme** : test → prod est une dent, la promotion suivante re-tend le ressort, et la porte ne s'ouvre que dans le bon sens. Le même mot — cliquet — désigne la même structure au grain des vérités (le ratchet des miroirs) et au grain des environnements. Ce n'est pas une métaphore : c'est la même égalité content-adressée qui juge.

**La réponse est un événement, l'impact est une vague — le KRD parle au présent.** `applyIntent` ne « répond » pas : il **réduit** — exactement la forme `state → command → events` des fixtures Operation (N2). Le jour où le builder se branche sur le store réel (S31/S33, OpenQuestion), ses tours deviendront des fixtures rejouables telles quelles — déploiements compris.

**Le mur en ∀ est le seul mur qui compte pour un chat.** Un chat a un espace d'entrées **infini** ; la seule preuve qui le couvre est une **propriété** : ∀ suite de messages, aucune écriture-vérité — et depuis l'ADR 0058, aucune exécution d'infrastructure non plus (`deploiement_test`/`deploiement_prod` sont des événements du twin ; le docker/Traefik réel reste gaté ADR 0052). C'est le test 13 du miroir, re-prouvé sur la grammaire étendue.

## Place dans le cliquet KRD

WB2-27 grave la dent « **un chat, une grammaire fermée — et tout le cycle de vie dedans** » : il consomme les phases stables de WB2-03/ADR 0055 (l'arbre `composes` vivant), WB2-11 (la promotion `promoteIdea` → DRAFT), WB2-22/ADR 0052 (le pipeline de déploiement gaté, lié depuis l'écran), WB2-26/ADR 0056 (l'impact au grain code) et WB2-25 (le registre des écrans). Sa construction a cliqueté red → green deux fois — le miroir (14 tests, ADR 0057) puis son extension (**22 tests**, ADR 0058 : générer, le cliquet d'environnements, le delta) rouges d'abord, verts ensuite. Les OpenQuestions de l'ADR 0058 (brancher `deploiement_test`/`deploiement_prod` sur le pipeline réel ADR 0052 avec approbation humaine, brancher le delta sur `diffGraphs` ADR 0056, des environnements multiples déclarés) rejoignent celles de l'ADR 0057 (le store Postgres réel S31/S33, fusionner `/ai-lab`, l'intent `ancrer_code`) — l'exception bootstrap (§6), documentée, jamais des échecs. Le mur reste intact : le chat **propose** — la promotion réelle passe par idée → miroir → `/goal` → approbation humaine, et le déploiement réel par le pipeline gaté.
