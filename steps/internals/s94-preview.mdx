## Implémentation

S94 ajoute le **planificateur d'environnement de aperçu éphémère**. À partir de la **surface émise d'une phase stable content-adressée** — les empreintes du serveur (S87), du front (S93), de l'infra/Pulumi (ADR 0043) et du plan datastore (S89) + le programme Pulumi émis — il calcule un `PreviewPlan` déterministe. Le package est `back/runtime/preview`.

**Le planificateur (pur, total, content-adressé).**

- `EmittedAppHash(phase, surface)` → l'**adresse de contenu unique** de toute l'app émise de la phase : un join en clés nommées (server ⊕ front ⊕ infra ⊕ datastore), keyé par le hash de phase, passé dans `records.Canonicalize` + `records.Hash` — **réutilise S02**, jamais forké. Tout changement d'octet dans n'importe quel artefact émis → un nouveau hash (aucune aperçu périmée ne peut se faire passer pour la phase).
- `BuildPlan(input)` → le `PreviewPlan` : `validate` (une phase, un projet, un serveur+front+infra, un programme émis du **même** projet) → `EmittedAppHash` → l'URL keyée phase (`subdomainOf` = `"p-"` + les 12 premiers caractères alphanumériques du hash de phase, DNS-safe) → la `StackName` Pulumi (`preview-<projet>-<sous-domaine>`, idempotente) → les commandes `Boot` (`pulumi stack select --create … && pulumi up --yes --cwd <dir>`) et `Teardown` (`pulumi destroy --yes --cwd <dir> && pulumi stack rm --yes …`) → l'`ID` content-adressé du plan entier (S02). Même input → plan byte-identique (même id, même URL).
- `ServedMatchesEmitted(plan, servedAppHash)` → le **done-criterion S94**, rendu déterministe : le aperçu qui tourne expose son hash d'app servie (la sonde `/__aidos_hash` que le serveur émis embarque, égale au `EmittedAppHash` baké dans les octets émis) ; on assert l'**égalité**. Une comparaison pure — le **code** juge, jamais un agent. Un mismatch → un `BlockReason` typé.

**Le déterminisme.** `BuildPlan` et `EmittedAppHash` sont des fonctions **pures, totales** de leur input canonicalisé — pas d'horloge, pas de RNG, pas de fuite d'ordre de map, pas de chemin absolu (le `--cwd` est dérivé par un `dir` qui coupe sur `/`, jamais `filepath`). Même surface émise pour la même phase → `PreviewPlan` byte-identique.

**Le mur + l'honnêteté.** `preview` ne lit que la surface émise (des octets déjà projetés, sous la ligne) et **planifie** l'environnement — il n'écrit **rien** dans le noyau/mirrors/fitness. Un input malformé (pas de phase, pas de serveur, projet croisé) → un `blockreason.BlockReason` typé (la forme S13, code `OUT_OF_SCOPE` réutilisé de la registry close) avec un `how_to_fix` non vide ; jamais un panic, jamais une URL/phase inventée. L'aperçu est un **processus** (Hono Node/Bun/edge — ADR 0040, **jamais** un binaire Go) démarré par le programme Pulumi émis (deploy = ré-émission, DP26).

**Le MCP `aidos-preview`** (`back/mcp/preview`, ADR 0009) expose `plan` · `app_hash` · `check_served` — purs, n'écrivent rien. **Le twin TS** `front/web/lib/preview.ts` reflète le planificateur et alimente la route **action-capable** `/preview` : construire le plan (URL keyée phase + boot/teardown + hash), voir le verdict served↔emitted, basculer « ré-émettre » pour observer une nouvelle empreinte, et **soumettre un vrai formulaire servi par l'aperçu** contre `/api/emitted-submit` — un bouton émis exécute l'opération liée (upload blob inclus).

**Les miroirs.** Godog (`preview.feature` + `preview_bdd_test.go`) : le build-green — l'aperçu sert l'app à une URL keyée phase, le hash servi égale le hash émis, un aperçu périmée est refusée, un aperçu sans phase est refusée, la même phase donne toujours la même URL. rapid (`preview_property_test.go`) : reproductibilité (même input → plan identique), keying phase (deux phases distinctes ne partagent jamais sous-domaine/URL), sensibilité du hash (tout changement d'un composant → un nouveau `EmittedAppHash`), parité served↔emitted (le hash honnête matche toujours, tout autre est refusé). Fixture (`preview_fixture_test.go`) : le cycle BUILD → BOOT → PROBE → TEARDOWN, la **PARITÉ** (`EmittedAppHash` autonome = celui du plan), et les workflows de refus (pas de phase, projet croisé, hash périmé). fast-check (`preview.test.ts`, 6/6) côté twin ; Playwright (`preview.spec.ts`, 5/5) côté écran, dont la soumission réelle avec upload blob.

**OpenQuestion OQ-S87-stackmanifest** (forward-dependency, exception bootstrap §6). Le `StackManifest` first-class (DP02) n'est pas encore une rangée noyau ; `preview` consomme le programme Pulumi déjà émis par `honoemit` (S87) et la surface émise — quand DP02 atterrit, le décodeur s'y branche, le planificateur est inchangé. Comme S93, le datastore **live** de l'app émise reste une dent ultérieure (OQ-S93-datastore) ; `/api/emitted-submit` reste un stand-in en mémoire. OpenQuestions documentées, pas des résidus rouges.

## Méta

S94 est la **première dent de l'EPIC 10** (aperçu/déploiement) : il consomme les surfaces émises par S87/S90/S93 et le plan datastore S89 pour les **monter ensemble** comme un environnement, sans en re-projeter aucun. Sa décision structurante est le **keying par phase content-adressée** : l'URL et l'empreinte d'app sont des **fonctions du hash de phase** (S02), si bien que l'identité « cet aperçu = cette phase » est une **adresse de contenu**, jamais un label mutable. C'est l'extension de la loi des phases content-adressées (S33) au plan de l'environnement : un aperçu est un *artefact* de la phase, pas un état à part qui pourrait dériver.

Le **done-criterion fait par le code** (`ServedMatchesEmitted`) est l'application directe du §8 (« le juge est déterministe ») au plan déploiement : « l'aperçu sert-elle la bonne app ? » n'est pas une appréciation, c'est une **égalité de hash**. Le serveur émis embarque sa propre empreinte (`/__aidos_hash`) ; la sonde la renvoie ; le code compare. Si l'aperçu servait un artefact périmé (un re-démarrage sur de vieux octets), le hash divergerait et le mirror passerait rouge. C'est aussi ce qui rend le **démontage déterministe** vérifiable : la commande de teardown est le miroir exact du boot, connue d'avance, pas un effet de bord oublié.

## Méta-méta

S94 illustre le **déterminisme-first** sur le plan de l'environnement : tout ce qui *peut* être une fonction pure l'**est** — l'adresse de contenu de l'app (un hash), l'URL (une dérivation du hash de phase), les commandes boot/teardown (une projection de la phase), le verdict (une comparaison). Aucun LLM n'entre dans la planification ni dans le jugement. Le « démarrer = ré-émettre » (DP26) est la forme déploiement de la règle « jamais prompt → code » : on ne *bricole* pas un serveur de aperçu, on **exécute le programme d'infra émis depuis la phase**, lui-même byte-stable. L'aperçu est jetable précisément parce qu'elle est entièrement reconstructible depuis la phase — rien d'unique ne vit dans l'environnement.

Et S94 respecte le **mur** sans exception : il lit des surfaces émises (sous la ligne) et planifie un environnement éphémère ; la soumission du formulaire servi écrit dans un datastore sous la ligne, jamais le noyau/mirrors/fitness. Il n'invente aucune URL, aucune phase, aucune règle, et n'écrit jamais une vérité. La porte vers le noyau reste `idée → miroir → /goal → approbation humaine` ; S94 n'en franchit aucune.
