## En une phrase

BA26 étend le type `AgentRun` (`back/runtime/agentrun`) pour le rejeu (gap A2) : un run gagne `Impl` (le hash de contenu de son `AgentImplementation`), `Seed` (déclaré en BA01, sinon dérivé `Hash(impl‖pack‖item)`) et `ProviderTranscript`. C'est une **nouvelle @version** du record — content-addressed, append-only — **jamais** une mutation in-place du hash existant (anti-overwrite §9). Un run legacy sans graine reste lisible ; un nouveau run en porte une.

## Implémentation

Le type vit dans `back/runtime/agentrun/agentrun.go` ; le jumeau TS dans `front/web/lib/agentrun.ts` ; la migration dans `back/migrations/agentrun_replay_baseline.sql` ; le panneau dans `front/web/components/AgentsPanel.tsx` (sous-section `replay-envelope`).

- **Les trois champs de rejeu** sur `AgentRun`, tous `omitempty` (load-bearing) :
  - `Impl string` — le hash de contenu de l'`AgentImplementation` (`agentimpl.Hash`, BA03) ;
  - `Seed string` — la graine, déclarée (BA01) ou dérivée ;
  - `ProviderTranscript string` — la réf au transcript (rédacté en BA28) que le rejeu re-nourrit.
- **`canonicalBody` étendu — la clé de l'additivité.** Les trois clés n'entrent dans l'adresse de contenu **que si elles sont non vides**. Un run legacy (seedless) les omet toutes les trois ⇒ son corps canonique est **octet-identique** à la forme pré-BA26 ⇒ son hash est **inchangé**. Un run de rejeu ajoute exactement les clés non vides — chacune **élargit réellement** l'adresse (le miroir property l'épingle : un run différant d'un seul champ de rejeu obtient un id différent — pas un champ mort).
- **`LegacyID(r)`** — reconstruit l'adresse qu'un run aurait eue sous le corps pré-BA26 (les huit champs d'origine), indépendamment de tout champ de rejeu. C'est la **preuve du supersede-via-version** : pour un run seedless, `Record(r).ID == LegacyID(r)` — le hash legacy n'est jamais muté en passant.
- **`DeriveSeed(impl, pack, item)`** — la graine dérivée déterministe : `Hash(Canonicalize({impl, pack, item}))` sur le schéma S01/S02 (`records.Hash` ∘ `records.Canonicalize`, RÉUTILISÉ, jamais forké). Pure, totale, non vide pour toute entrée non vide ; un trio différent ⇒ une graine différente.
- **`SeedFor(declared, impl, pack, item)`** — la source unique de « quelle graine ce run reçoit-il ? » : la graine **déclarée verbatim** si la couche en a déclaré une (BA01), sinon la graine **dérivée**. Declared-wins, derive-as-fallback.
- **La migration `agentrun_replay_baseline.sql`** (expand-only, forward-only, append-only) — ne touche aucune table/GRANT antérieure (S52 `agent_layer_baseline`, BA20 `scheduler_role_baseline` intactes). Le `body` étant JSONB, les trois champs y vivent comme clés ; la migration ajoute deux **index partiels** (`agent_run_seed_idx` sur `body->>'seed' WHERE body ? 'seed'`, idem pour `impl`) — un run legacy ne coûte rien — et un **CHECK de cohérence** `agent_run_replay_coherent_chk` : un `provider_transcript` SANS `impl`+`seed` est refusé (un run avec rien à rejouer). La posture S52 est ré-énoncée (le rôle agent reste INSERT+SELECT, append-only, aucune écriture au-dessus de la ligne).
- **Le jumeau TS** — `AgentRun` gagne `impl?`/`seed?`/`providerTranscript?` (optionnels, additifs). La logique de graine est **single-sourcée** dans `lib/agentlayer` (`deriveSeed`/`seedFor`, le jumeau FNV-1a ; le Go SHA-256 fait foi) ; BA26 la **réutilise** et expose `runSeed(declared, impl, pack, item)` (le jumeau au grain-run de `SeedFor`) + `agentRunReplayCoherent(run)` (le jumeau du CHECK de la migration).
- **Le panneau action-capable** (`replay-envelope`) — deux radios de mode (legacy / replay) + bouton **Construire le run** (`replay-build`). Mode replay : le run porte `impl`, une graine dérivée (`runSeed("", …)`) et un transcript ; mode legacy : aucun des trois. L'écran affiche `impl`, `seed` (tag « dérivé »), le transcript, et le verdict de cohérence (`replay-coherent`, `data-coherent`). Thémé (ADR 0010, tokens) + bilingue FR/EN (ADR 0011, next-intl).
- **Les miroirs** :
  - *Property rapid* (`back/runtime/agentrun/agentrun_replay_property_test.go`, N1) — (1) **roundtrip** Marshal→Unmarshal identité sur chaque champ ; (2) **legacy lisible** : un run seedless Record + lit, et son id == `LegacyID` (hash legacy stable) ; (3) `DeriveSeed`/`SeedFor` déterministe+total+non-vide, declared-wins ; (4) chaque champ de rejeu participe à l'adresse (pas de champ mort) ; (5) toujours pas une couche (aucun `Version`, aucun `Mirror`).
  - *Migration-roundtrip Testcontainers* (`back/runtime/agentrun/migration_roundtrip_test.go`, N5, Postgres réel) — un run de rejeu persiste et se relit sans perte (les index partiels résolvent un lookup par seed et par impl) ; un run legacy seedless persiste et se relit avec les clés de rejeu absentes ; le CHECK refuse un transcript sans impl+seed et admet une ligne legacy ; **le mur tient** : le rôle agent INSERT+SELECT son propre run mais NI UPDATE NI DELETE (append-only), et aucune écriture dans `kernel.agent_layer`.
  - *Reproductibilité fast-check* (`front/web/lib/agentrun-replay.test.ts`, N1) — `deriveSeed` déterministe+non-vide (+ exemples fixes pour « différent ⇒ différent », le jumeau FNV-1a 32-bit n'étant pas l'autorité) ; `runSeed` declared-wins/derive-fallback ; `agentRunReplayCoherent` (legacy cohérent, transcript-sans-trio incohérent, trio-complet cohérent) — 9 tests verts.
  - *E2e Playwright* (`tests/e2e/agents.spec.ts`, bloc BA26, N0) — contrôles présents ; un nouveau run porte graine dérivée + impl + transcript et est cohérent ; un run legacy seedless reste lisible + cohérent (back-compat).

Vérifié vert : `go test ./runtime/agentrun/` (property + Testcontainers sur Postgres réel), `gofmt -l` clean, `go vet` clean, `npx vitest run lib/agentrun-replay.test.ts` (9 passés), `tsc --noEmit` clean, `biome` clean, et les 3 cas Playwright BA26 verts.

## Méta

**Pourquoi étendre le record par une @version plutôt que muter le hash ?** Parce que l'identité d'un run *est* son hash de contenu (S01/S02). Recalculer le hash d'un run existant après ajout de champs, ce serait **réécrire l'histoire** — l'append-only volerait en éclats, et tout pointeur vers l'ancien id deviendrait orphelin. BA26 superpose : `omitempty` + `canonicalBody` qui exclut les champs vides garantit que l'ancien corps reste octet-identique, donc l'ancien hash reste valide. `LegacyID` n'est pas décoratif : c'est l'assertion exécutable que la migration est *annoncée*, pas un effet de bord.

**Pourquoi `omitempty` est-il load-bearing et pas cosmétique ?** Sans lui, un `Seed: ""` entrerait dans le JSON canonique comme `"seed":""` et **changerait le hash** de tous les runs legacy. `omitempty` + l'omission explicite dans `canonicalBody` sont la *seule* raison pour laquelle un run pré-BA26 garde son id. C'est pourquoi le miroir property l'épingle des deux côtés (legacy stable ∧ champ-de-rejeu adressé).

**Pourquoi `DeriveSeed` réutilise `records.Hash` au lieu d'un RNG ?** Parce qu'une graine *dérivée* doit être reproductible : `Hash(impl‖pack‖item)` est la même à chaque fois pour le même trio. Un `rand` la rendrait non rejouable — exactement le contraire du but. La graine n'est aléatoire que si la couche en *déclare* une (BA01) ; sinon elle est calculée, jamais tirée.

**Pourquoi seulement une *réf* de transcript ici, et la rédaction en BA28 ?** Parce que le verrou gap H1 (« le ledger n'est pas un store de secrets ») est une discipline de *persistance*, pas de *schéma*. BA26 ouvre le champ ; BA28 enforce que ce qui est persisté est rédacté/hashé/chiffré avant écriture. Découpler les deux garde chaque step minimal et vérifiable seul.

## Méta-méta

BA26 boucle l'extension de schéma sur les trois invariants AIDOS.

- **Le mur (NIVEAU 3).** `runtime.agent_run` reste **sous la ligne** : un run est un événement runtime, pas une couche/vérité — aucun champ `version`, aucun champ `mirror`, comme S52 l'a déclaré. L'extension élargit ce qu'un run *enregistre*, jamais ce que l'agent *peut écrire* : le rôle agent garde INSERT+SELECT, append-only, et n'a aucune écriture au-dessus de la ligne (le roundtrip Testcontainers l'assert positivement). Le schéma de truth (BA01 pour la SOURCE, BA20/BA26 pour le SCHÉMA) passe par la porte légale / supersede-via-version, jamais une mutation silencieuse.
- **Determinism-first.** Tout est fonction pure et fait foi : `Record` (content-address), `DeriveSeed`/`SeedFor` (graine reproductible), `LegacyID` (preuve d'additivité), `agentRunReplayCoherent` (le CHECK). Aucun LLM ; aucune horloge (les timestamps sont SUPPLIED) ; aucun RNG (la graine est déclarée ou dérivée). Les miroirs de reproductibilité (rapid + fast-check) épinglent : même entrée ⇒ même sortie. Une graine tirée au hasard serait une faille de déterminisme qui bloquerait le step.
- **Anti-Goodhart.** L'identité d'un run est son hash de contenu — elle ne peut pas être gonflée ni gamée : changer un champ change l'id, ajouter un champ de rejeu l'élargit honnêtement, et un run vide ne peut pas se faire passer pour un autre. La cohérence du rejeu (transcript ⇒ impl+seed) est un CHECK déclaré au bord du stockage, pas une convention qu'on pourrait contourner. Un run reste une trace honnête de ce qui s'est passé, jamais une vérité auto-déclarée.
