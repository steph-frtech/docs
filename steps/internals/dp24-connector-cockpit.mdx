## Implémentation

### Le paquet — `back/runtime/connectordeclare` (3 fichiers)

DP24 pose le **chemin PROPOSE** d'une déclaration de connecteur : la fonction runtime que l'action serveur du cockpit appelle pour graver un connecteur / Skill / serveur MCP — non par une écriture directe du Kernel, mais par un **ChangeSet PROPOSÉ** (`DRAFT`, jamais `APPLIED`). C'est une **composition pure** de deux moteurs existants — DP20 (le modèle de connecteur) et S20 (l'enveloppe transactionnelle) — **sans forker** ni l'un ni l'autre (ADR 0007). Tâche **backend-only** ; le mur tient (aucun GRANT). C'est la pièce qui **clôt l'EPIC E**.

Trois fichiers neufs (anti-overwrite respecté, §9) :

- `back/runtime/connectordeclare/connectordeclare.go` — l'op pure : `ProposeConnectorDeclaration`, `declarationLabel`, `ErrInvalidConnector`, `ParentPhaseConnectors`.
- `connectordeclare_fixture_test.go` — le **miroir fixture N2** (`state → command → events`), **écrit RED-first** — **5** `Test` funcs.
- `connectordeclare_property_test.go` — le **miroir property ∀** (rapid), **écrit RED-first** — **4** `Test` funcs × **100** cas.

### `ProposeConnectorDeclaration` — valider (DP20) puis ouvrir un DRAFT (S20)

```go
func ProposeConnectorDeclaration(source connector.ConnectorSource) (changeset.ChangeSet, error)

const ParentPhaseConnectors = "connectors"
var  ErrInvalidConnector  error // wraps the DP20 verdict (multi-%w)
```

La fonction est **pure et totale** — aucun DB, aucune horloge, aucun aléa, aucun I/O — et fait, dans l'ordre :

1. **Valider (DP20)** — `connector.Validate(source)`. Une source invalide retourne `fmt.Errorf("%w: %w", ErrInvalidConnector, err)` **et** un `changeset.ChangeSet{}` **vide** : **aucun draft pour un monstre**. Le double `%w` (multi-%w) permet au front de faire `errors.Is` sur **`ErrInvalidConnector`** *et* sur le verdict DP20 verbatim (`connector.ErrAIDirectDBForbidden`, `ErrRWRequiresAuthority`, …) — le `BlockReason` actionnable est celui de DP20.
2. **Corps canonique (DP20)** — `connector.CanonicalBody(source)` rend les bytes exacts du corps S02 que le rôle *writer* graverait (réutilisé, jamais re-frappé).
3. **Ouvrir un DRAFT (S20)** — `changeset.Open(declarationLabel(source), ParentPhaseConnectors, spec, mirror)`. `Open` rend **toujours** `StatusDraft` — la fonction n'a **aucun chemin vers `Apply`** (le mur : l'agent n'applique jamais une vérité).

```go
spec := &changeset.Delta{
  Kind:   "add",               // une déclaration AJOUTE une source
  Target: "connector_source",  // records.KindLayer
  Body:   json.RawMessage(body), // = connector.CanonicalBody(source), corps S02
}
mirror := &changeset.Delta{
  Kind:   "add",
  Target: "kernel.connector-source",
  Body:   json.RawMessage(`{"reflects":"kernel.connector-source","test_kind":"invariant"}`),
}
```

Le `MirrorDelta` garde l'enveloppe **COMPLÈTE** (KRD §33) : un `spec_delta` **sans** son `mirror_delta` est un **monstre** que le gate de commit refuse — donc `changeset.SpecHasMirror` ne refuse **jamais** l'enveloppe, et un humain **POURRAIT** l'appliquer via `/goal → approbation`.

### La forme du ChangeSet rendu — pour le front

Le `changeset.ChangeSet` retourné porte **toujours** :

- `Status == changeset.StatusDraft` (`"DRAFT"`) — **jamais** `APPLIED` (le mur ; l'humain applique, via le rôle *writer*, par `/goal → approbation`) ;
- `AppliedAt == nil` — une enveloppe non appliquée n'a aucune estampille de commit ;
- `ID` = l'**adresse de contenu S20** (`records.Hash` via `changeset.Open`, qui **exclut** `Status`/`AppliedAt` du hash) — même source ⇒ **même id** ;
- `Label == "declare {kind}: {name}"` (`declarationLabel`, déterministe — ex. `declare connector: slack-notify`) ;
- `ParentPhase == "connectors"` (`ParentPhaseConnectors` — déclaré, pas inventé par appel, pour que l'id soit byte-stable) ;
- un `SpecDelta` non nil (`add` / `connector_source` / le corps S02 — **byte-round-trip** au corps canonique DP20) **et** un `MirrorDelta` non nil (l'enveloppe est committable **si et seulement si** un humain l'applique par le gate).

### Le front, S58 et le jumeau TS — réutilisés, jamais re-frappés

L'**action serveur** du cockpit (« déclarer un connecteur ») appelle `ProposeConnectorDeclaration` et **rend** le `DRAFT` à l'écran (status `"DRAFT"`, jamais appliqué) — c'est le PROPOSE montré. La porte MCP légale par laquelle elle passe est le `changeset_open` **déjà enregistré** de la gateway **S58** (un propose below-the-line, **aucun nouvel outil de gateway**). Le **jumeau TS** existe déjà — `front/web/lib/connector-source.ts` (`validate` / `contentId` / `canonicalBody`, mêmes jeux clos + le verdict `AI_DIRECT_DB_ACCESS_FORBIDDEN`). L'approbation et la seconde approbation RW restent celles de l'**humain** (S20 `Apply` + `connectorenforce.ConnectorRuntimeApproval`), **jamais** l'agent (le greffage UI + son e2e Playwright est l'affaire d'un agent front séparé).

## Méta

- **Le miroir Go est l'épreuve « déclaration ⇒ ChangeSet proposé, jamais appliqué ».** Le miroir fixture épingle les formes d'action comme `state → command → events` : `state` = la source DP20 déclarée, `command` = `ProposeConnectorDeclaration`, `events` = soit le ChangeSet `DRAFT` proposé (RO/RW valides), soit le refus + **aucun** draft (IA→DB, RW-sans-autorité). Le miroir property mesure le cœur déterministe : ∀ source valide, **même id**, **corps round-trip**, et l'invariant capital — **toujours `DRAFT`, jamais `APPLIED`**. C'est l'`ui-completeness` côté preuve : que l'écran propose et ne grave jamais en direct n'est pas une promesse, c'est une propriété prouvée. Et le miroir e2e Playwright du parcours complet (déclarer → basculer RO/RW → approuver une action RW → lire la timeline d'audit → enregistrer un MCP) est l'autre face de ce miroir — le geste exécutable depuis l'écran, prouvé de bout en bout (agent front).

- **Déterminisme-first (§6/§8) : valider et ouvrir sont des fonctions pures, donc du code.** `ProposeConnectorDeclaration` n'invite **aucun** LLM : le verdict de validation est celui de DP20 (set-membership sur des jeux clos, jamais un jugement), l'id du ChangeSet est l'adresse de contenu de S20 (`records.Hash`), le label est dérivé déterministiquement du kind + name. La fonction est pure et totale — aucun DB, aucune horloge, aucun aléa, aucun I/O — donc même source ⇒ même propose (le miroir property le pin). Proposer une déclaration est une **composition de deux moteurs purs**, pas une décision floue.

- **Réutiliser plutôt que réinventer (ADR 0007), sur DP20 + S20.** DP24 n'invente **ni** modèle de connecteur **ni** moteur de changeset : il **réutilise** `connector.Validate` / `connector.CanonicalBody` / `connector.ErrAIDirectDBForbidden` (DP20, composé jamais forké) et `changeset.Open` / `changeset.Delta` / le jeu clos `DRAFT|APPLIED|REVERTED` (S20, importé jamais re-frappé). Le front réutilise le jumeau TS déjà écrit ; la porte MCP réutilise le `changeset_open` déjà enregistré de la gateway S58 (aucun nouvel outil). DP24 n'ajoute que la **glu** : valider-puis-ouvrir, et la référence de miroir qui garde l'enveloppe complète. Un seul modèle de connecteur, un seul moteur de changeset dans tout AIDOS.

## Méta-méta

- **L'écran PROPOSE un ChangeSet — jamais une écriture Kernel directe.** C'est le mur (§2) gravé au cœur du geste : `ProposeConnectorDeclaration` valide puis **ouvre** un `DRAFT`, et n'a **aucun chemin** vers `changeset.Apply`. Elle n'écrit **rien** dans `kernel`, `mirrors` ou `fitness` ; elle ne consulte **aucun** truth-store. L'agent (et l'écran qu'il sert) n'a **aucun GRANT** pour graver une vérité ; la seule porte est `idée → miroir → /goal → approbation`, où c'est l'**humain** (via le rôle *writer* de la CLI `aidos`) qui applique. Le bouton « déclarer un connecteur » ne grave rien — il **propose**, et la déclaration ne devient une vérité que si un humain l'approuve. Les **deux portes** restent distinctes (amendement A2) : la DÉCLARATION above-the-line (propose → ChangeSet → approbation), l'EXÉCUTION below-the-line (`connectorenforce.ConnectorRuntimeApproval`, DP21) — DP24 n'ouvre que la première.

- **`ui-completeness` : aucune capacité connecteur headless — tout se fait par écran.** L'enjeu porteur de DP24, c'est que **chaque** capacité de la couche connecteurs soit atteignable **et exécutable** depuis l'écran (§7) : déclarer (PROPOSE), basculer RO/RW, approuver une action RW au runtime, séparer interne/externe/IA/cloud, lire la timeline d'audit Merkle GV03 (DP22), enregistrer un MCP/Skill (un op = un outil MCP, ADR 0009). Une capacité connecteur qui ne serait atteignable que sans écran serait un **trou headless** qui bloquerait l'étape, au même titre qu'un monstre. *Tout se fait par écran* : un cockpit qui fait tout, pour toute la couche.

- **DP24 clôt l'EPIC E — la couche connecteurs est complète et pilotable.** L'EPIC E a posé les sources (DP20), l'enforcement runtime (DP21), l'audit Merkle (DP22) et l'infra émise (DP23) ; DP24 leur donne enfin un **poste de pilotage exécutable**, sans franchir le mur. La loi de complétude (Mandat A, §5) veille : un geste sans miroir serait un **monstre** — `ProposeConnectorDeclaration` ne vit que parce qu'il porte sa preuve vivante (fixture + property, RED-first). Et c'est *load-bearing* : sans ce cockpit, les briques de l'EPIC E resteraient des moteurs sans poste de commande — gouvernées, auditées, émises, mais **inatteignables par l'humain**. Avec lui, la couche connecteurs est **complète de bout en bout**, et l'EPIC E est clos.
