## Implémentation

### Le paquet — `deploycockpit` (nouveau, additif)

DP29 ajoute **UN seul paquet**, `back/runtime/deploycockpit/`, **strictement additif** (anti-overwrite §9 — aucun fichier existant n'est touché). C'est une tâche **backend-only** : le `DeployPanel.tsx` du front et son e2e **existent déjà** (la partie lourde de l'EPIC F) ; le livrable de DP29 est la **projection Go pure + son miroir**. Le mur tient (le cockpit **lit** des faits below-the-line, il n'écrit **rien**).

Les trois fichiers :

- `back/runtime/deploycockpit/deploycockpit.go` — l'impl : la projection PURE du cockpit.
- `back/runtime/deploycockpit/deploycockpit_property_test.go` — **6** fonctions de test (rapid, N1).
- `back/runtime/deploycockpit/deploycockpit_fixture_test.go` — **8** fonctions de test (N2).

### `Project` — la `DeployCockpitProjection` qui ASSEMBLE (jamais ne recalcule)

Le cœur du paquet : une projection **PURE, déterministe** qui assemble — en une seule passe — tout ce que l'écran `/deploy` rend pour un projet.

```go
func Project(projectID string, in Input) Projection
```

`projectID` est l'argument **positionnel** du spec (« `DeployCockpitProjection(projectID, …)` ») : quand il est vide, il retombe sur `in.Project` — le caller peut passer le projet positionnellement **ou** dans l'`Input` (le `Project` de la projection fait écho à celui qui est non vide, **`projectID` l'emportant**).

`Project` **n'invente rien, ne recalcule rien**. Chaque verdict est **lu** des jumeaux purs :

- **les `PhaseCard`** : pour chaque phase, la **liveness** = `LivenessOf(p.Phase)` et la **déployabilité** = `deploy.IsDeployable(p.Phase, p.Gate)` (le `reasons == nil` est normalisé en `[]string{}`). Un index `livenessByPhase` est construit pour que chaque environnement **peigne sa phase servie depuis la MÊME source** — jamais re-dérivée ;
- **les `EnvironmentCard`** : l'échelle par défaut (`defaultLadder`) si aucun env n'est fourni ; la **porte DP28** sur `EnvPreview` (`HumanValidated` + `StagingPromotable = HumanValidated && ServedPhaseID != ""`) ; la `ServedLiveness` depuis l'index ; l'**URL live** = `envrollback.LiveURL(...)` (DP28, toujours https) ; le `Domain`/`TLS` depuis `domainByEnv` (DP27) ;
- **les `Domains`** (DP27, `nil` normalisé en `[]`) et les **`Profiles`** (`stackmanifest.Profiles()`, l'ensemble **fermé** DP11) ;
- enfin `proj.Hash = proj.contentAddress()`.

### `LivenessOf` — projection PURE de la coupe (jamais vert sur rien)

```go
func LivenessOf(p phases.StablePhase) Liveness {
  if !p.Stable {
    return LivenessRouge
  }
  if len(p.Cut) == 0 && len(p.SensorStatus) == 0 {
    return LivenessInconnu
  }
  return LivenessVert
}
```

Le trichotome est **fermé** — `LivenessVert` / `LivenessRouge` / `LivenessInconnu` — et c'est une **projection PURE** de la coupe S23 (`phases.StablePhase`, lue jamais recalculée) : une phase **instable** ⇒ **rouge** ; une phase **stable** *sans* évidence (coupe vide ∧ aucun capteur) ⇒ **inconnu** (la liveness n'est pas encore calculable) ; une phase **stable** *avec* évidence ⇒ **vert**. Le cockpit **ne peint jamais du vert sur rien** — l'absence d'évidence est `inconnu`, jamais un faux vert.

### `EnvPreview` + `DefaultLadder` — l'échelle fermée

```go
const EnvPreview scope.Environment = "preview"

func DefaultLadder() []scope.Environment // copie de {EnvPreview, EnvStaging, EnvProd, EnvFutureCloud}
```

`EnvPreview` est le rung **runtime** de DP28 (l'éphémère, le plus bas) — **pas** un scope-env du kernel ; le cockpit mêle le rung runtime aux rungs scope, donc la const porte la valeur verbatim et `envrollback.LiveURL` la consomme via `envrollback.Environment`. `DefaultLadder()` renvoie une **copie** de l'échelle déclarée une fois — **jamais dérivée d'une itération de map** (déterminisme).

### Les types — `Input` / `Projection` et leurs cards

`Input{Project, Phases []PhaseInput, Environments []EnvironmentInput, Domains []domainbind.EnvDomainBinding}` ; `PhaseInput{NodeID, Label, Head, Phase phases.StablePhase, Gate deploy.Gate}` ; `EnvironmentInput{Env, ServedPhaseID, DomainRoot, HumanValidated}`. En sortie : `Projection{Project, Phases []PhaseCard, Environments []EnvironmentCard, Domains, Profiles []stackmanifest.Profile, Hash}` ; `PhaseCard{NodeID, Label, Head, Liveness, Deployable, Reasons}` ; `EnvironmentCard{Env, ServedPhaseID, ServedLiveness, LiveURL, Domain, TLS, HumanValidated, StagingPromotable}`. Chaque champ est un **fait déjà projeté** below-the-line ; le cockpit ne fait que les **assembler**.

### `contentAddress` — l'adresse de la projection (records, S02 réutilisé)

```go
func (p Projection) contentAddress() string // records.Canonicalize+Hash sur le corps MOINS le champ Hash
```

L'adresse hache le **corps canonique** de la projection **moins** son propre champ `Hash` (un champ ne peut pas s'adresser lui-même — `canonicalProjectionBody` re-marshalle un clone avec `Hash` vide), si bien que « même DAG ⇒ même projection » est **une seule comparaison d'octets**. C'est `records.Canonicalize+Hash` de S02, **réutilisé** — jamais un schéma de hash forké. PURE, TOTAL : un échec de `Canonicalize`/`Marshal` (une faute de programmation — les formes sont des structs simples) se replie en hash de `"{}"`, donc le hash **diffère**, jamais **égal en silence**.

## Méta

- **Le miroir Go est l'épreuve « le cockpit ASSEMBLE, il ne recalcule pas », ∀.** Le miroir property mesure le cœur déterministe : il épingle que la projection est **reproductible** (`TestReproducibility` — même `Input` ⇒ `Projection` + `Hash` byte-identique), que la liveness est une **projection pure** (`TestLivenessIsPureProjection` — un état rouge n'est **jamais** peint vert, aucune estimation), que la déployabilité est **exactement** le stop-gate DP26 (`TestDeployabilityIsTheStopGate` — rouge ⇒ non-déployable avec ses reasons, identiques à `deploy.IsDeployable`), que la porte humaine est **reflétée** fail-closed (`TestHumanGateReflected` — preview→staging promotable **iff** validé), et que les profils + l'échelle sont **fermés** (`TestProfilesAreClosed`, `TestDefaultLadderIsClosed`). Les fixtures (N2) épinglent le parcours : phases colorées, vert déployable vs rouge refusé, env qui sert une phase + son URL, la porte staging, les profils offerts, le content-address, la résolution du `projectID`, et la **totalité** (un input vide ⇒ projection vide-mais-typée, jamais un panic). Que le cockpit *reflète* la vérité plutôt que de la *re-juger* n'est pas une promesse — c'est une propriété prouvée.

- **Déterminisme-first (§6/§8) : assembler, projeter une liveness, juger une déployabilité sont des fonctions pures, donc du code.** DP29 n'invite **aucun** LLM. `Project` est **TOTAL** — pas de DB, pas d'horloge, pas de rng, pas de fuite d'ordre de map (les slices sont en ordre de frontière / d'échelle, les reasons triés par `IsDeployable`, les profils en ordre canonique), pas d'I/O. `LivenessOf` est une suite de comparaisons pures ; la déployabilité est `deploy.IsDeployable` (le code DP26) ; la porte humaine est un `if` déterministe ; l'adresse est `records.Hash` (S02). Même `Input` ⇒ `Projection` byte-identique (le miroir de reproductibilité le pin). Un cockpit qui ferait *deviner* à un agent l'état d'une phase serait un **trou de déterminisme** — ici, le code juge, l'agent ne s'assoit jamais dans la boucle.

- **Réutiliser plutôt que réinventer (ADR 0007), sur DP25–28 + DP11 + S02.** DP29 n'invente **ni** un moteur de liveness, **ni** un moteur de déployabilité, **ni** un mécanisme d'URL : il **compose** les jumeaux purs déjà éprouvés — la liveness **rit** `phases.StablePhase` (S23/S86, son `Stable`/`Reasons` **EST** la liveness), la déployabilité **est** `deploy.IsDeployable` (DP26, le **même** stop-gate « done is computed » que le deploy/promote hérite), l'URL live **est** `envrollback.LiveURL` (DP28), les bindings de domaines **sont** `domainbind.EnvDomainBinding` (DP27), les profils **sont** `stackmanifest.Profiles` (DP11), l'adresse **est** `records.Canonicalize+Hash` (S02). Il **ne duplique** rien : pas un second moteur à côté, mais **une projection** qui lit et assemble — le read-side companion des jumeaux d'action DP25–28.

## Méta-méta

- **Le cockpit LIT below-the-line — il n'écrit AUCUNE vérité (le mur, §2).** C'est la frontière fine du mur. Le cockpit **lit** des faits déjà projetés below-the-line (les coupes du DAG S23, les promotions DP28 enregistrées, les bindings DP27) et **assemble** le read model que l'écran rend. `Project` n'écrit **rien** dans `kernel`, `mirrors` ou `fitness` — la projection ne fait que **lire**, et un input malformé donne une projection vide-mais-typée, jamais un panic. Quand l'humain **déclenche** un déploiement/rollback depuis l'écran, ce n'est jamais un write-to-truth depuis cette projection : c'est un **acte de runtime below-the-line** (preview/staging) **ou** une **proposition de ChangeSet** pour les vérités d'infra. L'agent n'a aucun GRANT pour graver une vérité ; la seule porte vers le kernel reste idée → mirror → `/goal` → approbation humaine.

- **La liveness est une projection PURE du DAG — JAMAIS une estimation (ui-completeness : aucune deploy API headless).** Le cockpit colore chaque phase `vert`/`rouge`/`inconnu` par **projection** de la coupe cohérente (S23), jamais par un calcul propre ni — surtout — par une *estimation*. Une phase stable sans évidence est `inconnu`, jamais un faux vert : le cockpit refuse de peindre du vert sur rien. Et *tout se fait par écran* : chaque capacité de l'EPIC F (déployer, promouvoir, revenir en arrière, choisir un profil, voir l'URL live, suivre la timeline d'audit) est **atteignable et exécutable** depuis le cockpit — **aucune API de déploiement headless** (ui-completeness : une capacité sans écran serait un trou). Le `DeployPanel.tsx` + l'e2e l'attestent ; un follow-up pourrait ajouter le twin TS `lib/deploy-cockpit.ts` (motif `lib/env-binding-cockpit.ts`) pour que l'écran consomme la projection — mais l'écran rend déjà DP25–28 via les actions existantes.

- **DP29 ÉTEND S99 et CLÔT l'EPIC F — additif, sans rien casser (anti-overwrite §9).** La règle est nette : DP29 **ajoute** un paquet (`back/runtime/deploycockpit/`), **aucun** fichier existant n'est touché (`git status` : seulement `?? back/runtime/deploycockpit/`). Il **étend** S99 (le cockpit par-projet) par le read model de déploiement, et il **clôt l'EPIC F** : toute la machinerie posée par DP25–28 (preview par profil, pipeline keyé sur les phases stables, domaines + TLS, environnements + rollback + porte humaine) se retrouve **assemblée** dans un seul cockpit pilotable par écran. La loi de complétude veille : une projection sans miroir serait un **monstre** — le cockpit ne vit que parce qu'il porte sa preuve vivante (property + fixture, RED-first). C'est l'anti-overwrite poussé jusqu'à la clôture d'un EPIC : on **ajoute** un read model, on **n'altère** rien des jumeaux d'action.
