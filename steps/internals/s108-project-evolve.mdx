## Implémentation

S108 ajoute la **boucle médiane par projet** : `back/archive/projectevolve` (sous-système Archive, KRD §62/§64/§66, ROADMAP-app-builder §S108, EPIC 12 / E12). Elle **réutilise verbatim** la sandbox + la gate de promotion S42 (`back/runtime/evolve` — `Confine`, `Promote`, les zones `can_write`/`cannot_write`, les statuts mirror/out-of-sample) et la sélection QD S26 (`back/archive/qd` — `Elites`, MAP-Elites, « une élite verte par niche, fitness max »). Elle **ajoute** strictement ce que S108 exige : l'**ancrage à un miroir fixe**, le **cull** des variantes qui cassent la vérité, la **frontière projet** (S55) et la **grammaire de niche project-scopée**. Elle **n'écrit rien** (le mur) : chaque fonction rend une VALEUR ; toute persistance branches/reports/ideas passe par le grant `aidos` du MCP `evolve`, jamais le rôle agent.

**Le cull tue les casseurs de vérité — `Cull(FixedMirror, []Variant) → CullResult`.** Il passe le **miroir fixe** (le juge déterministe) sur chaque variante et retire celles dont le `Mirror` n'est pas `green` — **quel que soit** leur `Fitness` (l'ancre anti-Goodhart) — plus celles d'un **autre projet** (la frontière S55). Les survivantes sont préservées dans l'ordre ; les `Killed` sont triés (byte-stable). C'est le « miroir + property test tuent les variantes cassant la vérité » de la roadmap, fait code.

**Les niches sont project-scopées — `Niches(FixedMirror, []Variant) → map[string]Variant`.** Il **cull** d'abord (un casseur ne peut JAMAIS devenir élite), puis projette les survivantes dans la grammaire S26 via `NicheKey(v) = projectID::niche` (préfixe projet → deux projets aux niches identiques ne collapsent jamais) et délègue à `qd.Elites` — qui **réaffirme** la règle clé (seul le vert admis) et le « fitness max gagne, départage par id ». On ne re-coine ni la niche ni la fitness ; chaque élite est une survivante réelle, verbatim.

**La promotion est gatée par l'autorité — `Promote(FixedMirror, Variant, authorityApproved) → PromotionResult`.** S108 ajoute UN check de **frontière** AVANT la gate : une variante d'un autre projet est refusée avec `SANDBOX_ESCAPE` (le code central S82 d'isolation cross-projet — le mur S55). Sinon il **délègue** à `evolve.Promote`, la gate binaire à trois conditions `mirror_green ∧ out_of_sample_green ∧ authority_approval`. Une variante au miroir rouge est refusée quel que soit son score ; une mirror-verte-mais-out-of-sample-rouge est refusée (§87) ; sans autorité, refusée. Une gate passée rend une **PROPOSITION** (`WritesTruth` toujours false) — jamais un gel (la porte est le `/goal` humain).

**L'orchestration n'émet que branches/reports/ideas — `RunMediumLoop(FixedMirror, []Variant) → ProjectEvolutionRun`.** Elle cull, place en niches, puis émet pour chaque élite survivante un branch (`/branches/evolution/...`), un report (`/reports/....json`) et une idée (`/ideas/proposed/...`) — **chaque chemin passé par `evolve.Confine`** (un chemin qui s'échapperait est dropé, jamais émis). Ordre des clés trié → run byte-replayable. `GateableBy` annexe la gate restante par niche (« autorité toujours requise »). L'invariant clé que pin le property test : **tout chemin émis est sous `can_write` — la boucle ne gouverne jamais** ; **aucun casseur de miroir n'est élite**.

**Le MCP `aidos-project-evolve`** (`back/mcp/project-evolve`, ADR 0009) expose `project_evolve_run`, `project_evolve_cull`, `project_evolve_niches`, `project_evolve_promote` — chacun **défère** au moteur pur. Read-only sur le Kernel (le mur) ; stdio ; pur, déterministe.

**Le twin TS `lib/project-evolve.ts`** reproduit `cull` / `niches` / `nicheKey` / `promote` pour l'écran — le Go est l'autorité. La route **action-capable** `/project-evolve` (`ProjectEvolvePanel.tsx`) porte des contrôles liés au twin pur : un toggle **« casser le miroir »** (v-broken, fitness 0.99 → bascule en tué, jamais élite), un toggle **« accorder l'autorité »**, et un bouton **« promouvoir »** par niche (sans autorité → refusé ; avec → proposé, `writesTruth=false`). Elle rend le miroir fixe, les niches Pareto, la liste des tuées et le verdict de promotion. Thème ADR 0010, bilingue fr/en ADR 0011 ; ajoutée à la nav `WorkbenchHeader`.

**Les miroirs.** `projectevolve_fixture_test.go` (5 tests — les trois done-criteria : une variante cassant le miroir est tuée et jamais élite malgré la fitness supérieure ; une élite verte n'est promouvable qu'avec autorité ; la sandbox n'écrit aucune vérité ; + out-of-sample rouge refusé même avec autorité ; + variante cross-projet refusée) ; `projectevolve_property_test.go` (rapid, 4 props : déterminisme ; aucune élite ne casse le miroir et toutes in-projet ; tout chemin émis ne gouverne jamais ; une élite par niche = max fitness in-projet vert). Côté front `lib/project-evolve.test.ts` (fast-check, 7 — done-criteria + invariants) + `tests/e2e/project-evolve.spec.ts` (Playwright, 3 — dont les done-criteria exécutés depuis l'écran). `go build ./...` + `go test ./archive/projectevolve` verts.

## Méta

**Pourquoi réutiliser S42 + S26 plutôt que réécrire ?** S42 a déjà rendu autoritaires la quarantaine (`Confine`, l'allow-list des trois zones), la gate à trois conditions et la forme « la promotion est une proposition, jamais un gel ». S26 a déjà rendu autoritaire MAP-Elites (« une élite verte par niche, fitness max, le miroir est le juge »). S108 n'a pas à réinventer ces invariants — c'est l'**accrétion additive** (§9). Il ajoute exactement ce qui manquait pour des **apps par projet** : l'**ancrage à un miroir fixe** (la boucle cherche une meilleure implémentation, pas une vérité nouvelle), le **cull** explicite (les casseurs sont retirés AVANT QD, pas seulement non-promus), et la **frontière projet** (E12 est multi-tenant ; une variante de A ne peut être promue dans B).

**Pourquoi le cull est-il séparé de la placement QD ?** Parce qu'il rend **visible** le done-criterion « une variante cassant le miroir est tuée ». `qd.Elites` exclut déjà les rouges, mais S108 doit **rapporter** quelles variantes ont été tuées (l'écran les affiche, l'e2e les vérifie). `Cull` est donc un geste de premier ordre — le miroir tue, et la mort est observable, jamais silencieuse.

**Pourquoi `SANDBOX_ESCAPE` pour la frontière cross-projet ?** Le `blockreason` central porte déjà `SANDBOX_ESCAPE` (S82, « un workspace par projet a tenté de lire/écrire hors de sa racine »). La promotion cross-projet est exactement cette violation au niveau version-DAG — on **réutilise** le code existant plutôt que d'en inventer un quatrième (la règle d'honnêteté : ne jamais coiner un code de blocage redondant).

## Méta-méta

**Le déterminisme, sur trois plans.** (1) La **toolchain qui code AIDOS** : le cull, la placement de niche, la gate de promotion sont des **fonctions pures** — pas un « agent qui évalue les variantes ». Un property test rapid + un fast-check pin « même entrée → même sortie ». (2) Le **runtime produit** : la boucle médiane d'un projet déployé tourne sur ces mêmes fonctions ; le juge est le **miroir**, jamais un LLM. (3) Le **codeur d'apps émises** : les variantes seraient générées par un générateur déterministe (self-play / mutation AlphaEvolve) derrière le seam injecté, jamais « un LLM qui improvise une implémentation et se note lui-même ».

**L'anti-Goodhart est structurel, pas une politesse.** Le score ne peut **pas** promouvoir une variante : la gate exige le **miroir vert** d'abord, et le cull retire les rouges **avant** que QD ne regarde la fitness. Il n'existe aucun chemin de code où un « bon score » contourne le miroir. C'est la traduction mécanique de §8 (« le juge est déterministe », « les poids sont déclarés, jamais appris ») : ici la fitness **ordonne dans une niche**, elle ne **décide** jamais de l'admission.

**La sandbox ne gouverne jamais — l'invariant est une propriété, pas une intention.** `RunMediumLoop` passe **chaque** chemin émis par `evolve.Confine` et un chemin qui s'échapperait est **dropé** ; le property test `EmittedWritesNeverGovern` le vérifie sur des entrées arbitraires. La promotion rend une **PROPOSITION** (`WritesTruth` toujours false). L'évolution est ainsi **prouvée** incapable d'écrire une vérité — c'est le mur (§2) rendu exécutable au niveau de la boucle d'apprentissage.
