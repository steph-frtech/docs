## Implémentation

S114 **compose** des moteurs déjà verts, il n'en reconstruit aucun :

- **S111 `costmeter` / S52 `agentrun`** — le `RunMeter` (BA11) qui porte la consommation réelle d'un run (`Tokens`, `CIMinutes`). S114 le réutilise verbatim comme substrat de métrage.
- **S73 `operation` async/outbox** — la garantie exactly-once-relative (at-least-once + dispatch idempotent ⇒ pas de doublon observable). S114 la **court à l'envers** : un webhook entrant, content-adressé, est l'inverse d'un effet sortant à l'outbox.
- **S61 / S53** — l'identité compte et le `project_id` qui keyent l'attribution.
- **`records.Hash`/`Canonicalize`** (S02) — le content-addressing réutilisé tel quel pour l'idempotence des webhooks.

Le nouveau package est `back/runtime/billing`. Son cœur :

- **`Plan` + `planQuotas`** — l'ensemble CLOS `free→pro→scale→enterprise` (l'ordre = le chemin d'upgrade, `NextPlan`), et la table de quotas DÉCLARÉE (§8 — au-dessus de la ligne, jamais apprise), strictement ascendante sur chaque axe (prouvé par fixture). Quatre axes : `MaxLLMTokens`, `MaxBuildLoopMinutes`, `MaxSandboxHours`, `MaxDeployedApps`.
- **`MeterUsage(account, runs)`** — le **fold de comptage** pur, total, monotone : il somme le `RunMeter` (S111) de chaque `MeteredRun` dont le compte correspond, attribué exactement par projet ; les heures-sandbox floor-divisent les secondes sommées. Même `(account, runs)` ⇒ même `Usage`. `MeterProject` filtre par `(account, project)` — les usages par projet somment à l'usage compte (prouvé property).
- **`CheckQuota(plan, usage)`** — dénie sur **tout** axe dépassé (OR par axe ; égal-à-la-limite = dans le quota, plafond inclusif) avec un `BlockReason{QUOTA_EXCEEDED}` dont le `how_to_fix` nomme les axes ET le `NextPlan`. Un plan inconnu dénie `UNKNOWN_PLAN`. `CanRunBuild` est la porte nommée que la boucle-build (S83) consulte. **Jamais d'échec silencieux** — un `how_to_fix` vide serait la prison §44.5, interdite.
- **`IngestWebhook(log, event)`** — content-adresse l'événement (`records.Hash(Canonicalize(webhookBody))`, byte-identique au jumeau TS) ; un webhook **rejoué** collisionne avec son ingest antérieur et est **supprimé** (S73 exactly-once-relative, run inbound) ; un événement mal formé est **refusé** (`ErrInvalidWebhook`), jamais silencieusement ignoré. `ApplyEvent(current, event)` est la transition de plan autoritative (checkout/subscription.updated → le plan ; canceled → free ; payment → inchangé).
- **`pact.go`** — `EmitContract` rend un contrat Pact-v3 (un ACK par kind entrant + une interaction DENY pour un event mal formé) ; `VerifyContract` lève l'endpoint billing en-process (`httptest`) et rejoue chaque interaction via le **même** `IngestWebhook` que le runtime. Vérifier ce provider vérifie le handler entrant, sans réseau. Le provider nommé est `stripe` (`ProviderName`, ADR 0049).

Tout est **pur, total, déterministe** : pas d'horloge, pas de rng, pas d'I/O, pas de LLM. Le package **n'écrit rien** — plans/usage/quotas/webhook-events sont des rows runtime/commerciales (un seam below-the-line), jamais un schéma `kernel`/`mirrors`/`fitness`.

## Méta

**Pourquoi un package séparé de `costmeter` (S111) ?** Parce que S111 répond à « ce coût build-time vaut-il sa valeur ? » (un verdict **advisory** pour l'architecte, sur une **cellule**), et S114 à « ce build peut-il tourner sous le plan du **client** ? » (un quota **blocking** pour le client, sur un **compte**). Les deux partagent le substrat de métrage — le `RunMeter` réel des AgentRun — et **rien d'autre**. Fusionner les deux confondrait deux publics et deux natures de verdict. La frontière est exactement la phrase de la roadmap : « couche économique customer-facing, **distincte** du HarnessCostBudget kernel ».

**Pourquoi le webhook entrant est une operation async S73 (run inbound) ?** Parce qu'un webhook **est** out-of-band par nature : le provider le pousse quand il veut, le retransmet en cas d'incertitude réseau. La seule façon honnête de le modéliser est l'idempotence par content-addressing — exactement la garantie outbox de S73, mais l'événement entre au lieu de sortir. On **réutilise** le même `records.Hash` que l'outbox sortant ; la 5e nature de trigger (le webhook entrant) projette les quatre de S73.

**Pourquoi le métrage est-il un comptage et jamais un LLM ?** C'est le mandat determinism-first (§6/§8) appliqué à la facturation : compter des tokens/minutes est une **pure fonction** (un fold sur un ledger), donc cela DOIT être du code, faisant autorité. Un agent qui « estime » l'usage serait un gap de déterminisme — et pire, une facturation non reproductible (anti-Goodhart). Le miroir de reproductibilité (même ledger ⇒ même usage) verrouille cette garantie.

## Méta-méta

S114 illustre la **frontière du mur appliquée à l'argent** : la couche commerciale touche des rows runtime, jamais le truth-store. Appliquer un changement de plan modifie une row commerciale (un seam), pas le kernel — l'agent reste sans GRANT sur la vérité. C'est la généralisation §2 : *toute* écriture autoritative passe la porte `idea → mirror → /goal`, et la facturation, qui n'est **pas** une vérité produit, n'a pas à la franchir — elle vit explicitement **sous la ligne**.

Et le `BlockReason{QUOTA_EXCEEDED}` est la preuve, côté économique, de l'anti-prison §44.5 : un blocage sans issue est un monstre. Un over-quota porte **toujours** son `NextPlan` (le chemin d'upgrade) ; le code refuse structurellement d'émettre un blocage à `how_to_fix` vide. La facturation, comme le mur, **explique toujours comment se débloquer** — la même loi qui gouverne un refus du kernel gouverne un refus de quota.
