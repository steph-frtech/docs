## Implémentation

### Le paquet — `interpretsvc` + `aidosinterpreter` (additif)

L'app émise est **multi-plateforme** depuis **une** seule spec — Backend (Hono/TS + le sidecar Go), Web (React), Mobile (Expo/React Native), Desktop (Electron) — chacune une **projection déterministe** de la même vérité (ADR 0040, addendum 2026-06-14). Cette page documente le **SIDECAR INTERPRÉTEUR Go runnable** : la **clé de voûte runtime** du serveur Hono émis. Le paquet est **strictement additif** (anti-overwrite §9 — aucun fichier existant n'est touché, aucun `gen/` n'est édité à la main) ; `operation.Interpret` est **réutilisé verbatim**, **rien n'est forké**.

Les fichiers (chemins absolus) :

- `/data/dev/aidos/back/runtime/interpretsvc/interpretsvc.go` — la **logique pure importable** : `Registry` (la coupe d'opérations, lecture seule) et `Interpret(reg, opName, input, auth, deps) → Outcome{Operation, Result, Events}`. **Réutilise `operation.Interpret` VERBATIM**, **aucune** règle réimplémentée.
- `/data/dev/aidos/back/runtime/interpretsvc/memdeps.go` — les **seams en mémoire** (`MemStore` + `MemDeps`) implémentant `operation.Deps` (`Validator`/`Authorizer`/`Reader`/`Mutator`) ; le **chemin logique-pure** du miroir.
- `/data/dev/aidos/back/runtime/interpretsvc/dbdeps.go` — le **pont pgx réel** sur le **schéma émis** (`DBDeps`) : read=`SELECT`, create=`INSERT … RETURNING *` (id déterministe **content-adressé** via `records.Hash`), clear=`DELETE` ; encode/décode JSON pour les colonnes text (`items`). **Mur §2 : écrit seulement les tables de l'app émise.**
- `/data/dev/aidos/back/runtime/interpretsvc/http.go` — le `Server` (`http.Handler`) : `GET /healthz`, `POST /interpret` `{operation, input, auth}` → `{result, events}` ; erreurs honnêtes `404`/`403`/`422`/`400`/`405`.
- `/data/dev/aidos/back/cmd/aidosinterpreter/main.go` — le service `main` : `PORT` (8080) ; `DATABASE_URL` absent → mode **démo seedé** (Cart), présent → `DBDeps` pgx.
- `/data/dev/aidos/back/cmd/aidosinterpreter/Dockerfile` — image multi-stage **distroless**.
- `/data/dev/aidos/back/runtime/interpretsvc/README.md` — architecture, signature HTTP pour le câblage Hono, OpenQuestions.

### La logique pure — `Registry` + `Interpret`

```go
// La coupe d'opérations, en lecture seule.
type Registry struct { /* … */ }
func NewRegistry(ops []operation.Operation) (*Registry, error) // prend TOUTE coupe

// Réutilise operation.Interpret VERBATIM — aucune règle réimplémentée.
func Interpret(reg *Registry, opName string, input map[string]any,
    auth AuthContext, deps operation.Deps) (Outcome, error)

type Outcome struct {
    Operation string
    Result    any
    Events    []operation.Event
}
```

`Interpret` ne **ré-implémente** aucune règle d'interprétation : il **réutilise** `operation.Interpret`, la **source** d'interprétation gouvernée. La `Registry` est la **coupe** d'opérations (ici, ancrée sur `createOrder`) — `NewRegistry` prend **toute** coupe.

### La signature HTTP — le port émis branché sur le sidecar

```text
POST /interpret   {operation, input, auth?}  →  {result, events}
GET  /healthz                                →  {status:"ok", operations:[…]}
```

C'est le contrat que le **serveur Hono émis** appelle : le port émis `OperationInterpreter = (operation, input) => Promise<unknown>` se branche directement sur `POST /interpret`. Le handler Hono **valide/route** (TS pur), **délègue** l'exécution au sidecar Go, **projette** le résultat. Les erreurs sont **honnêtes** : `404` (op inconnue), `403` (deny policy), `422` (règle métier), `400`/`405`.

### Les seams — `MemDeps` (logique-pure) et `DBDeps` (pont pgx réel)

```go
// memdeps.go — le chemin logique-pure du miroir
type MemDeps struct { store *MemStore }   // implémente operation.Deps

// dbdeps.go — le PONT pgx réel sur le SCHÉMA ÉMIS (mur §2)
type DBDeps struct { pool *pgxpool.Pool }
// read   → SELECT
// create → INSERT … RETURNING *   (id content-adressé via records.Hash)
// clear  → DELETE
```

Les deux implémentent `operation.Deps` (`Validator`/`Authorizer`/`Reader`/`Mutator`). `MemDeps` est le chemin **logique-pure** du miroir ; `DBDeps` est le **pont** réel : read=`SELECT`, create=`INSERT … RETURNING *` (id déterministe content-adressé), clear=`DELETE`, JSON encode/décode pour les colonnes text. **Le mur §2 :** `DBDeps` n'écrit **que** les tables de l'app émise — **jamais** `kernel`/`mirrors`/`fitness`.

### Le service `main`

`PORT` à 8080. Sans `DATABASE_URL`, le service boote en **mode démo seedé** (un `Cart`) sur `MemDeps` ; avec, il câble `DBDeps` sur le pool pgx. Le `Dockerfile` est un **multi-stage distroless**.

## Méta

- **Le miroir d'exécution d'opération est l'épreuve « le sidecar exécute une opération exactement comme le Kernel l'interprète », ∀ et par fixture.** Le miroir fixture épingle le **parcours** réel : `createOrder` crée un `Order` depuis le cart, vide le cart et émet `[OrderCreated, CartCleared]` (`interpretsvc_test.go`), un refus de policy ou une op inconnue donne un **échec typé sans `Order`**, et le pont pgx réel lit/insère/supprime sur un **Postgres réel** (`dbdeps_integration_test.go`, Testcontainers). Le miroir property (rapid) mesure le cœur déterministe : **même** input sur le **même** état → **même** effet — reproductible. Que le sidecar **réutilise** `operation.Interpret` plutôt que de **ré-implémenter** l'interprétation n'est pas une promesse — c'est une propriété **prouvée** : le serveur Go in-process de la slice §S46 (la divergence) et le sidecar appelé par Hono partagent la **même** logique d'interprétation, et leur **parité de comportement** est ce que les miroirs scellent.

- **Le pont State↔DB vit ENTIÈREMENT dans les seams — par design, pas un gap.** `operation.Interpret` ne rend **pas** de writes DB : il reste **pur** et passe ses effets **par** le seam `Mutator` (`deps.Mutate`). Le pont State↔DB vit **entièrement** dans les seams (`operation/deps.go`) — c'est le **contrat**, par **design** : le job du sidecar est exactement de **fournir** ces seams (`MemDeps`, `DBDeps`). Le « marche de plus » honnête : `OQ-SIDECAR-clear-where` — `operation.evalMutate` ne forwarde au seam `Mutator` que le `Data` du step ; la **cible** du verbe `clear` vit dans le `Where` (`{id:$.cart.id}`) que l'interpréteur **ne transmet pas** encore. Le seam dérive la cible **honnêtement** du State (slot `$.<entity>` lié par le read), **jamais** une règle réimplémentée ; un `Where` non dérivable est **refusé** (jamais de table wipe). Le vrai correctif (thread `m.Where` au `Mutator`) est un **changement Kernel**, hors de cette surface. Les autres OpenQuestions (`-validate`, `-policy`, `-expr`, `-registry`) sont **documentées, non truquées** : `Validator` = check minimal, `Authorizer` = verdict configurable (vrai = évaluateur Policy ∀), `sum()` pour `total` non câblé (même OQ que la slice §46), la `Registry` ancrant `createOrder` (le loader `kernel.operation` est le tooth suivant).

- **Déterminisme-first (§6/§8) : le sidecar est du code, jamais un LLM.** Aucun LLM n'entre dans le sidecar — ni pour interpréter une opération, ni pour décider un verdict, ni pour écrire en base. L'interprétation est `operation.Interpret`, la **source** ; le SQL est **byte-stable** (colonnes triées) ; l'`id` est **content-adressé** (`records.Hash`, même contenu → même id). Un sidecar qui ferait *deviner* à un agent ce qu'une opération produit serait un **trou de déterminisme** ; ici, le code interprète, l'agent ne s'assoit jamais dans la boucle runtime.

## Méta-méta

- **ADR 0040 multi-plateforme — une source, N plateformes.** L'app émise n'est **pas** une application : c'est **une** spec (au-dessus du mur) qui se **projette** vers N plateformes — Backend (Hono/TS + le sidecar Go), Web (React), Mobile (Expo/React Native, « expo go »), Desktop (Electron, « l'app en dur »). La plateforme est une **dimension** de l'émission, **jamais** une seconde source à maintenir, et chaque cible est une **projection déterministe byte-stable** (émetteurs purs, aucun LLM). Le **DDL Postgres** et le **datastore** (ADR 0006) sont **neutres à la plateforme** ; un **seul** modèle de types et un **seul** client typé (`hc`) irriguent Web, Mobile et Desktop — pas de double-typage. L'addendum (2026-06-14) **grave** ce que la Décision 1 (constructrice ≠ construite) impliquait sans le nommer.

- **Le sidecar réutilise `operation.Interpret` — le mur, une seule source d'interprétation.** C'est la frontière que le sidecar grave (§2). L'interprétation des opérations reste **en Go, gouvernable, non dupliquée** : le sidecar **réutilise** `operation.Interpret` **verbatim** et n'est **jamais** ré-émis en TypeScript (pas de duplication d'une logique gouvernée, une seule source d'interprétation autoritaire — la Décision 7 d'ADR 0040 réalisée). Il n'écrit **aucune** vérité : il ne touche **que** le schéma de l'app émise (below-the-line), **jamais** `kernel`/`mirrors`/`fitness`. Le serveur de boutique Go de la slice §S46 était une **divergence** de spec (l'app héritait de la stack de la constructrice) — **corrigée** vers **serveur Hono émis + callback vers le sidecar Go**. Le serveur Go subsiste comme **preuve d'exécution** de l'interpréteur, pas comme cible de déploiement.

- **Le déploiement réel passe par Pulumi — l'app émise, déployable pour de vrai.** Le bundle Hono/TS (front React + routing back) **+ le sidecar interpréteur Go** (la **seule** dépendance Go, partagée, gouvernée, versionnée avec le Kernel) se provisionne par **Pulumi** (ADR 0043, addendum 2026-06-13) : un **stack par projet×env** via `@pulumi/docker`, **réel**, prouvé par `demoshop-dev` en ligne (Traefik + Let's Encrypt), **portable** vers `future_cloud` (DP33) par simple changement de provider. L'app **mobile** (Expo) et **desktop** (Electron) s'empaquettent par leurs toolchains natives au-dessus du **même** serveur Hono + sidecar. La loi de complétude veille : le sidecar ne vit que parce qu'il porte sa preuve vivante (13 miroirs verts, dont 2 contre un Postgres réel) ; et la porte vers le kernel reste, comme toujours, idée → miroir → `/goal` → approbation humaine.
