## Implémentation

### Le câblage — un bouton qui *exécute* l'item 1 (additif §9)

L'**item 2** câble le bouton « Déployer » de `/v2/deploy` sur l'exécuteur **Pulumi par projet** de l'[item 1](/steps/internals/dp-pulumi-per-project). C'est **strictement additif** (anti-overwrite §9) : un seul **nouveau** fichier (la server action), trois fichiers **étendus** (la lib de projection, le client, la page i18n) ; aucun `gen/` édité à la main, le `BuilderClient` **non touché**. `git status` = **7 M + 1 ??** (le `??` est `actions.ts`), **uniquement** les changements voulus.

| Fichier | Rôle |
| --- | --- |
| `front/web/app/v2/deploy/actions.ts` (**NOUVEAU**) | la server action `deployStackPulumi` |
| `front/web/lib/v2/deploy.ts` (étendu) | la **projection PURE** `entityToSource` + `projectOf` + `DEFAULT_DEPLOY_ENV` |

### La server action — `deployStackPulumi`

```ts
"use server";
// front/web/app/v2/deploy/actions.ts
export async function deployStackPulumi(
  project: string,
  entitiesJSON: string,
): Promise<PulumiDeployResult>
```

Le geste capital. Il (1) écrit les entités de X (la projection pure `[]EntitySource`) dans un **fichier temp** (`mkdtemp` / `finally rm` — jamais de fuite), puis (2) exécute :

```text
go run ./cmd/aidospulumi up --project <X> --env dev --entities <tmp>
   cwd = back/ · GOTOOLCHAIN=auto · execFile (PAS un shell)
```

`project` **et** les arguments passent par `execFile` (`node:child_process`, `promisify`) — **jamais** par un shell (pas d'`exec`, pas d'interpolation). L'exécuteur imprime sur stdout le JSON `UpResult{ status, stack, dir, url, containers }`, parsé **tel quel**. La server action renvoie `{ status, url, containers, stack, detail }` ; une **panne** ⇒ `status: "error"` + un `detail` **actionnable** (la commande lancée, ou l'erreur tronquée). Le dépôt qui porte le module Go + `.deploy-pulumi/` est `AIDOS_REPO` (**overridable**, défaut `/data/dev/aidos`).

```ts
export interface PulumiContainer { readonly name: string; }
export interface PulumiDeployResult {
  readonly status: "up" | "error";
  readonly url: string | null;          // https://<project>-<env>.sagedesk.fr  | null
  readonly containers: readonly PulumiContainer[];
  readonly stack: string;               // <project>-<env>
  readonly detail: string;
}
```

### La projection pure — `entityToSource`

```ts
// front/web/lib/v2/deploy.ts
export function entityToSource(entity: Entity): EntitySourceJSON
export function projectOf(entity: Entity): string   // === subdomainOf — UN SEUL juge
export const DEFAULT_DEPLOY_ENV = "dev";
```

`entityToSource` projette chaque entité en `[]EntitySource` — un **mapping scalaire clos** S35→type Go (`text`, `numeric`, `int`, `bool`, `timestamptz` ; `ScalarType` importé), **ordre source préservé**, `id` **content-adressé**. C'est une **fonction pure** : la db déployée est seedée du schéma **réel** de X. `projectOf(entity)` **est** `subdomainOf` — un seul juge pour le sous-domaine **et** le nom de projet, d'où la cible `X-dev.sagedesk.fr` exacte. `DEFAULT_DEPLOY_ENV` fixe l'env à **`dev`** (le staging, en aval de la porte DP28).

## Méta

- **L'exécuteur réel est l'item 1 ; cet item 2 ne fait que le câbler.** `deployStackPulumi` exécute `aidospulumi up --project X --env dev --entities <tmp>` — l'exécuteur de l'item 1 (**Pulumi par projet**). Avec `--entities`, cet exécuteur **émet l'app de X** : `aidosappemit` (X) produit le **schéma** + les **entités** + le **seed**, montés par `MaterialiseApp` / `EmitPulumiStackApp`, avec `APP_NAME=X` brandé dans l'app. Puis `pulumi up` fait monter les conteneurs (`X-dev-db` Postgres seedée, `X-dev-app` l'app brandée) sur `traefik_default`, routés HTTPS. L'item 2 ne **ré-implémente** rien de ce moteur : il **matérialise** les entités de l'écran dans un temp et **passe** le chemin à l'exécuteur. Le câblage est **mince** ; la puissance est dans l'item 1.

- **L'e2e câble le bouton, pas le moteur — le vrai `pulumi up` est un geste gaté hors e2e.** Le miroir e2e prouve le **câblage** : que le bouton est **désarmé** pour un anonyme (la garde ADR 0052), qu'il **s'arme** une fois la garde franchie, et qu'il pinne la **bonne cible** (`X-dev.sagedesk.fr`) avec le bon `data-project`. Il **ne déclenche pas** un vrai `pulumi up` — exactement comme le real-deploy du builder n'est jamais cliqué en e2e : un déploiement réel est un **geste gaté side-effectant** (auth + rate-limit + DP28), pas un acte de test. Ce que l'e2e scelle, c'est l'**état et le gating** ; ce que le déploiement réel produit (URL + conteneurs **live**) est la **vérité de l'exécuteur**, observée en prod, jamais simulée.

- **Déterminisme-first (§6/§8) : la projection est du code, jamais un LLM.** `entityToSource` est une **fonction pure** déterministe — un **mapping scalaire clos** (S35→type Go), un **ordre source** préservé, un `id` **content-adressé** : **aucun** LLM ne « comprend » une entité pour fabriquer sa source. `projectOf=subdomainOf` est **un seul juge** déterministe (le nom de projet **est** le sous-domaine). Le `project` et les arguments passent par `execFile` (jamais un shell), et la sortie « live » est le JSON `UpResult` **parsé tel quel** — jamais devinée. Un câblage qui ferait *deviner* à un agent la cible, les types des champs ou l'URL serait un **trou de déterminisme** ; ici le code projette, l'agent ne s'assoit jamais dans la boucle.

## Méta-méta

- **Pulumi est le chemin d'exécution réel par projet ; le compose reste une projection dérivable, jamais exécutée.** C'est le basculement gravé par l'ADR 0043 amendé (et l'ADR 0052 amendé). L'**ancien** `docker compose` est **remplacé** comme moteur : `pulumi up` **monte** désormais les conteneurs, par projet. Le `docker-compose`-emit n'est pas détruit — il devient une **projection dérivable** de la **même** source (l'app émise / le `StackManifest`), **jamais exécutée**, une vue parmi d'autres (anti-overwrite §9, **une source → N cibles**). Le planificateur compose reste **visible** à l'écran en secondaire ; le primaire est le **vrai** Pulumi. Changer de moteur, ce n'est pas réécrire la source : c'est **brancher** le bon exécuteur.

- **Le mur (§2) : l'action n'écrit aucune vérité ; la porte humaine DP28 reste en amont du staging.** L'action de déploiement est un **geste gaté side-effectant** — gardé en amont par la garde ADR 0052 (auth + rate-limit), il **n'écrit AUCUNE vérité** (rien dans `kernel`/`mirrors`/`fitness` ; il matérialise une projection below-the-line et **lance** l'exécuteur). Les entités elles-mêmes sont une **projection PURE** de l'état de l'écran. Et la **porte de validation humaine DP28** reste **en amont** du staging : l'`env` est **`dev` par défaut** (`DEFAULT_DEPLOY_ENV`), jamais un push silencieux vers la prod. Le déploiement réel **n'érode** ni la source, ni le mur, ni la discipline humaine.

- **Le déploiement 1-clic par projet supersede les one-offs.** Jusqu'ici, déployer une app réelle passait par des **one-offs** (`alphashop`, `guestbook`) montés à la main. Désormais, chaque projet de `/v2` déploie **ses propres** entités en **un clic** — `deployStackPulumi(X)` lève la full-stack **réelle** de X (db seedée de **ses** entités, app brandée X, HTTPS) sans ligne de commande, sans gabarit. Le `BuilderClient` n'est **pas** touché (ses kernels candidats ne portent que `coordinate+version`, **aucun** champ d'entité typé que `--entities` exige ; son real-deploy reste sur le pipeline existant — §9). *Tout se fait par écran* : la capacité de déploiement réel, jusqu'ici headless, devient un **bouton** qui *exécute* — un clic restant un **geste gaté**, jamais une écriture de vérité. La porte vers le kernel reste, comme toujours, idée → mirror → `/goal` → approbation humaine.
