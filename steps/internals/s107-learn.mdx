## Implémentation

S107 ajoute la **fermeture de la boucle `/learn`** : `back/runtime/learn` (sous-système Runtime, KRD §53/§67/§42/§98, ROADMAP-app-builder §S107). Elle **compose** trois moteurs purs déjà autoritaires — sans en forker aucun — et ajoute strictement le maillon qui manquait : **le bump de hash quand un miroir approuvé s'attache à une opération/policy**, puis la **vague de rouge ciblée** que ce bump sème.

**Le bump est un delta d'adresse de contenu déterministe — `BumpHash(Target, ApprovedMirror) → (Bump, error)`**. La `Target` porte le corps canonique de l'AST de la cible (opération ou policy) **avant** la réflexion ; l'`ApprovedMirror` est l'**outcome** du `/goal` humain (un `MirrorID` content-adressé + le `Reflects` ref de la cible). `BumpHash` valide d'abord (kind dans `{operation, policy}`, mirror_id non vide, le miroir reflète **bien** la cible bumpée — sinon `ErrReflectMismatch`, pas d'attachement croisé), puis : `before = records.Hash(records.Canonicalize(specBody))` ; `after = records.Hash(records.Canonicalize(specBody + réflexion))`. La réflexion est **additive et append-only** — `reflectionAttached` fusionne le `MirrorID` dans un set `_reflections` trié, dédupliqué, donc l'adresse est ordre-indépendante. `Moved = after != before` ; **une re-réflexion d'un miroir déjà attaché ne bouge pas l'adresse**. `records.Hash`/`Canonicalize` sont **réutilisés** (jamais un hachage forké).

**La vague de rouge est ciblée — `TargetedWave(Bump, []redwave.Edge, links.Heads) → redwave.RedWave`**. Quand le bump a **bougé**, la tête de la cible a avancé à l'adresse `After`, donc tout lien épinglé sur l'ancienne tête résout périmé ; `TargetedWave` **réutilise `redwave.Impact`** (jamais un moteur de vague forké) en bumpant exactement l'id de la cible, ordonné mirror-first (§42/§98). Quand le bump n'a **pas** bougé (re-réflexion no-op), la vague est **vide** — pas de dent, pas de travail.

**Le mur est ré-asserré — `WallVerdict(reality.Incident) → *blockreason.BlockReason`**. Il **réutilise `reality.ToKernel`** : toujours non-nil, toujours `REALITY_CANNOT_DECLARE_TRUTH`. La boucle ne déclare jamais de vérité ; la seule continuation légale est celle déjà prise (incident → idée draft → /goal humain → miroir approuvé, un **input**).

**La boucle complète — `Close(incident, mirror, target, edges, heads) → (Outcome, error)`**. Elle compose `reality.Learn` (l'idée draft, provenance=incident), `BumpHash`, `TargetedWave` et `WallVerdict`. L'`Outcome` porte la `Candidate` (idée draft, `WroteKernel=false`), l'`ApprovedMirror`, le `Bump`, la `Wave` (la worklist) et le `Wall` (toujours un refus). `WroteKernel` est **toujours false** ; le schéma `fitness` n'est **jamais nommé** dans le package (vérifié par grep — aucun import) : c'est la garantie anti-circularité matérialisée.

**Le MCP `aidos-learn`** (`back/mcp/learn`, ADR 0009) expose `bump_hash`, `targeted_wave`, `close_loop`. Read-only sur le Kernel (le mur) ; stdio ; pur, déterministe.

**Le twin TS `lib/learn.ts`** reproduit `bumpHash` + `targetedWave` + `closeLoop` pour l'écran — le Go est l'autorité sur le fil (le twin hashe en FNV-1a sur le même JSON canonique key-sorted ; l'invariant prouvé — `before != after` ssi le corps change — tient pour tout hash déterministe). La route **action-capable** `/learn` (`LearnPanel.tsx` + Server Actions) porte UN contrôle « fermer la boucle » avec un toggle « re-réflexion » lié au twin pur ; elle rend la provenance=incident, l'adresse avant/après, le verdict `Moved`, la worklist ordonnée mirror-first, et le statut du mur. Thème ADR 0010, bilingue fr/en ADR 0011 ; ajoutée à la nav `WorkbenchHeader` (clé `learn`).

**Les miroirs.** `learn_fixture_test.go` (5 scénarios : le done-criterion incident → idée draft (provenance=incident, wrote-no-kernel) → miroir approuvé → bump de hash → red wave mirror-first ; le bump change vraiment l'adresse ; une re-réflexion no-op → aucun bump, vague vide ; le mur refuse toujours ; un miroir au mauvais reflet est refusé) + `learn_property_test.go` (rapid, 4 props : bump déterministe ; wave déterministe ; le mur tient pour tout incident ; la boucle n'écrit jamais le kernel). Côté front `lib/learn.test.ts` (fast-check, 4/4 — dont le done-criterion sur le démo) + `tests/e2e/learn.spec.ts` (Playwright, 4/4 — dont le done-criterion exécuté depuis l'écran). `go build ./...` + `go test` verts.

## Méta

**Pourquoi composer plutôt que coder à neuf ?** S107 n'invente aucun mécanisme : l'incident → idée et la porte `ToKernel` toujours refusée sont S43 (`reality`) ; la vague de rouge est S22 (`redwave.Impact`) ; le content-addressing est S01/S02 (`records`). S107 ajoute **un seul** maillon — le **bump de hash quand un miroir s'attache** — et **assemble**. C'est l'accrétion additive (§9) poussée jusqu'au bout : la valeur de S107 n'est pas du nouveau code, c'est la **fermeture mécanique** de la boucle entre des pièces déjà éprouvées.

**Pourquoi le bump est-il un hash et pas un drapeau ?** Parce que l'identité d'une cible **est** son adresse de contenu. Attacher un miroir n'« annote » pas la cible — ça **change ce qu'elle est** (elle a une dent de plus). En re-canonicalisant + re-hachant le corps, le bump est **structurel** : impossible d'avoir une nouvelle dent sans une nouvelle adresse, impossible d'avoir une nouvelle adresse sans qu'un lien périmé apparaisse. Le déterminisme (§6/§8) est ici doublement gardé : le bump (`records.Hash`) et la vague (`redwave.Impact`) sont des **fonctions pures** avec leur miroir de reproductibilité (même entrée → même sortie). Un agent qui « décide quoi rougir » serait un gap de déterminisme — exactement comme un agent qui ferait un diff au lieu d'un algorithme de diff.

**Le miroir approuvé est un input, jamais un output.** C'est subtil mais central : `Close` reçoit l'`ApprovedMirror`, il ne le **fabrique** pas. La rédaction du miroir (le Gherkin/property que l'humain écrit) reste au-dessus du mur, au `/goal`. S107 ne fait que **réagir** mécaniquement à une décision humaine déjà prise. C'est ce qui empêche la circularité : le code n'écrit jamais le test qu'il satisferait ensuite.

## Méta-méta

**S107 est le dernier mètre de la boucle externe (boucle ③).** S106 a transformé la prod en senseur (constater) ; S107 ferme la boucle jusqu'à la **nouvelle dent** — mais **toujours via l'humain**. La séquence complète : prod diverge (S106, déterministe) → idée draft (provenance=incident) → **vous grillez, vous écrivez le miroir, vous approuvez au /goal** (jugement, au-dessus du mur) → bump + red wave (S107, déterministe) → la boucle-build draine la worklist. AIDOS sépare net **constater** et **propager** (code) de **juger** (humain). S107 est la couche où il serait le plus tentant de laisser l'agent « apprendre » — et où il ne le fait pas.

**« Rien n'apprend sa propre fitness » rendu exécutable.** La property `Close_NeverWritesKernel` épingle l'invariant pour **toute** entrée tirée : `WroteKernel == false`, le mur tient. Le package ne nomme **jamais** le schéma `fitness`. C'est l'anti-Goodhart matérialisé : l'agent ne peut pas fabriquer la vérité qu'il satisfera ensuite, ni régler les poids/seuils qui le jugent. Le seul on-ramp de la réalité vers le Kernel reste `idée → miroir → /goal → approbation`, et S107 le respecte jusque dans sa signature de type (le miroir est un paramètre, pas un retour).

**La worklist est une conséquence calculée, pas une intention.** Le red wave n'est pas « ce que l'agent pense devoir refaire » — c'est **exactement** l'ensemble des liens périmés par le bump, ni plus ni moins (§42), ordonné par le rang de couche (mirror-first). Cette discipline — la worklist est **dérivée** de l'adresse, jamais déclarée — est la même qui fait que l'identité est calculée et non déclarée partout dans AIDOS. Quand les faits changent, le travail à faire n'est pas une opinion : c'est une fonction pure de l'état du graphe de liens. C'est ce qui rend la boucle externe **fiable** : la même approbation produit la même worklist, traçable et idempotente.
