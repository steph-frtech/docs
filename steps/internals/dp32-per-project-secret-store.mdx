## Implémentation

### Le paquet — `bootstrap` (étendu, additif)

DP32 **étend** `back/runtime/bootstrap/`, **strictement additif** (anti-overwrite §9 — aucun fichier existant n'est touché). Il **branche** le **secret store par projet** (S91) sur le provisioning : une app émise a besoin de **secrets** pour tourner (un credential DB, une clé API tierce, un secret OAuth, un certificat), et DP32 les **câble** au boot. L'`envemit` (DP04) et le `secretstore` (S91) sont **réutilisés intégralement** — **rien n'est forké**. C'est une tâche **backend-only** : aucun écran Workbench n'est ajouté.

Les trois fichiers DP32 (écrits mirror-first — l'impl **après** les deux miroirs) :

- `back/runtime/bootstrap/bootenv.go` — l'impl.
- `back/runtime/bootstrap/bootenv_fixture_test.go` — **9** fixtures (Godog-class, N2), écrit **RED-first**.
- `back/runtime/bootstrap/bootenv_property_test.go` — **5** lois (rapid, N1).

### L'ordre de merge gravé — un set fermé de couches

```go
type MergeLayer string

const (
	MergeLayerReferences MergeLayer = "references"
	MergeLayerStore      MergeLayer = "store"
	MergeLayerOverrides  MergeLayer = "overrides"
)

var bootMergeOrder = []MergeLayer{MergeLayerReferences, MergeLayerStore, MergeLayerOverrides}

func BootMergeOrder() []MergeLayer // une COPIE — jamais mutable, jamais dérivée d'une map
```

`MergeLayer` est un **set fermé** : `references` (le `.env.example` de DP04, la base de toutes les clés + leurs placeholders) → `store` (les valeurs S91, scopées projet) → `overrides` (les overrides de déploiement, qui gagnent en dernier). L'ordre est une **liste déclarée une fois** ; `BootMergeOrder()` en renvoie une **copie** (jamais dérivée d'une itération de map — déterminisme §6) que le Workbench peut **rendre**, pour que le merge soit lisible.

### `MergeBootEnv` — résoudre le `.env` concret, pure, totale, fail-closed

```go
func MergeBootEnv(envExample []byte, store *secretstore.SecretStore, projectID string, overrides map[string]string) (map[string]string, *blockreason.BlockReason)
```

Le cœur du paquet. Il résout le `.env` **concret** en **trois couches** :

- **Couche 1 (références).** Parse les lignes `KEY=VALUE` du `.env.example` (envemit réutilisé). Un val égal au `SecretPlaceholder` est une **référence de secret** à résoudre ; le `DeployTimePlaceholder` n'est **pas** un secret (résolu par un override ou laissé comme marqueur documenté).
- **Couche 2 (store).** Pour chaque référence **non overridée**, `secretstore.Get(projectID, ref)`, scopé. Les références **non résolubles** sont collectées (on ne bloque qu'**après** la couche overrides).
- **Couche 3 (overrides).** Appliqués sur **chaque** clé en dernier (`sort.Strings` → ordre stable, last-write-wins).

Deux gardes **fail-closed** :

- `project_id` vide ⇒ `MISSING_SECRET_AT_BOOT` (le scope d'isolation est obligatoire).
- La différence d'ensemble `requises − (store ∪ overrides)` non vide ⇒ `MISSING_SECRET_AT_BOOT`, les clés manquantes **triées** et **nommées** dans l'explication actionnable.

Sur un block : un env `nil` + le `BlockReason` (un boot bloqué ne résout **jamais** à moitié). La fonction est **pure, totale** : pas d'horloge, pas de RNG, pas de fuite d'ordre d'itération — même entrée → env byte-identique (le miroir de reproductibilité) ; et les **bytes émis ne sont jamais mutés** (la résolution est **en mémoire seule**).

### `RotateSecret` — tourner par S91, décision append-only par empreinte

```go
func RotateSecret(store *secretstore.SecretStore, projectID, name, newValue string) (RotationDecision, error)

type RotationDecision struct {
	ProjectID, Name, OldFingerprint, NewFingerprint string
}
```

`before := store.StoreFingerprint(projectID)` ; `store.Rotate(projectID, name, newValue)` (S91 **invalide** l'ancienne valeur — `Get` ne la renvoie **plus jamais**) ; `after := store.StoreFingerprint(projectID)`. La `RotationDecision` est **append-only** (§9), **content-adressée par empreinte** (`OldFingerprint`/`NewFingerprint`) — **jamais** la valeur en clair (une décision qui imprimerait le secret serait elle-même une fuite). Rotater un secret **absent** ⇒ `secretstore.ErrNotFound` : on **Set** ce qui n'existe pas, on **Rotate** ce qui existe.

### `SecretsStateFromStore` + `EmitBootstrapSequenceWithStore` — brancher DP12 sur le vrai store

```go
func SecretsStateFromStore(m stackmanifest.StackManifest, store *secretstore.SecretStore, projectID string) SecretsState
func EmitBootstrapSequenceWithStore(m stackmanifest.StackManifest, host HostState, store *secretstore.SecretStore, projectID string) (Sequence, *blockreason.BlockReason)
```

`SecretsStateFromStore` dérive le present-set du **vrai** store : il boucle `RequiredSecrets(m)` et teste `store.Has(projectID, key)`, scopé (la **présence** sans **lecture** de valeur — leak-free) ; la sortie est **triée** ; un store `nil` ou un `projectID` vide ⇒ present vide (fail-closed). `EmitBootstrapSequenceWithStore` branche **pleinement** DP12 : il dérive l'état du store réel puis **délègue** à `EmitBootstrapSequence` — la loi `MISSING_SECRET_AT_BOOT`, le set ordonné fermé, la résolution de port pure et le mur tiennent **inchangés**. Le mock DP12 (la liste de NOMS présents passée en donnée) est **remplacé** par le store réel ; `EmitBootstrapSequence(mock)` reste **intact**.

### Le scan no-leak — réutilisé verbatim

```go
func ScanBootEmission(emittedSource string, knownValues []string) []secretstore.Finding
func BootEmissionIsClean(emittedSource string, knownValues []string) bool
```

Réutilisent `secretstore.ScanEmission` / `IsClean` **verbatim** (anti-duplication §9) : le scan déterministe gitleaks-style sur le source émis, **jamais** un LLM. L'émission est propre **par construction** — le `.env.example` ne porte que des références, `MergeBootEnv` les résout en mémoire. Le scanner ne reçoit **jamais** la master key et **caviarde** tout match dans son propre rapport.

`MISSING_SECRET_AT_BOOT` (`blockreason.CodeMissingSecretAtBoot`), `secretstore.ErrNotFound` (rotater un absent).

## Méta

- **Le miroir Go est l'épreuve « les secrets sont scopés projet, le merge est gravé et déterministe, et rien ne fuit », ∀.** Le miroir fixture (Godog-class, N2) épingle le **parcours** en 9 sous-cas : le merge résout les références dans l'**ordre gravé** ; les overrides **gagnent en dernier** ; une référence requise manquante **bloque le boot** (`MISSING_SECRET_AT_BOOT`) ; la rotation **invalide** l'ancien secret **et** enregistre la **décision** ; rotater un absent est **refusé** ; le source émis est **références-only** (scan vert) ; le secret de A **ne fuit jamais** vers B ; le bootstrap consomme le **vrai** store ; et le bootstrap branché est **reproductible**. Le miroir property (rapid, N1) mesure le cœur déterministe en **5 lois**, dont deux **capitales** : `TestProp_DP32_MergeIsDeterministic` épingle que la **même entrée** produit le **même** `.env` concret (le merge ne dérive jamais), et `TestProp_DP32_NoSecretInEmittedSource` épingle qu'**aucune** valeur de secret ne survit dans le source émis (∀ secret). `TestProp_DP32_CrossProjectIsolation` pin l'isolation A↛B, `TestProp_DP32_MissingReferenceFailsClosed` le fail-closed, `TestProp_DP32_OverrideWinsLast` le last-write-wins. Que le store *isole* un secret plutôt que de le *fuiter*, qu'il *refuse* un boot incomplet plutôt que de *deviner* un credential, n'est pas une promesse — c'est une propriété prouvée.

- **Déterminisme-first (§6/§8) : l'ORDRE DE MERGE est du code (une liste gravée), jamais un LLM.** DP32 n'invite **aucun** LLM — ni pour décider *comment* fusionner, ni pour *résoudre* une référence, ni pour *scanner* une fuite. L'**ordre de merge** est une **liste déclarée** (`bootMergeOrder = [references, store, overrides]`), pas un `sed` interactif ni un agent qui « comprend » l'intention : `MergeBootEnv` est une fonction **pure, totale**, sans horloge, sans RNG, sans fuite d'ordre d'itération (`sort.Strings` partout où l'ordre compte). Le **scan** est du code gitleaks-style (`secretstore.ScanEmission`), pas un LLM qui « repère un secret ». Si bien que « même entrée ⇒ même `.env` » est une **seule comparaison** — la loi `TestProp_DP32_MergeIsDeterministic` le pin. Un secret store qui ferait *deviner* à un agent l'ordre de merge ou la présence d'un secret serait un **trou de déterminisme** (un `.env` qui change à chaque boot, une fuite ratée par un scanner statistique) — ici, le code résout, l'agent ne s'assoit jamais dans la boucle runtime.

- **Réutiliser plutôt que réinventer (ADR 0007, §9), sur S91 + DP04 + DP12 + S55 + S02.** DP32 n'invente **ni** un coffre, **ni** un scanner de secrets, **ni** un parseur d'`.env`, **ni** un émetteur de bootstrap. La **seule** logique propre à DP32 est l'**ordre de merge gravé** + la **décision de rotation append-only**. Pour le **coffre**, il **réutilise** S91 `secretstore` (Get/Has/Rotate/ScanEmission/EnvVar/StoreFingerprint — chiffrement au repos, scope, isolation). Pour le **`.env.example`**, il **réutilise** DP04 `envemit` (`.env.example`/`SecretPlaceholder`/`Keys`). Pour le **bootstrap**, il **réutilise** DP12 `EmitBootstrapSequence` **verbatim** (la projection pure, intacte). Pour l'**isolation à la persistance**, S55 (RLS) ; pour le **content-address**, S02 (`StoreFingerprint`). Il **ne forke** rien : pas un second coffre ni un second scanner à côté, mais **un branchement** qui assemble des moteurs déjà éprouvés.

## Méta-méta

- **Les secrets vivent dans l'appliance — JAMAIS dans la vérité, git ou le source émis (le mur, §2).** C'est la frontière que DP32 grave. Les secrets vivent dans le **store chiffré au repos**, scopé `project_id` (S91), et **nulle part ailleurs** : jamais dans le **truth-store** (`kernel`/`mirrors`/`fitness`), jamais **git**, jamais le **source émis** de l'app. Le `.env.example` émis (DP04) ne porte **que des références** (zéro valeur, une property ∀), le scan déterministe est **vert** sur l'émission, et la valeur concrète n'existe qu'en **mémoire** au boot et en **variable d'environnement** dans l'appliance. La `RotationDecision` est une **décision enregistrée** (append-only, par empreinte content-adressée — qui a tourné quoi, l'empreinte avant/après), **jamais** un `write-to-kernel` ; et c'est le **code** qui juge à chaque étape — `MergeBootEnv`, `RotateSecret`, `SecretsStateFromStore` sont des fonctions déterministes, jamais un LLM. L'agent n'a aucun GRANT pour graver une vérité, et la seule porte vers le kernel reste idée → mirror → `/goal` → approbation humaine.

- **Brancher, ce n'est pas dupliquer (anti-overwrite §9) — le mock DP12 cède la place au vrai store, sans rien casser.** La discipline est nette. DP12 avait posé le bootstrap avec un **mock** de la présence des secrets (la liste de NOMS passée en donnée) — la projection juste, mais nourrie par une donnée factice. DP32 **branche** le vrai store : `EmitBootstrapSequenceWithStore` dérive la présence du store **réel** (`SecretsStateFromStore`, via `Has` scopé) et **remplace** le mock — la loi `MISSING_SECRET_AT_BOOT`, le set ordonné fermé, la résolution de port pure et le mur tiennent **inchangés**. Et `EmitBootstrapSequence(mock)` reste **intact** (les 11 tests DP12 verts) : DP32 ne touche qu'à la **source** de la présence, pas à la projection. On **ajoute** un branchement, on **n'altère** rien de DP12 ni des fragments DP04–DP15.

- **Fail-closed, append-only, jamais la valeur — trois invariants méta-méta qui tiennent ensemble.** D'abord le **fail-closed** : un secret requis non résolu **refuse le boot** (`MISSING_SECRET_AT_BOOT`, clés nommées) — jamais un credential blanc ou deviné (honnêteté §8). Ensuite l'**append-only** : la `RotationDecision` s'**ajoute** à l'historique (par empreinte), elle ne détruit rien — tourner n'est pas écraser silencieusement (« an override is not an edit, it is a recorded decision », §8). Enfin le **jamais-la-valeur** : la rotation s'enregistre par **empreinte** (`StoreFingerprint`), le scan **caviarde** tout match, et la valeur ne sort **jamais** à l'écran — un futur écran `/secret-store` *poserait* et *tournerait* les secrets et *montrerait* l'**empreinte**, jamais la valeur. La loi de complétude veille : un branchement sans miroir serait un **monstre** — DP32 ne vit que parce qu'il porte sa preuve vivante (9 fixtures + 5 property, RED-first, l'impl écrite **après** les deux miroirs). Des OpenQuestions non-bloquants subsistent, par-design (forward dep) : la persistance Postgres du store + le log de rotations append-only (déférés au deploy track) et le miroir **pas encore** persisté au schéma Postgres `mirrors` — exception bootstrap S06, où le test **EST** la preuve red→green, back-fillée au pas qui bâtit le schéma.
