### L'événement `validation_humaine` — `HumanValidation` (append-only, content-adressé)

Le cœur de l'extension : la validation humaine devient un **événement enregistré**, append-only et content-adressé :

```go
type HumanValidation struct {
  ID        string      // content-adressé via records.Hash(Canonicalize(...))
  Env       Environment // l'env que l'humain a VU et validé (typiquement EnvPreview — le dev)
  PhaseHash string      // la phase exacte validée
  Validated bool        // le verdict humain : oui / non
  By        string      // l'auteur, défaut « human »
}

func RecordHumanValidation(in HumanValidationInput) HumanValidation
```

`RecordHumanValidation` est **PURE** : l'`ID` est dérivé de `records.Hash` + `Canonicalize` (content-adressé ⇒ reproductible), et `By` vaut `"human"` par défaut. C'est une **décision HITL RUNTIME** below-the-line — provenancée, append-only — qui n'appelle **jamais** `authority.Decide` (calque `ConnectorRuntimeApproval`, A2).

### `covers` — set-membership PURE, fail-closed (le code juge)

```go
// covers reports whether this validation is a fresh, VALIDATED authorisation for the EXACT phase.
func (v *HumanValidation) covers(phaseHash string) bool
```

Une **comparaison de set-membership pure**, **fail-closed** (calque `connectorenforce.ConnectorRuntimeApproval.covers`, A2) : `nil`-safe (pas de validation ⇒ `false`), exige `Validated == true` **et** `PhaseHash == phaseHash`. C'est le mur (§2) : le **code** *vérifie* que la décision humaine couvre la phase exacte — **jamais** un LLM. L'humain *décide* ; le code *juge la couverture*.

### `PromoteInput.DevValidation` + la porte dans `Promote()`

`PromoteInput` est **étendu** d'un seul champ :

```go
type PromoteInput struct {
  // ... (champs S98 inchangés)
  DevValidation *HumanValidation `json:"dev_validation,omitempty"` // gate EnvStaging uniquement
}
```

La porte est insérée dans `Promote()` **APRÈS** le stop-gate de stabilité (S98), **AVANT** la ré-émission :

```go
if in.Env == EnvStaging && !in.DevValidation.covers(phaseHash) {
  br := devNotHumanValidatedBlock(phaseHash, in.DevValidation)
  return Promotion{}, br
}
```

Promouvoir vers **staging** est **refusé** (`DEV_NOT_HUMAN_VALIDATED`) tant qu'une `HumanValidation{Env: preview, PhaseHash == phase promue, Validated: true}` n'est pas portée. Fail-closed : `nil` / autre-phase / `validated=false` ⇒ refuse. **Per-phase** : valider N-1 ne débloque pas N. Les sauts vers **prod** et **preview** ne sont **pas** gatés (seul `EnvStaging` l'est).

## Méta

- **Le miroir Go est l'épreuve `dev validé avant staging`, ∀ — et `rollback ⇒ re-projection de N-1`, ∀.** Le miroir property mesure le cœur déterministe : il épingle que la promotion vers staging est **refusée** `forall` tant que le dev n'est pas validé (`TestPromoteToStagingRequiresHumanValidation`), que la validation est **per-phase** (`TestStagingValidationIsPerPhase` — valider N-1 ne débloque pas N), que `validated=false` / `nil` / autre-phase **refusent** (`TestStagingValidationRefusedIsFailClosed`), et que `RecordHumanValidation` est **reproductible** (`TestHumanValidationReproducible` — même input → même `ID` content-adressé). Les fixtures (N2) épinglent les 4 sous-cas de la porte, le fait que prod/preview ne sont **pas** gatés, et que la validation est une décision append-only ; le Godog (N0) tient en mots-métier. Que le staging *exige le « oui » humain sur cette phase précise* n'est pas une promesse — c'est une propriété prouvée.

- **Déterminisme-first (§6/§8) : enregistrer une validation, juger sa couverture, gater une promotion sont des fonctions pures, donc du code.** DP28 n'invite **aucun** LLM : `RecordHumanValidation` est pure (content-adressée via `records.Hash` + `Canonicalize`), `covers` est une **comparaison de set-membership** pure et fail-closed, la porte dans `Promote()` est un `if` déterministe. L'humain *décide* (il valide ou refuse au runtime) ; le **code** *vérifie* que la décision couvre la phase exacte. Aucune horloge, aucun RNG, aucune I/O, aucun jugement flou. Même input ⇒ même verdict (le miroir de reproductibilité le pin).

- **Réutiliser plutôt que réinventer (ADR 0007), sur S98 + le calque A2.** DP28 n'invente **ni** un nouveau moteur de promotion, **ni** un nouveau mécanisme d'approbation : il **réutilise** la machinerie d'environnements de S98 (`Promote`, `Rollback`, `RollbackProducesReProjection`, le stop-gate de stabilité) et **calque** le motif `ConnectorRuntimeApproval.covers` (A2) pour la couverture par-phase fail-closed. Et il **étend** S98 — il ne le **duplique pas** : pas un second moteur de promotion à côté, mais **un champ** (`DevValidation`) + **un `if`** + **un événement** (`validation_humaine`), avec les sauts preview/prod et le rollback re-projection intacts.

## Méta-méta

- **La `validation_humaine` est une décision HITL RUNTIME below-the-line — provenancée, append-only, JAMAIS `authority.Decide`.** C'est la frontière fine du mur (§2). L'humain qui **valide** le dev *autorise un mouvement de runtime* (une promotion vers staging) — il ne **gouverne aucune vérité**. `RecordHumanValidation` n'écrit **rien** dans `kernel`, `mirrors` ou `fitness` ; elle n'appelle **jamais** `authority.Decide` (qui, lui, gouverne la truth). C'est exactement le calque de `ConnectorRuntimeApproval` (A2) : un humain approuve un **acte d'exécution**, pas une vérité. L'agent n'a aucun GRANT pour graver une vérité ; la seule porte vers le kernel reste idée → mirror → `/goal` → approbation humaine.

- **Le rollback re-projette, il n'est PAS un write-to-kernel — append-only §9, rien restauré stale.** Revenir en arrière (`Rollback`) ne *réécrit* aucune vérité : il fait le **checkout d'une phase antérieure** du DAG (hash N-1) qui **re-émet** l'app (DP05 + DP12), le vert antérieur intact. La vérité n'est jamais touchée ; seule la **projection servie** change. `RollbackProducesReProjection` le **prouve** : la sortie est la re-projection de la phase cible, **jamais** un artefact stale tiré d'un cache. C'est l'append-only (§9) gravé jusqu'au déploiement : rien n'est restauré d'un fige, tout est re-projeté depuis une vérité déjà établie.

- **DP28 ÉTEND S98, il ne le CASSE ni ne le DUPLIQUE pas — la porte gravée dans une comparaison pure.** La règle (§9) est nette : `Promote`/`Rollback`/`Provenance` (signatures), `ENV_PROMOTE_NOT_STABLE`, `ROLLBACK_NOT_EARLIER`, `RollbackProducesReProjection` restent **untouched** ; les sauts preview/prod restent non gatés ; le rollback re-projette toujours. La porte est **un seul `if`** dans `Promote()`, posée **après** le stop-gate, **avant** la ré-émission. Les 2 propriétés S98 patchées (`TestPromoteReproducible`, `TestPromoteLiveURLDeterministicAndHTTPS`) prouvent que le comportement S98 est **préservé** sous la nouvelle loi (elles rattachent simplement une dev validation quand l'env tiré est staging). La loi de complétude veille : un geste sans miroir serait un **monstre** — l'extension ne vit que parce qu'elle porte sa preuve vivante (fixture + property + Godog, RED-first, confirmé RED via « undefined: HumanValidation/RecordHumanValidation/DevValidation »). C'est l'anti-overwrite poussé jusqu'à la promotion : on **ajoute** une porte, on **n'altère** rien de l'existant.
