## Implémentation

### Le paquet — `backup` (nouveau, additif)

DP31 ajoute **UN seul paquet**, `back/runtime/backup/`, **strictement additif** (anti-overwrite §9 — aucun fichier existant n'est touché). Il grave la **stratégie de backup** des apps qu'AIDOS émet : la sauvegarde de leur **donnée** (volumes bind par-projet + dump du datastore) — **distincte** du rollback-par-phase de DP28 (le backup sauvegarde la **donnée**, le rollback re-projette le **code**). C'est une tâche **backend-only** : aucun écran Workbench n'est ajouté.

Les trois fichiers (écrits mirror-first — l'impl **après** les deux miroirs) :

- `back/runtime/backup/backup.go` — l'impl.
- `back/runtime/backup/backup_fixture_test.go` — **5** fixtures (Godog-class, N2), écrit **RED-first**.
- `back/runtime/backup/backup_property_test.go` — **4** lois (rapid, N1).

### Le set fermé des moteurs + les types

```go
type EngineKind string

const (
	EnginePostgres EngineKind = "postgres"
	EngineDoltgres EngineKind = "doltgres"
)

func IsKnownEngine(e EngineKind) bool
```

`EngineKind` est un **set fermé** — `postgres` (le datastore prod, DP15) ou `doltgres` (le store git-for-data non-prod). Un engine **hors-set** est refusé (`ErrUnknownEngine`). Les types de l'état et de l'artefact :

- `VolumeSnapshot{Name string; Bytes []byte}` — un volume bind sauvegardé ;
- `DatastoreDump{Engine EngineKind; Rows []byte}` — le dump du datastore ;
- `ProjectState{ProjectID string; Volumes []VolumeSnapshot; Datastore DatastoreDump}` — l'état d'un projet à un instant T ;
- `BackupArtifact{ProjectID, StorageKey, ContentAddress string; Volumes []VolumeSnapshot; Datastore DatastoreDump}` — l'artefact produit ;
- `RestoreDecision{ProjectID, ArtifactAddress, Address string}` — la décision de restauration, append-only ;
- `BackupResult{Fired bool; Artifact *BackupArtifact; Events []asyncfragments.DispatchEvent}` — le résultat d'une réalisation.

### `ScheduleBackup` — planifier l'échéance

```go
func ScheduleBackup(projectID, contentAddress string) (operation.Operation, operation.Async)
```

La planification : elle produit l'`Operation` et l'`Async` qui portent l'**échéance future**. Le payload de l'effet **est** l'adresse-contenu (`contentAddress`) — déterministe, ce qui rend le replay sûr (voir plus bas).

### `RealizeBackup` — réaliser à l'échéance, fail-closed secrets

```go
func RealizeBackup(state ProjectState, clock operation.Clock, outbox operation.Outbox, sink operation.Sink) (BackupResult, error)
```

Le cœur du paquet. La sauvegarde se réalise **à l'échéance** via le **calque DP16** `asyncfragments.RealizeScheduled` (`operation.Tick` / `Outbox` / `Sink` / `EffectID`, S73) — l'horloge est **injectée** (`clock operation.Clock`), **jamais** `time.Now`. Deux gardes :

- **Le replay ne double jamais l'événement.** L'`EffectID` **est** l'adresse-contenu de l'artefact : rejouer la planification donne le **même** `EffectID`, donc l'événement `backup-pris` n'est **pas** dispatché deux fois (exactly-once relatif).
- **Fail-closed sur les secrets.** Avant de minter le moindre artefact, `secretstore.ScanEmission` / `IsClean` (S91) balaye `SerializeForScan(artefact)`. Un secret en clair ⇒ `ErrSecretInClear` et **aucun** artefact n'est produit — la garde se ferme **avant** la frappe.

L'état pré-vol est vérifié : `ProjectID` vide ⇒ `ErrNoProject` ; engine hors-set ⇒ `ErrUnknownEngine`.

### `RestoreBackup` — round-trip sans perte, décision append-only

```go
func RestoreBackup(artifact BackupArtifact) (ProjectState, RestoreDecision, error)
```

La restauration fait un **round-trip sans perte** (`StateEqual` prouve l'égalité octet à octet de l'état restauré) et **enregistre** une `RestoreDecision` **content-adressée** — une décision **append-only** (§9), **jamais** un `write-to-kernel`. Restaurer, c'est *décider* de revenir à un état, pas effacer l'état courant en place.

### `AccessArtifact` — refus cross-project, défense en profondeur

```go
func AccessArtifact(artifact BackupArtifact, projectID string) error
```

L'accès est **refusé** cross-project : `nil` **ssi** le projet **possède** l'artefact, sinon `ErrCrossProject`. La défense est **en profondeur** — on vérifie le `ProjectID` de l'artefact **et** le préfixe-token de sa `StorageKey`. La `StorageKey` est **namespacée** par `datafragments.IsolationToken` (le token DP15 **réutilisé**) : `<token>/backups/<adresse>` — deux apps aux octets identiques produisent deux **clés distinctes**.

### Les helpers + les sentinelles

`StateEqual(a, b ProjectState) bool` (la comparaison du round-trip, via `records.Hash` + `Canonicalize`, S02) ; `SerializeForScan(artifact BackupArtifact) string` (le corps balayé par S91). Les sentinelles : `ErrNoProject`, `ErrUnknownEngine`, `ErrSecretInClear`, `ErrCrossProject`.

## Méta

- **Le miroir Go est l'épreuve « la sauvegarde est planifiée, déterministe, isolée et sans-secret », ∀.** Le miroir fixture (Godog-class, N2) épingle le **parcours** en 5 sous-cas : la sauvegarde **planifiée** se réalise bien **à l'échéance** (horloge injectée) et produit un artefact **restaurable** plus l'événement dispatché ; un **replay** ne double **pas** l'événement ; la restauration **round-trip sans perte** et enregistre sa `RestoreDecision` ; l'**isolation projet** tient (A inaccessible depuis B) ; et une **outbox non-writable** donne une **erreur typée**, jamais un panic. Le miroir property (rapid, N1) mesure le cœur déterministe en **4 lois**, dont deux **capitales** : `TestProperty_ReproducibleArtifact` épingle que le **même état** (à la même horloge) produit un artefact **byte-identique** (la sauvegarde ne dérive jamais), et `TestProperty_NoSecretInClearArtifact` + `TestProperty_BackupRefusesLeakingState` épinglent qu'**aucun secret en clair** ne survit — scan propre ∀ état sain, refus ∀ état qui fuit. `TestProperty_ProjectNamespacedKeys` pin que les clés sont **namespacées projet**. Que la sauvegarde *capture fidèlement* la donnée plutôt que de la *dériver*, qu'elle *refuse* un secret plutôt que de l'*exfiltrer*, n'est pas une promesse — c'est une propriété prouvée.

- **Déterminisme-first (§6/§8) : la PLANIFICATION est du code (une horloge injectée), jamais un LLM.** DP31 n'invite **aucun** LLM — ni pour décider *quand* sauvegarder, ni pour décider *quoi* sauvegarder. La planification se réalise via une **horloge injectée** (`operation.Clock`, le calque DP16 `asyncfragments.RealizeScheduled`) : on n'appelle **jamais** `time.Now`, l'instant est passé en paramètre, donc le test contrôle le temps et le résultat est reproductible. L'**adresse** de l'artefact content-adresse le corps canonique de l'état (`records.Hash` + `Canonicalize`, S02), si bien que « même état ⇒ même artefact » est **une seule comparaison d'octets** — la loi `TestProperty_ReproducibleArtifact` le pin. Et le payload de l'effet **est** cette adresse, ce qui rend l'exactly-once relatif gratuit : un replay calcule le même `EffectID` et ne double pas l'événement. Une stratégie de backup qui ferait *deviner* à un agent l'instant ou le contenu serait un **trou de déterminisme** (un artefact qui change à chaque exécution, un replay qui double) — ici, le code planifie, l'agent ne s'assoit jamais dans la boucle runtime.

- **Réutiliser plutôt que réinventer (ADR 0007), sur DP16 + S91 + DP15 + S02 + S72.** DP31 n'invente **ni** un planificateur, **ni** un scanner de secrets, **ni** un mécanisme d'isolation, **ni** un schéma d'adresse. Pour la **planification**, il **calque** DP16 `asyncfragments.RealizeScheduled` (`operation.Tick`/`Outbox`/`Sink`/`EffectID`, S73 — le moteur Windmill). Pour le **no-secret**, il **réutilise** S91 `secretstore.ScanEmission` / `IsClean` (fail-closed, avant toute frappe). Pour l'**isolation par-projet**, il **réutilise** `datafragments.IsolationToken` (le token DP15) qui namespace la `StorageKey`. Pour le **content-address** et le round-trip sans perte, il **réutilise** `records.Hash` + `Canonicalize` (S02). Et la **cible object-storage** réelle reste le **slot S72** (ADR-gated). Il **ne duplique** rien : pas un second planificateur ni un second scanner à côté, mais **une stratégie** qui assemble des moteurs déjà éprouvés.

## Méta-méta

- **La sauvegarde est below-the-line — la restauration n'écrit AUCUNE vérité (le mur, §2).** C'est la frontière que DP31 grave. La sauvegarde et la restauration sont **below-the-line** : elles n'écrivent **rien** dans `kernel`, `mirrors` ou `fitness`. La `RestoreDecision` est une **décision enregistrée** (append-only, content-adressée — qui a restauré quoi, vers quelle adresse), **jamais** un `write-to-kernel` ; restaurer, c'est *décider* de revenir à un état, pas réécrire une vérité. Et c'est le **code** qui juge à chaque étape — `RealizeBackup`, `RestoreBackup`, `AccessArtifact`, `StateEqual` sont des fonctions déterministes, jamais un LLM. L'agent n'a aucun GRANT pour graver une vérité, et la seule porte vers le kernel reste idée → mirror → `/goal` → approbation humaine.

- **Le backup, c'est la DONNÉE ; le rollback (DP28), c'est le CODE — deux retours en arrière qu'il ne faut jamais confondre.** La règle est nette. Le **rollback** de DP28 re-projette une **phase antérieure du DAG** (le checkout d'une vérité figée qui **re-émet l'app** — le **code**) ; il ne touche **pas** à la donnée que l'app a produite depuis. Le **backup** de DP31 sauvegarde et restaure la **donnée** (les volumes + le datastore, à un instant T) ; il ne touche **pas** au code de l'app. On peut rollbacker le code sans perdre la donnée, et restaurer la donnée sans changer le code. DP31 pose la seconde moitié, là où DP28 avait posé la première — additivement, sans rien casser (anti-overwrite §9 : on **ajoute** un paquet, on **n'altère** rien de DP28 ni des fragments DP15–18).

- **Append-only (§9) : sauvegarder et restaurer n'écrasent rien — et les secrets ne fuient jamais (S91).** Deux invariants méta-méta tiennent ensemble. D'abord l'**append-only** : la `RestoreDecision` s'**ajoute** à l'historique (content-adressée), elle ne détruit rien — restaurer n'est pas écraser. Ensuite le **fail-closed sur les secrets** : la garde S91 (`secretstore.ScanEmission` / `IsClean`) se ferme **avant** la frappe, si bien qu'**aucun** secret en clair ne peut jamais entrer dans un artefact (`ErrSecretInClear`) — une sauvegarde n'est jamais un canal d'exfiltration. La loi de complétude veille : une stratégie sans miroir serait un **monstre** — le backup ne vit que parce qu'il porte sa preuve vivante (5 fixtures + 4 property, RED-first, l'impl écrite **après** les deux miroirs). Des OpenQuestions non-bloquants subsistent, par-design (forward dep) : la persistance Postgres `restore_decisions`/`secrets` (déférée au deploy track S06/DP32) et le wire object-storage réel (slot S72, ADR-gated) ; et le miroir n'est **pas encore** persisté au schéma Postgres `mirrors` — exception bootstrap S06, où le test **EST** la preuve red→green, back-fillée au pas qui bâtit le schéma.
