## Implémentation

S95 ajoute le **planificateur de migration de donnée de l'app émise** : `back/runtime/datamigrate`. **Distinct** de la migration du truth-store (`back/migrations`, le Postgres propre de l'OS) — ici on migre les données d'une **app déployée qui tourne avec de VRAIES lignes**, quand son schéma d'entité change de façon **cassante**. Trois cas durs (S95 done-criteria) : **rename-avec-backfill**, **split d'entité**, **cardinalité 1-N→N-N**.

**Le planificateur (pur, total, content-adressé).**

- `Build(c Change) → (Plan, *BlockReason)` : `validate` (un projet, un `ChangeKind` connu — le set fermé `{rename, split, cardinality}` —, le corps assorti complet et typé dans le set scalaire fermé) → **la GATE** (le backfill déclaré) → `stage` (les trois `Step` forward-only) → `contentAddress` (S02). Même `Change` → `Plan` byte-identique (même `ID`, mêmes steps, même SQL de backfill).
- **La GATE `hasValidBackfill`** **réutilise `db.RequireMigration`** (S37/§44.3) : elle lui passe un descripteur à impact historique (`AppliesExistingRecords`) pour valider la déclaration avec **exactement les mêmes sets fermés** que le chemin truth-store, jamais une règle forkée. Une stratégie inconnue → le code §44.3 `UNKNOWN_MIGRATION_STRATEGY` verbatim ; un backfill absent/insuffisant → la GATE refuse, et S95 re-cadre le refus en **`BREAKING_MIGRATION_NO_BACKFILL`** (le code de l'app déployée).
- `stage` produit les trois `Step` `{Stage, SQL, Note}` — **expand** (DDL additif, NULLable), **backfill** (le **déplacement de données**, la nouveauté sur la migration truth-store : `UPDATE … SET new = old` pour le rename, `INSERT INTO new SELECT … FROM source` pour le split, `INSERT INTO join SELECT id, fk FROM source` pour la cardinalité), **contract** (le `DROP` destructif, un pas forward **séparé** après le backfill).
- `preservesAllData(steps)` → la **garantie no-loss CALCULÉE** : un plan préserve tout ssi chaque `contract` est **précédé** d'un `backfill`. Une vérification pure sur les steps — le **code** juge le no-loss, jamais un agent.

**Le nouveau `BlockReason`.** `blockreason.CodeBreakingMigrationNoBackfill = "BREAKING_MIGRATION_NO_BACKFILL"` — extension additive de l'enum close (change_type: refine, jamais une suppression), avec sa rangée canonique dans la registry (severity `blocking`, explication FR §44.3/§9, `how_to_fix` non vide : declare_the_backfill / use_expand_contract / prove_no_data_loss) et son entrée dans `codeOrder`. La property mirror de `blockreason` (chaque code a un `how_to_fix` non vide) couvre le nouveau code.

**Le déterminisme.** `Build` est pur, total — pas d'horloge, pas de RNG, pas de fuite d'ordre de map, pas de chemin absolu ; le SQL est en texte **driver-neutre** (clé : un client mince applique le plan, aucun pilote baké). Le `knownScalar` **réutilise** l'émetteur `db.EmitMigration` (sonde une `EntitySource` minimale) pour le set de types — **une seule source de vérité**, pas de map forkée. `ID` = `records.Hash(records.Canonicalize(body))`, S02 réutilisé.

**Le mur + l'honnêteté.** `datamigrate` ne lit que le changement (AST déjà épinglé, sous la ligne) et la `DataTruthScope` déclarée ; il **planifie**. Il n'écrit **rien** dans le noyau/mirrors/fitness. Un changement breaking sans backfill, un changement malformé, une stratégie inconnue → un `BlockReason` typé, jamais un panic, jamais une colonne inventée, jamais un `DROP` silencieux.

**Le MCP `aidos-datamigrate`** (`back/mcp/datamigrate`, ADR 0009) expose `plan` · `kinds` · `gate` — purs, n'écrivent rien. **Le twin TS** `front/web/lib/datamigrate.ts` reflète le planificateur (même GATE, mêmes trois steps, même `preservesAllData`) et alimente la route **action-capable** `/data-migrate` : choisir le type breaking, remplir le corps, basculer le backfill déclaré, **planifier** — l'écran rend les steps expand→backfill→contract, le badge no-loss calculé, et le refus honnête sans backfill.

**Les miroirs.** Godog (`datamigrate.feature` + `datamigrate_bdd_test.go`, 5 scénarios) : rename-avec-backfill préserve toute donnée, split sans perte, 1-N→N-N sans perte, breaking-sans-backfill refusé, émission reproductible. rapid (`datamigrate_property_test.go`, 4 propriétés) : reproductibilité (même change → plan identique), no-loss (chaque plan accepté met backfill avant contract), la GATE (breaking-sans-backfill **toujours** refusé `BREAKING_MIGRATION_NO_BACKFILL`), sensibilité du content-address (changes distincts → ids distincts). Fixture (`datamigrate_fixture_test.go`, 7 cas) : les trois lifecycles expand→backfill→contract + les quatre workflows de refus (breaking-sans-backfill, stratégie inconnue, malformé, pas de projet). fast-check (`datamigrate.test.ts`, 6/6) côté twin ; Playwright (`data-migrate.spec.ts`, 5/5) côté écran, dont le refus sans backfill et la reproductibilité du plan id.

**OpenQuestion OQ-S95-apply** (forward-dependency, exception bootstrap §6). S95 **planifie** la migration (le SQL + l'adresse de contenu) ; son **exécution** sur le vrai datastore déployé (le `pulumi up` + l'apply Atlas, DP26) est la dent **S96** (le pipeline de déploiement, gaté par S95). Le plan est driver-neutre exprès pour qu'un client mince l'applique. La preuve Testcontainers « no data loss sur un Postgres réel ensemencé » que la skill `migrate` décrit est, ici, **portée par la garantie calculée `preservesAllData` + les miroirs** ; l'apply réel arrive avec S96. OpenQuestion documentée, pas un résidu rouge.

## Méta

S95 est la dent qui **gate S96** (le déploiement qui migre). Sa décision structurante est de **séparer le PLAN de l'APPLY** : `datamigrate` est une **fonction pure** qui émet un plan content-adressé et driver-neutre, et c'est S96 qui l'exécute via le programme d'infra émis (deploy = ré-émission). Cela maintient le déterminisme-first jusque dans la migration de données : le **quoi** (les steps, le no-loss) est calculé et reproductible ; le **comment** (l'apply contre un vrai datastore) est un effet, isolé en aval.

La **réutilisation de `db.RequireMigration`** est délibérée : la GATE §44.3 (les sets fermés `applies_to`/`strategy`, l'exigence `preserve_old_truth`) est **un seul code**, partagé entre la migration truth-store (S37) et la migration de l'app déployée (S95). S95 n'**ajoute** que ce que le truth-store n'avait pas — le **déplacement de données** (le backfill SQL), parce que l'OS n'a pas de « vraies lignes d'une app utilisateur ». Le nouveau `BlockReason` est l'expression, au plan de l'app déployée, de l'invariant §44.3 « changer la vérité du code ne change pas la vérité des données déjà produites ». Le `preservesAllData` calculé est l'application du §8 (« le juge est déterministe ») au no-loss : ce n'est pas une promesse, c'est une propriété structurelle vérifiée (contract précédé de backfill).

## Méta-méta

S95 illustre le **déterminisme-first** sur le plan de la migration de données : tout ce qui *peut* être une fonction pure l'**est** — la détection du caractère breaking (un diff structurel × le scope), la mise en scène des steps (une projection du changement), le SQL de backfill (une dérivation des noms épinglés), le verdict no-loss (une comparaison de l'ordre des stages), l'adresse de contenu (un hash). Aucun LLM n'entre — ni dans la planification, ni dans le jugement « cassant ou pas ». Un agent qui « jugerait » si une migration est sûre serait une **brèche de déterminisme** ; ici c'est du code, autoritaire.

Et S95 respecte le **mur** sans exception : il lit un changement et un scope (sous la ligne) et planifie une migration ; il n'écrit jamais une vérité, n'invente jamais une colonne ni une règle de recopie, ne supprime jamais avant d'avoir recopié. Le `BlockReason` `BREAKING_MIGRATION_NO_BACKFILL` est la forme honnête du refus : **avant** tout `DROP`, avec un chemin de réparation actionnable. La porte vers le noyau reste `idée → miroir → /goal → approbation humaine` ; S95 n'en franchit aucune — il rend simplement **calculable** la sûreté d'une évolution de schéma sur une app qui tourne déjà.
