## En une phrase

BA27 câble le compteur vivant + l'arrêt-sur-budget dans la boucle (`back/runtime/agentloop`) et **nourrit le coût mesuré du run terminé à `economics.Evaluate`** (S51/S29) — un trou que personne ne remplissait jusqu'ici. Le check de budget tourne **AVANT chaque tour** (halt pré-call, gap G3) : un tour qui dépasserait le plafond est refusé avant de démarrer, et le compteur ne franchit **jamais** le plafond.

## Implémentation

Le code vit dans `back/runtime/agentloop/drive.go` (la boucle) et `back/runtime/agentloop/economics.go` (le pont vers l'économie) ; le jumeau TS dans `front/web/lib/agentrun.ts` ; le panneau dans `front/web/components/AgentsPanel.tsx` (sous-section `economics-loop`) ; la capacité exposée par `back/mcp/agentloop`.

- **`DriveWithEconomics(in) → (AgentRun, RunMeter, error)`** — la boucle BA27. Identique à `Drive` (BA15) mais elle **retourne aussi le `RunMeter` final** : le coût CONSOMMÉ que l'appelant nourrit à `economics.Evaluate`. `Drive` délègue désormais à elle et jette le meter (rétro-compat). Pure : même entrée ⇒ même `(run, meter)`.
- **Le halt PRÉ-CALL (gap G3).** À chaque tour, le coût déclaré est **PROJETÉ** sur le meter sans le committer (`projected := meter.Tally(turn.Cost)`), puis `CheckBudget(projected, …)` tranche. Si la projection dépasse, le tour est **refusé avant de démarrer** : on enregistre l'action de breach (`Autorisee:false`, BlockReason `AGENT_BUDGET_EXCEEDED`), on met `Result:abandoned`, on `break` — le coût n'entre jamais dans le meter committé (`meter = projected` n'a lieu QUE si la projection est dans le budget). Le compteur reste donc **au/sous le plafond**.
- **Le `min()` des caps est autoritaire (BA11).** `agentimpl.CheckBudget` réutilise `EffectiveTokensCap(h, b) = min(goal.Budgets.Tokens (S29), HarnessCostBudget.MaxLLMTokensPerGoal (S51))` — le plus serré gagne, fail-closed. La boucle ne réinvente aucune arithmétique : elle appelle la même porte BA11.
- **`MeasuredCostOf(meter) → economics.MeasuredCost`** (`economics.go`) — projette les axes du run vers la forme S51 : `Tokens → LLMTokens`, `CIMinutes → CIMinutes`. `MutationRuntime` et `HumanReviewMinutes` restent à 0 (un run d'agent ne lance ni la suite de mutation S40 ni des minutes de revue humaine — fabriquer ces axes serait un monstre). Les axes `Turns`/`WallClock` du meter sont gouvernés par la *gate* de budget BA11, pas par l'*économie* §66.3 — délibérément non mappés. Pure, totale.
- **`EvaluateRun(meter, budget, vc) → economics.EconomicsDecision`** — le pont : mappe le meter via `MeasuredCostOf` et **défère** à `economics.Evaluate` (le verdict §66.3 AUTORITATIF sur le `HarnessCostBudget` DÉCLARÉ). N'ajoute aucun jugement propre (determinism-first : l'évaluateur économique fait foi). N'écrit rien.
- **`FinalMeter`** est désormais un mince wrapper sur `DriveWithEconomics` — il n'y a **qu'un seul** meter (celui de la boucle), jamais un second replay qui pourrait dériver de l'autoritaire.
- **La capacité MCP** (`back/mcp/agentloop/main.go`) — le handler `drive` appelle `DriveWithEconomics` et expose `Meter` + `Economics` (le verdict §66.3) dans son `driveOutput`, en plus du run. Tout op backend = un outil MCP (ADR 0009) ; lecture seule, n'écrit aucune vérité.
- **Le jumeau TS** — `driveWithEconomics(in) → { run, meter }` (le `drive` public délègue), `measuredCostOf(m)` et `evaluateRun(m, b, vc)` (qui défère à `economics.evaluate`). Le halt pré-call est répliqué à l'identique (projeter, vérifier, committer seulement si dans le budget).
- **Le panneau action-capable** (`economics-loop`) — deux radios de plafond (serré / large) + bouton **Lancer la boucle** (`economics-drive`). Serré : le plafond force le halt pré-call (meter tenu à 10, run abandonné) ; large : le run va au bout (meter 20, vert). L'écran rend le résultat (`data-result`), le compteur (`data-tokens`, tag « cap tenu / franchi »), le coût mesuré, et le verdict économique (`data-verdict`). Thémé (ADR 0010, tokens) + bilingue FR/EN (ADR 0011, next-intl).
- **Les miroirs** :
  - *Fixture halt* (`back/runtime/agentloop/economics_loop_fixture_test.go`, N2) — (1) un tour de breach **ne démarre jamais** : run abandonné, meter tenu au plafond (10, pas 20), action de breach `AGENT_BUDGET_EXCEEDED` ; (2) un run dans le budget se ferme vert, meter = somme des tours ; (3) le coût mesuré atteint `economics.Evaluate` → `within_budget` sous un cap large, `over_budget_flagged` sous un cap cellule plus serré ; (4) `EvaluateRun` concorde avec `economics.Evaluate ∘ MeasuredCostOf`.
  - *Property* (`back/runtime/agentloop/economics_loop_property_test.go`, N1, rapid) — pour tout script arbitraire : (a) le meter **ne franchit JAMAIS** le cap effectif (`EffectiveTokensCap`) — le halt pré-call tient ; (b) abandonné ⇒ meter ≤ cap ∧ au moins l'action de breach enregistrée ; (c) **reproductible** (même entrée ⇒ même `(run, meter)`, deux fois) ; (d) `MeasuredCostOf` déterministe + mappe `Tokens → LLMTokens`.
  - *Reproductibilité fast-check* (`front/web/lib/agentloop-economics.test.ts`, N1) — halt pré-call (abandonné, meter 10) ; run dans le budget (vert, meter 20) ; `measuredCostOf` mappe les axes ; `evaluateRun` within/over ; le meter ne franchit jamais le cap ; reproductible ; `measuredCostOf` déterministe — 8 tests verts.

## Méta

**Pourquoi PRÉ-CALL et pas après le tally ?** La version BA15 tallait puis vérifiait : le meter franchissait le plafond d'un tour, puis on coupait. C'est « anti-runaway *constaté* », pas *empêché*. Le roadmap est explicite (gap G3 : « refuser de DÉMARRER un tour qui dépasserait »). BA27 projette le coût **avant** de committer : le tour de trop ne s'exécute pas et son coût n'entre jamais. La propriété « le meter ne franchit jamais le cap » devient un invariant *prouvé* sur tout script, pas un best-effort. Pour un agent qui code en streaming, la même discipline impose un hard-stop mi-token au franchissement (le `Provider`, BA17) — ici la boucle pure le modélise au grain-tour.

**Pourquoi réutiliser `economics.Evaluate` au lieu d'un verdict local ?** Parce que le verdict §66.3 est DÉCLARÉ et AUTORITATIF (les caps vivent dans la zone `fitness`, lecture seule). `EvaluateRun` n'est qu'un *pont* : il mappe le meter dans la forme d'entrée et défère. Lui faire trancher serait dupliquer une règle déclarée — une dérive de déterminisme. L'agent ne décide jamais « suis-je dans le budget ? » par inférence ; il appelle la fonction qui le calcule.

**Pourquoi ne mapper que `LLMTokens` + `CIMinutes` ?** Parce que `HarnessCostBudget` (S51) ne budgète que ces axes côté économie. `Turns`/`WallClock` sont gouvernés par la *gate* BA11 (anti-emballement), pas par l'*économie*. Inventer un axe `mutation_runtime` ou `human_review` pour un run d'agent serait fabriquer un coût qu'il ne produit pas — un monstre (la règle d'honnêteté). On laisse ces axes à 0.

**Pourquoi `DriveWithEconomics` retourne le meter plutôt qu'un second `FinalMeter` ?** Parce que deux chemins qui re-calculent le coût peuvent diverger. BA27 collapse `FinalMeter` en un wrapper : il n'existe **qu'un** meter, celui que la boucle a réellement tallé. Le panneau et l'économie lisent la même source autoritaire.

## Méta-méta

BA27 boucle le câblage du budget sur les trois invariants AIDOS.

- **Le mur (NIVEAU 3).** Le run reste **sous la ligne** : `DriveWithEconomics` n'écrit aucune vérité, le snapshot économique qu'elle alimente est un diagnostic runtime, et `economics.Evaluate` est lecture seule sur le `HarnessCostBudget` DÉCLARÉ (l'agent est SELECT-only sur `fitness`). Relever un cap est un /goal contre la fitness déclarée, jamais une édition ici. La gate de budget consultée AVANT exécution est l'intercepteur sur le chemin — le tour de trop ne franchit jamais le mur économique.
- **Determinism-first.** Tout fait foi en code pur : la projection (`Tally`), le `min()` des caps (`CheckBudget`/`EffectiveTokensCap`), le mapping (`MeasuredCostOf`), le verdict (`economics.Evaluate`). Aucun LLM ; aucune horloge (les timestamps sont SUPPLIED) ; aucun RNG. Les miroirs de reproductibilité (rapid + fast-check) épinglent : même entrée ⇒ même `(run, meter, verdict)`. Un agent qui déciderait « suis-je dans le budget ? » par inférence serait une faille de déterminisme qui bloquerait le step.
- **Anti-Goodhart.** Le `Result` n'est jamais auto-déclaré par le mock : `abandoned` est COMPUTÉ par le franchissement du cap (déclaré), `green` par `goal.IsClosed`. Le compteur est monotone et ne peut pas être truqué (les deltas sont clampés ≥ 0). Le verdict économique compare un coût MESURÉ à un budget DÉCLARÉ au-dessus de la ligne — ni l'un ni l'autre n'est gonflable par l'agent. La dépense reste une trace honnête qui alimente la décision « ça vaut-il son coût ? », jamais une vérité que l'agent s'attribue.
