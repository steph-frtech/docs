## En une phrase

BA24 rend opérante l'**OrchestrationPolicy** sur `CoucheAgent` (`back/kernel/agentlayer/orchestration.go`) et un `Validate` **conscient du kind** : une couche `orchestration` exige une policy *et* une équipe non vide ; un agent n'en porte aucune. La policy borne `MaxConcurrency` au knob déclaré (jamais un cap fantôme, gap F1) ; un run **épingle** sa `@version` (immutabilité par-run, gap F3) ; et `ResolveConflict` arbitre un conflit même-cible par une règle **totale, déterministe, symétrique, zéro-lost-update** (mirror-first puis content-hash, gap F2). Tout est pur ; rien n'écrit la vérité (la policy se *propose* via idée→miroir→/goal).

## Implémentation

Le modèle vit dans `back/kernel/agentlayer/orchestration.go` ; les jumeaux TS dans `front/web/lib/scheduler.ts` ; le panneau dans `front/web/components/SchedulerSection.tsx` (sous-section `scheduler-orchestration`).

- **Les types fermés** — `FanMode` (`sequential | parallel | pipeline`) et `SameFileConflictPolicy` (un seul membre : `serialise_then_merge` — la *seule* politique zéro-lost-update ; un coin-flip n'est pas dans l'ensemble). `OrchestrationPolicy` porte `ClaimArbitrage`, `FanOut`, `FanIn`, `ConflitMemeFichier`, `MaxConcurrency`, `CapsParRole []RoleCap`. `CoucheAgent` gagne deux champs `omitempty` : `Equipe []string` (les @versions des membres) et `Orchestration *OrchestrationPolicy`.
- **`validatePolicy(p, specMaxConcurrency)`** — guard PUR, TOTAL, fail-closed : enum inconnu, cap négatif, ou **cap fantôme** (policy `MaxConcurrency > spec`, sauf si le knob spec vaut 0 = « non borné par la spec ») ⇒ invalide (gap F1).
- **`Validate` kind-aware** — pour `LayerKindOrchestration` : `Orchestration != nil` (sinon `ErrOrchestrationNeedsPolicy`), `len(Equipe) > 0` (sinon `ErrOrchestrationNeedsTeam`), puis `validatePolicy(...)`. Pour tout autre kind : `Orchestration == nil` ET `len(Equipe) == 0` (sinon `ErrNonOrchestrationCarriesPolicy` / `ErrNonOrchestrationCarriesTeam`). Le reste du `Validate` S52/BA01 est inchangé (le mur, les knobs).
- **Immutabilité par-run (gap F3)** — `PolicyVersion(p)` = `records.Hash(canonicalPolicyBody(p))` : ordre de champs FIXE, séparateur `\x1f` (pas de collision par concaténation), donc même policy ⇒ même version, tout changement ⇒ version différente. `PinForRun(runID, version)` gèle la version (refuse une version vide) ; il n'existe **aucun setter** qui mute un pin. `MutationIsForbidden(pin, liveVersion)` = `pin.PolicyVersion != liveVersion` — vrai = édition mid-run détectée, à rejeter (nouvelle proposition obligatoire).
- **`ResolveConflict(a, b ClaimContender)` (gap F2)** — l'ordre total est `aBeforeB` : `MirrorRank(layer)` (mirror 0 < projection 1 < operation_action 2 < button 3 ; inconnu = 4), puis `ContentHash` lexicographique, puis `Agent`, puis `Target` (l'ordre est total sur *tous* les champs ⇒ la fonction est **symétrique** : `ResolveConflict(a,b)` et `ResolveConflict(b,a)` nomment le même gagnant). Le résultat porte `Winner`, `Loser` (qui ATTEND — jamais jeté), `NextAction = serialise_then_merge` (toujours), `SameTarget = (a.Target == b.Target)`. `MirrorRank` est ré-énoncé dans le kernel pour ne dépendre d'**aucun** import runtime.
- **Le panneau action-capable** (`SchedulerSection.tsx`) — la policy déclarée s'affiche (`orch-policy`) avec son verdict (`orch-policy-verdict`, borné par le knob spec = 2) ; **Tenter une édition mid-run** (`orch-bump-version-button`) bascule la version vive → `orch-pin-status` passe en « interdit » (gap F3) ; **Résoudre le conflit même-cible** (`orch-resolve-conflict-button`) appelle `resolveConflict` sur deux contenders (un `mirror` reviewer@v1 vs un `operation_action` executor@v1) → `orch-conflict-result` montre le vainqueur mirror-first, le perdant qui attend (`orch-conflict-loser`), `next_action = serialise_then_merge` ; **Réinitialiser** (`orch-reset-button`). Thémé (ADR 0010, tokens) + bilingue FR/EN (ADR 0011, next-intl).

## Méta

**Pourquoi un `Validate` *conscient du kind* plutôt qu'un champ optionnel ?** Parce qu'un agent qui porterait une policy serait un **monstre** : une orchestration sans équipe ne coordonne rien, une équipe sans policy n'a pas de règles. La complétude exige une correspondance 1-1 entre la forme et le kind. Le `Validate` la fait respecter de manière fail-closed : la mauvaise forme ne *compile* pas dans le sens AIDOS — elle est rejetée à la porte.

**Pourquoi borner le cap au knob spec (gap F1) ?** Parce qu'un cap déclaré sur l'agent (BA01) qu'une policy pourrait gonfler serait un **cap fantôme** — un chiffre qu'on croit appliqué mais qui ne l'est pas. BA24 fait de la policy une *borne* du knob, jamais une autorité au-dessus : le nombre que BA25 fera respecter à l'ordonnanceur est exactement le nombre déclaré, jamais un plus grand.

**Pourquoi l'immutabilité par-run (gap F3) ?** Parce qu'adapter une orchestration en plein run, c'est changer les règles du jeu pendant la partie — l'antithèse du cliquet. Un run épingle la `@version` comme un `AgentRun` épingle l'agent : la coordination d'un run est **reproductible**. Toute évolution est une nouvelle proposition (idée→miroir→/goal), tracée, approuvée — jamais un live-edit silencieux.

**Pourquoi un conflit réglé par règle, jamais par course (gap F2) ?** C'est le cœur determinism-first de BA24. Une course (ou un coin-flip, ou un « LLM arbitre ») jetterait le travail vert du perdant — un **lost-update**. La règle totale `ResolveConflict` ne décide que de *l'ordre* (qui passe en premier) ; le perdant *attend*, puis on **sérialise + merge** (`merge-semantic` rejoue chaque miroir sur le cut fusionné — un miroir rouge bloque). Mirror-first d'abord, content-hash ensuite : déterministe, total, symétrique. Aucun travail n'est jamais perdu.

## Méta-méta

BA24 est un cas d'école des trois invariants AIDOS appliqués à la coordination multi-agent.

- **Le mur (NIVEAU 3).** La policy est une *vérité* au-dessus de la ligne ; l'écran ne l'écrit jamais — il la **propose** (le chemin `Propose` rend un `proposed` requérant l'autorité S16). L'arbitrage de conflit ne décide que d'un ordre : il n'écrit aucune vérité. L'orchestration coordonne, elle ne décrète pas — exactement comme un agent n'est jamais une autorité.
- **Determinism-first.** Tout ce qui *peut* être une fonction pure l'**est** et fait foi : `validatePolicy`, `PolicyVersion` (un hash, pas un agent), `MutationIsForbidden` (une comparaison), `ResolveConflict` (un ordre total). Aucun LLM nulle part ; le conflit est mergé *par règle*, jamais par une course. Un arbitrage-par-LLM serait une faille de déterminisme qui bloquerait le step. Les miroirs de reproductibilité (rapid + fast-check) épinglent : même entrée ⇒ même sortie.
- **Anti-Goodhart.** Les poids de l'ordre (mirror-first, content-hash) sont **déclarés**, jamais appris. Le cap est déclaré et borné ; on ne peut pas le gonfler pour « passer ». Et l'immutabilité par-run ferme la porte au plus subtil des hacks : changer la règle pendant qu'on est mesuré dessus. La policy qui gouverne un run est gelée pour la durée du run — la mesure ne peut pas bouger sous le test.
