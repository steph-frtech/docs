## Implémentation

### Le paquet — `back/runtime/spike/dp19connectorgov` (jetable, zone /spike)

DP19 est un **SPIKE-gate** (T0, ratchet OFF, **zone `/spike`** : code jetable, aucune écriture `kernel`/`mirrors`/`fitness`, aucune persistance). Il ouvre l'EPIC E en répondant **par mesure** à une seule question : la gouvernance des connecteurs **tient-elle avec le mur EXISTANT, sans nouveau point de confiance unique** ? Le paquet `back/runtime/spike/dp19connectorgov` porte le gate pur ; son jumeau TS `front/web/lib/connector-governance.ts` grave la matrice mesurée pour le front.

```go
type Connector struct {
```

### `GateConnectorAction` — réutilise les 5 enforcers, n'ajoute que scope + A2

Le gate est **pur, total, fail-closed** — aucune base, aucune horloge, aucun aléa, aucune I/O. Il **réutilise** les enforcers existants (`agentimpl`, set-membership pur) et n'**ajoute** que deux gardes (§5 : on ADD, on ne RETIRE jamais) :

1. **Scope (l'ajout)** — `op == OpWrite && c.Scope == ScopeRO` ⇒ refus `CONNECTOR_SCOPE_READ_ONLY` **avant tout le reste** : un connecteur RO n'a aucune porte d'écriture.
2. **Capacité (le mur existant)** — `agentimpl.ToolAllowed(impl, c.Server, tool)` ; non liée ⇒ `CONNECTOR_TOOL_NOT_BOUND`.
3. **Confinement / egress (le mur existant)** — pour `PlaneExternal`, `agentimpl.EgressAllowed(impl, c.EgressHost)` ; hors liste ⇒ `CONNECTOR_EGRESS_NOT_ALLOWED`.
4. **A2 — approbation runtime (l'ajout)** — `op == OpWrite && c.Scope == ScopeRW` ⇒ exige `approvalFor(approvals, c.Name, OpWrite)` (une `ConnectorRuntimeApproval` fraîche, `Granted` par un humain) ; absente ⇒ `CONNECTOR_WRITE_NOT_APPROVED`. C'est **set-membership fail-closed**, **PAS** `authority.Decide`.

Une lecture ne requiert que (2)+(3). `GateOutcome` a exactement deux formes — admise, ou refusée avec un `SpikeCode` — la **même** forme fail-closed que les `ToolDecision`/`EgressDecision` existants.

### `GateAIDataAccess` — A3, l'IA jamais en direct sur la DB

```go
if via == nil || target == AIDirectDBTarget {
  return GateOutcome{Admitted: false, Code: CodeAIDirectDBForbidden}
}
return GateConnectorAction(impl, *via, op, approvals) // le seul chemin IA→DB légal
```

A3 est set-membership fail-closed : une cible directe (`AIDirectDBTarget`, ou tout `via == nil`) est refusée `AI_DIRECT_DB_ACCESS_FORBIDDEN` — la cible directe n'est **jamais** membre de la surface autorisée de l'IA. Le **seul** chemin IA→DB légal passe par un connecteur contrôlé, qui **défère** alors au même `GateConnectorAction` (capacité + scope + approbation).

### Le ledger Merkle — `ActionToRun` + `LedgerFor` réutilisent `agentrun`

Chaque action — **admise OU refusée** — est projetée en `agentrun.AgentRun` (`ResultGreen` si admise, `ResultBlocked` sinon), `agentrun.Record`-ée, puis pliée dans le **ledger Merkle existant** via `agentrun.BuildLedger`. Les horodatages sont **fournis** (pas d'horloge arg-less — déterminisme). `LedgerFor` rend un ledger dont `agentrun.Verify().OK` est vrai ssi la chaîne est intacte. **Aucune nouvelle chaîne** : le tamper-evidence est celui d'`agentrun`.

### `BuildMatrix` — 6 cellules gravées comme DONNÉE, verdict COMPUTÉ

`BuildMatrix` sonde deux connecteurs jetables (`postgresRO()` interne RO, `slackRW()` externe RW egress `slack.com`) + la tentative IA→DB directe, en six `probeStep`. Chaque pas produit un `MatrixRow{case, connector, scope, plane, op, approvalRequired, expectAdmitted, measuredAdmitted, measuredCode, ledgerEntry, pass}` où `pass = (measured == expect) && ledgerEntry`. Le verdict global est **COMPUTÉ** (jamais déclaré, §8) : `VerdictGo` ssi **toutes** les cellules `pass` ∧ `agentrun.Verify(ledger).OK` ; sinon `VerdictNoGo`. ## Méta

- **Le verdict est une mesure, jamais un avis — et le miroir T0 le prouve en trois mesures.** D'abord, `BuildMatrix` n'a **rien à déclarer** : il *exécute* le gate sur six cellules et **observe** chaque sortie (`measuredAdmitted`/`measuredCode`), puis pose `pass = (measured == expect) && ledgerEntry`. Le verdict global est la **conjonction** des `pass` ∧ `Verify(ledger).OK` — du booléen pur, computé, jamais un LLM-juge (§8). Ensuite, le **déterminisme** est lui-même mesuré (`TestSpike_BuildMatrix_Deterministic` : même `impl` ⇒ même matrice) — le gate n'a ni horloge, ni aléa, ni I/O. Enfin, le **ledger** est mesuré : six entrées, `Verify().OK`, root content-adressé `a5f508e2…` — chaque action est vérifiable, et `TestSpike_LedgerTamper_GoesRed` prouve qu'altérer une entrée fait rougir la chaîne.

- **Le no-go est reproductible, pas une absence de go.** `TestSpike_UngovernedSurface_VerdictNoGo` injecte une surface non-liée (`Tools=nil`) et **mesure** que le verdict bascule en `no-go` — le ledger restant vérifiable. Un no-go ne fabrique jamais un vert absent : il **nomme** la cellule fautive. C'est l'honnêteté §8 appliquée au gate lui-même : un go n'est crédible que si le même code peut, sous d'autres entrées, produire un no-go observable.

- **Réutiliser plutôt que réinventer (ADR 0007), sur les deux plans.** Le gate n'invente ni un enforcer ni une chaîne d'audit : la capacité est `agentimpl.ToolAllowed`, l'egress `agentimpl.EgressAllowed`, le ledger `agentrun.BuildLedger`/`Verify`. DP19 n'ajoute que la **composition** (le scope RO/RW, l'approbation A2, l'invariant A3) — du set-membership de la même forme fail-closed. C'est le déterminisme-first (§6) : décider d'admettre ou refuser une action de connecteur est une **fonction pure** de ses entrées déclarées, donc c'est du **code**, jamais un agent.

## Méta-méta

- **Aucun nouveau mur, aucun nouveau point de confiance unique.** C'est la réponse mesurée à la question DP19, et c'est le mur (§2) appliqué à la couche connecteurs. Le réflexe naïf — bâtir un nouveau gardien des connecteurs — créerait une nouvelle surface de confiance à percer. DP19 prouve l'inverse : la gouvernance des connecteurs est un **cas particulier** de la sécurité déjà construite. Les enforcers existants gardent la capacité et l'egress ; le ledger existant rend tout vérifiable ; on n'**AJOUTE** que des gardes (§5, « ADD a guardrail, never REMOVE one »), jamais un nouveau mur ni un nouveau `BlockReason` canonique. EPIC E (DP20+) ne pourra que continuer d'ajouter des gardes sur ce socle.

- **L'IA jamais en direct sur la DB est load-bearing.** A3 n'est pas un confort, c'est un invariant porteur : si l'IA pouvait joindre la base en direct, toute la gouvernance (scope, approbation, ledger) serait contournable par la porte de derrière. Le gate ferme cette porte par set-membership fail-closed — la cible directe n'est jamais membre de la surface autorisée — et n'ouvre que le chemin médié par un connecteur **contrôlé** (donc gouverné et journalisé). L'IA construit le code au build-time ; elle ne s'assoit pas dans la boucle runtime à faire ce qu'un connecteur gouverné doit faire.

- **A2 : le Kernel gate la vérité, jamais un effet runtime.** C'est la distinction la plus fine de DP19. AIDOS a déjà un truth-admitter (`authority.Decide`) — mais il gouverne si une **vérité** peut changer (approuver un ChangeSet, valider un /goal). Une écriture de connecteur (« poster ce message Slack ») est un **effet runtime**, pas un changement de vérité. A2 la fait admettre par une **approbation humaine runtime jetable** (`ConnectorRuntimeApproval`), **jamais** par `authority.Decide`. La mention d'`authority.Decide` dans les critères antérieurs est explicitement **SUPERSEDED** : confondre l'admission d'une vérité et l'admission d'un effet serait faire approuver un post Slack par les approbateurs du noyau. Tout cela en zone `/spike`, ratchet OFF — le code prouve puis s'efface ; la promotion de la couche reste l'affaire de l'unique porte (idée → miroir → /goal). Le verdict mesuré est gravé dans l'ADR 0069.
