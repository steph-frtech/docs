## En une phrase

BA22 ajoute au paquet `back/runtime/scheduler` le **moteur lease/expire** : `Schedule(queue, agents, now, leaseUntil)`, un planificateur **pur et total** d'UN tick (il expire les leases périmés `claimed→open`, gate les dépendances, et loue la tête mirror-first au rôle correspondant), un **tick driver** (la seule coquille impure, qui fournit `now` par tick — gap E1, l'anti-agent-mort sans humain), et `Fence(writeEpoch, currentEpoch)`, le comparateur d'epoch déterministe au **write-path** (gap E2 : une écriture d'epoch périmé est refusée — `AGENT_LEASE_FENCED` — pas de lost-update). Tout est calculé par des fonctions pures, jamais par un LLM (determinism-first).

## Implémentation

Le cœur vit dans `back/runtime/scheduler/lease.go` + `tick.go`, jumelé dans `front/web/lib/scheduler.ts`.

- **`Schedule(queue, agents, now, leaseUntil) → ScheduleResult{Queue, Assignments}`** — le planificateur PUR d'un tick. Aucune horloge (`now` est *fourni*), aucun rng, aucune I/O ; même entrée ⇒ même `(queue, assignments)`. Trois règles dans l'ordre :
  1. **EXPIRE** — tout item `claimed` dont `lease_until` est non vide ET `< now` est récupéré (`claimed→open`, owner+lease vidés) ; son lease mort surface une `AgentAssignment{Statut: expired}`. L'`lease_epoch` reste **monotone** (non remis à zéro — c'est le jeton de fencing).
  2. **BLOCK/UNBLOCK** — un item `open`/`blocked` dont les `Dependencies` (la colonne JSONB S22) ne sont pas TOUTES `resolved` est surfacé `blocked` ; toutes résolues ⇒ il (re)devient leasable.
  3. **LEASE** — parmi les `open` leasables, la tête mirror-first (`HeadOf`, BA21) est staffée à son agent role-matché (`MatchRole`, BA21) ; cet agent devient occupé pour le reste du tick (un roster local mutable) ; on répète jusqu'à ce qu'aucune tête leasable ne puisse être staffée.
  Les assignments reviennent triés `(RedWorkItem, Statut)` — jamais l'ordre d'itération d'une map.
- **Le tick driver** (`tick.go`) — la SEULE coquille impure. `Driver{Clock, Source, Apply, Lease, Interval}` ; `Tick()` lit le snapshot (`QueueSource`), demande `now` à l'`Clock`, calcule la fenêtre de lease (`LeaseWindow.Until(now)` = `now + Duration`, fail-closed sur un `now` malformé), appelle le `Schedule` PUR, et applique via l'`Applier` (la couture que la coquille MCP BA23 câblera sur l'`UPDATE` du rôle `aidos_scheduler`). `Run(ctx)` boucle sur un `time.Ticker` jusqu'à annulation. L'`Clock` est une *seam* : `SystemClock` en prod (la seule touche d'horloge réelle), un stepper déterministe en test. C'est ainsi qu'un item d'agent mort est récupéré au tick suivant la péremption — sans action humaine (gap E1).
- **`Fence(writeEpoch, currentEpoch) → FenceVerdict`** — le comparateur de fencing au write-path (gap E2), total, sans panic : `==` ⇒ vivant (`OK`, pas de `BlockReason`) ; `<` ⇒ périmé (re-loué depuis — agent réveillé en retard — refusé `AGENT_LEASE_FENCED`) ; `>` ⇒ impossible (nul ne porte un epoch futur, refusé, fail-closed). C'est le miroir Go du garde `WHERE lease_epoch = $writeEpoch` de l'`UPDATE` du rôle ordonnanceur — le même compare déterministe, jamais un jugement LLM. Le `BlockReason` `AGENT_LEASE_FENCED` (S13) porte la forme actionnable (code/severity/explanation/how_to_fix).
- **Les miroirs de reproductibilité** (`lease_fixture_test.go` + `lease_property_test.go`, rapid ; `tick_test.go`) — fixtures hand-off (gate de dépendance bloque-puis-loue ; expire sans humain ; staffing mirror-first ; idempotence) + propriétés ∀ : (1) déterminisme byte-à-byte ; (2) ne loue jamais un item bloqué ; (3) expire (`< now` → reclaim ; `>= now` → lease intact, epoch inchangé) ; (4) **cross-invariant gap K4** (queue.status et assignment.statut restent jointement consistants : pas de `claimed` sans assignment live ; pas d'assignment fermé pointant un `claimed` encore live) ; (5) fencing (== vivant, ≠ refusé). `tick_test.go` prouve le reclaim d'un lease d'agent mort au tick (avec une `Clock` injectée), le reclaim-puis-re-lease (epoch 2→3), `LeaseWindow.Until` et le déterminisme de la boucle. *Note* : le générateur de file tire des `item_id` **distincts** (c'est la PK de `runtime.red_work_queue`) — un id dupliqué modéliserait une auto-dépendance que la file ne peut pas contenir.
- **Le jumeau front** (`front/web/lib/scheduler.ts` : `schedule`, `fence`, `QueueEntry.dependencies`) reflète le cœur Go verbatim ; son miroir fast-check (`front/web/lib/scheduler.test.ts`) rejoue les mêmes propriétés (déterminisme, never-lease-blocked, expire, idempotence, fencing `==`/`≠`).
- **L'UI action-capable** (`SchedulerSection.tsx`, sous-section `scheduler-lease-engine` sur `/agents`) — une file de démo : un miroir, une projection qui en dépend (bloquée), et un item d'agent mort (`lease_until` 11:00 < `now` 12:00). « Lancer un tick » bound à `schedule` → le lease mort est récupéré, la projection reste `blocked` ; « Résoudre le miroir » + re-tick → la projection se débloque et se loue ; « Vérifier le fence » bound à `fence` → un epoch périmé donne `AGENT_LEASE_FENCED`. Thémé (ADR 0010), bilingue FR/EN (ADR 0011). L'e2e Playwright (`tests/e2e/agents.spec.ts`, bloc BA22, 5 cas) prouve chaque contrôle à l'écran.

## Méta — pourquoi c'est construit ainsi

Trois décisions structurantes.

**Tout ce qui décide est pur ; le seul impur est le tick driver.** `Schedule` ne touche ni horloge, ni rng, ni I/O — `now` lui est *fourni*. C'est ce qui rend le moteur rejouable à l'octet et testable tick-par-tick avec une `Clock` fake. Le `Driver` est la frontière mince où l'impureté est *isolée* à une interface (`Clock`) ; CLAUDE.md §7 interdit une horloge arg-less dans un script `/long-run`, mais l'autorise dans un daemon runtime — c'est l'unique impureté sanctionnée de l'ordonnanceur.

**Le fencing par epoch monotone, pas par verrou ni horloge.** Le problème du split-brain (deux agents écrivent la même cible) se résout sans verrou distribué : chaque lease porte un numéro qui ne fait que monter, et l'écriture doit présenter *exactement* l'epoch courant. Un agent réveillé en retard a un epoch strictement inférieur ⇒ refusé. C'est un *fencing token* (la même technique que les fencing tokens des systèmes de lock distribués), réduit à un compare d'entiers — déterministe, total, et identique côté Go, côté TS, et côté garde SQL `WHERE lease_epoch = $writeEpoch`. On refuse l'epoch futur aussi (fail-closed) : seul l'ordonnanceur bump l'epoch.

**L'expire ré-applique le gate de dépendance dans le même tick.** Après un reclaim (`claimed→open`), l'item repasse par BLOCK/UNBLOCK : s'il a une dépendance non résolue, il devient `blocked` immédiatement (pas `open`). Ainsi un seul tick laisse toujours la file dans un état cohérent — d'où l'idempotence sur une file stabilisée et la cross-invariant K4.

## Méta-méta — l'invariant que ça garde vivant

> **L'ordonnanceur est un cœur qui bat sans humain — il récupère seul le travail d'un agent mort — et le temps ne peut jamais provoquer un lost-update : l'écriture en retard est refusée, pas avalée.**

BA22 fait passer la file de « journal en écriture seule » à « dispatcher fencé », mais le mur de S52/BA20 reste vrai à chaque tick : `Schedule` ne réclame jamais pour le rôle agent, n'écrit aucun schéma de vérité, et le tick driver applique sous le seul rôle `aidos_scheduler` (UPDATE des quatre colonnes de transition, SELECT sur `kernel.agent_layer`, rien d'autre). La défense en profondeur tient sur trois plans : `Fence` (Go) ⟺ `fence` (TS) ⟺ le garde `WHERE lease_epoch = $writeEpoch` de l'`UPDATE` — le même compare déterministe partout. Les deux miroirs de reproductibilité (rapid + fast-check) rejouent « même `(queue, now, agents)` ⇒ même `(queue, assignments)` » : un ordonnanceur qui jugerait par LLM l'expiration, le gate ou le casting — ce qu'une comparaison d'horloge, un set de résolus et un ordre total décident — serait un trou de déterminisme qui **bloque le pas**.

## Limites connues (OpenQuestions, par conception)

- **Persistance Postgres des miroirs.** Les miroirs fixture + property de BA22 sont matérialisés comme tests exécutables (`lease_fixture_test.go`, `lease_property_test.go`, `tick_test.go`) ; leur persistance dans le schéma `mirrors` est back-fillée au pas qui consomme ce schéma (exception bootstrap, S06). N'empêche pas le pas.
- **Le câblage UPDATE est BA23.** BA22 livre le planificateur pur, le tick driver et le comparateur `Fence` ; le serveur MCP `scheduler` qui applique les transitions atomiquement sous le rôle `aidos_scheduler` et vérifie l'epoch côté `UPDATE` est le pas BA23. Le `Fence`/`AGENT_LEASE_FENCED` de BA22 est le miroir Go/TS de ce garde SQL. Différé structurel, OpenQuestion documentée.
- **La coordination multi-agent est BA24/BA25.** BA22 staffe un agent par item par tick (au plus un lease live par item) ; l'arbitrage de N agents contendants sous une `OrchestrationPolicy` (conflits same-file, `MaxConcurrency`) est BA24/BA25. Surface ouverte au pas qui en a besoin.
