## Implémentation

### Le paquet — `back/runtime/deploy` (2 fichiers exactement)

DP26 **étend** le déploiement de S96 par l'ordre complet du substrat, **additivement**, sans le dupliquer. Tâche **backend-only** ; le mur tient (deploy = below-the-line, re-projette une phase, aucune écriture-vérité).

Deux fichiers, exactement :

- `back/runtime/deploy/deploy.go` — **ÉTENDU** (additif ; S96 préservé **byte-identiquement** ; imports ajoutés : `scope`, `stackmanifest`, `bootstrap`, `datafragments`, `stackemit`).
- `back/runtime/deploy/deploy_dp26_test.go` — le **miroir NEUF** (fixture + property), **écrit RED-first** (confirmé RED sur les symboles manquants, puis GREEN).

### L'API étendue — 4 champs d'`Input`, 1 champ de `DeployPlan`

`DeployPlan` GAGNE **1 champ** :

type DeployPlan struct {

L'**anti-overwrite (§9)** est gravé à la source : quand `Order` est `nil`, sa clé est **OMISE de l'adresse de contenu** (via `order_hash`) — donc les **IDs de plan S96 existants restent byte-inchangés**. Un `Manifest` vide ⇒ plan S96 exact.

L'ordre est **déclaré** (le slice `orderedStages`), jamais dérivé d'une itération non-déterministe — `OrderedDeployStages` en rend une **copie**. Sept rungs, ni plus ni moins.

### `BuildPlan` step 6 — le déroulé DP26 (seulement si `Manifest.AppName != ""`)

Quand un manifest est fourni, `BuildPlan` exécute son étape 6 en **réutilisant verbatim** quatre moteurs (ADR 0007), sans forker aucun :

1. **per-app check** — un manifest cross-app est **refusé** (`ErrManifestProjectMix`).
2. **DP05 `stackemit.EmitStack`** — RE-ÉMET la stack depuis la phase ; son empreinte = `StackBundleHash` (« jamais stale » : l'artefact est ré-émis, pas exhumé).
3. **DP15 `datafragments.SubstrateCoreFragments(project, env)`** — provisionne le substrat de données ; le gate **DP06 prod×doltgres** est **délégué** (en `prod`, doltgres est omis).
4. **DP12 `bootstrap.EmitBootstrapSequence`** — émet l'amorçage one-shot ; son empreinte = `BootstrapHash`.
5. **ordonner les 7 étapes** puis **content-address** : `Order.Hash = records.Hash` sur le résumé canonique `stack/bootstrap/seq:kind:detail`.

Tout refus de DP05 / DP15 / DP12 est **surfacé verbatim**. La migration (étape 4) **réutilise le MÊME** `datamigrate.Plan` forward-only que S95 — inséré à sa place dans la séquence, pas un second plan.

### L'invariant capital — l'ordre se replie dans l'id, jamais dans l'app

L'`Order.Hash` se **replie dans `DeployPlan.contentAddress`** via `order_hash` — un **ordre différent donne un deploy id différent**. Mais l'ordre **n'altère JAMAIS** `EmittedAppHash`, l'URL ni le `StackName` : la re-projection de l'app est préservée. Le miroir l'épingle pour **toutes** les phases.

### Ce qui est PRÉSERVÉ untouched (S96)

`IsDeployable`, `Gate`, `BuildPlan → PHASE_NOT_STABLE`, `DeployedMatchesPhase`, `MigrationIsForwardOnly`, `subdomainOf` — tous **inchangés**. DP26 n'ajoute **aucun** gate ; il réutilise `IsDeployable` (Stop-gate) et `DataTruthScope` (S95, migration destructive human-gated).

## Méta

- **Le miroir Go est l'épreuve `hash artefact = hash phase`, ∀ phase.** Le miroir property mesure le cœur déterministe : il épingle l'invariant capital — l'ordre n'altère **jamais** `EmittedAppHash`, `DeployedMatchesPhase` tient `forall` ; le miroir de reproductibilité pin la byte-identité (même phase → même `DeployPlan`, même `Order.Hash`). Le miroir fixture (N2, `state → command → events`) épingle la phase non-stable refusée (`PHASE_NOT_STABLE`), la migration breaking-no-backfill refusée (`BREAKING_MIGRATION_NO_BACKFILL`), et l'ordre canonique des sept étapes. Que le déploiement soit *invariant à l'ordre sur le résultat émis* et *déterministe sur le déroulé* n'est pas une promesse — c'est une propriété prouvée.

- **Déterminisme-first (§6/§8) : ré-émettre, provisionner, amorcer, ordonner, hacher sont des fonctions pures, donc du code.** DP26 n'invite **aucun** LLM : la re-émission est DP05 (émission déterministe depuis la phase), les fragments sont DP15, l'amorçage est DP12, l'ordre est un slice **déclaré**, l'`Order.Hash` est une adresse de contenu (`records.Hash`). L'ordre est un **plan-as-data** : aucune horloge, aucun RNG, aucune I/O, aucun docker. Même entrée ⇒ même sortie (le miroir de reproductibilité le pin). Construire un pipeline de déploiement est une **composition de moteurs purs**, pas un jugement flou.

- **Réutiliser plutôt que réinventer (ADR 0007), sur DP05 + DP15 + S95 + DP12.** DP26 n'invente **ni** re-émission, **ni** provisioning, **ni** migration, **ni** amorçage : il **réutilise verbatim** `stackemit.EmitStack` (DP05), `datafragments.SubstrateCoreFragments` (DP15), le `datamigrate.Plan` forward-only de S95, et `bootstrap.EmitBootstrapSequence` (DP12) — composés, jamais forkés. Et il **étend** S96 — il ne le **duplique pas** : pas de second déploiement à côté, mais 4 champs optionnels + 1 champ de plan, avec l'invariant capital intact. Un seul moteur de déploiement, une seule re-émission DP05, un seul gate de migration dans tout AIDOS.

## Méta-méta

- **Below-the-line : le déploiement ne grave aucune vérité, il re-projette une phase.** C'est le mur (§2) : déployer une phase n'écrit **rien** dans `kernel`, `mirrors` ou `fitness`. Le déploiement est une **re-émission PURE** depuis la **phase content-adressée** : il ne déclare aucune vérité nouvelle, il re-projette ce que la phase fige déjà. L'agent n'a aucun GRANT pour graver une vérité ; le déploiement n'en a pas besoin — il vit **en dessous de la ligne**.

- **DP26 hérite le Stop-gate de S96 — aucun nouveau gate.** L'enjeu porteur, c'est que « Déployer cette phase » reste **keyé sur la phase stable** (done-is-computed) sans inventer un second mécanisme de blocage. La phase non-stable est refusée par l'`IsDeployable` **existant** (`PHASE_NOT_STABLE`), *même* quand le plan porte sa section d'ordre. Et la migration **destructive** reste **human-gated** par `DataTruthScope` (S95) — `BREAKING_MIGRATION_NO_BACKFILL`. DP26 n'ajoute **aucun** gate : il branche un ordre sur les gates qui existent déjà.

- **DP26 ÉTEND S96, il ne le DUPLIQUE pas — l'anti-overwrite gravé dans l'adresse de contenu.** La règle (§9) est nette : quand le `Manifest` est absent, la forme S96 est **byte-inchangée** ; quand `Order` est `nil`, sa clé est **OMISE de l'adresse de contenu** — les IDs de plan S96 ne bougent **pas**. L'ordre se replie dans le *deploy id* (ordre différent → deploy id différent), mais **jamais** dans `EmittedAppHash`/URL/`StackName`. La loi de complétude veille : un geste sans miroir serait un **monstre** — l'extension ne vit que parce qu'elle porte sa preuve vivante (fixture + property, RED-first). C'est l'anti-overwrite poussé jusqu'au hash : on **ajoute** un comportement, on n'**altère** rien de l'existant.
