## Implémentation

### Le paquet — `back/runtime/preview` (2 fichiers exactement)

DP25 **étend** le preview de S94 par profile, **additivement**, sans le dupliquer. Tâche **backend-only** ; le mur tient (preview = below-the-line, aucune écriture-vérité). C'est la pièce qui **ouvre l'EPIC F**.

Deux fichiers, exactement :

- `back/runtime/preview/preview.go` — **ÉTENDU** (additif ; S94 préservé **byte-identiquement**, §9).
- `back/runtime/preview/preview_dp25_test.go` — le **miroir NEUF** (property + fixture), **écrit RED-first** (avant que le comportement de l'extension soit prouvé).

### L'API étendue — 5 champs d'`Input`, 2 champs de `PreviewPlan`

L'`Input` GAGNE **5 champs OPTIONNELS** ; la forme S94 est inchangée quand le `Manifest` est absent :

```go
type Input struct {
  // … champs S94 inchangés …
  Profile  stackmanifest.Profile      // défaut DefaultProfile = ProfileCore
  Manifest stackmanifest.StackManifest // la source DP02 amorcée — absent ⇒ pur plan S94, aucun bootstrap
  Host     bootstrap.HostState
  Secrets  bootstrap.SecretsState
  Env      scope.Environment          // défaut DefaultPreviewEnv = EnvDev — seulement pour le gate doltgres-in-prod DP11
}

const DefaultProfile    = stackmanifest.ProfileCore
const DefaultPreviewEnv = scope.EnvDev
```

`PreviewPlan` GAGNE **2 champs** :

```go
type PreviewPlan struct {
  // … champs S94 PRÉSERVÉS untouched : EmittedAppHash, ServedMatchesEmitted, URL, Subdomain, StackName, Boot, Teardown …
  Profile   stackmanifest.Profile
  Bootstrap *PreviewBootstrap // nil pour un plan S94
}
```

La signature de `BuildPlan` est **préservée** : `(PreviewPlan, *blockreason.BlockReason)`. L'**anti-overwrite (§9)** est gravé à la source : quand `Bootstrap` est `nil`, les clés `profile`/`bootstrap` sont **OMISES de l'adresse de contenu** — donc les **IDs de plan S94 existants restent byte-inchangés**.

### Le `PreviewBootstrap` et le `TeardownPlan` — amorçage + démontage

```go
type PreviewBootstrap struct {
  Profile      stackmanifest.Profile
  Sequence     bootstrap.Sequence
  SequenceHash string   // l'adresse DÉPENDANTE du profile — se replie dans l'ID du plan
  Services     []string
}

type TeardownPlan struct {
  StackName string
  Commands  []string
  Services  []string  // ordre INVERSE du boot
}

func TeardownOf(plan PreviewPlan) TeardownPlan  // pure — démontage déterministe
```

`buildBootstrap` **réutilise verbatim** (ADR 0007) les deux moteurs de l'EPIC D — il ne **forke** ni l'un ni l'autre :

1. **`composeemit.FilterByProfile`** (DP11) — retient les services que le profile sélectionne ;
2. **`bootstrap.EmitBootstrapSequence`** (DP12) — émet la séquence d'amorçage one-shot déterministe.

Un **manifest cross-app** (deux projets mélangés) est **refusé** : `ErrManifestProjectMix` (nouvelle erreur).

`TeardownOf` est **pure** : les services se dénouent dans l'**ORDRE INVERSE** du boot ; un démontage **complet** est un **sur-ensemble** d'un démontage **lean** (commandes destroy + stack-rm).

### L'invariant capital — `EmittedAppHash` profile-FREE

`EmittedAppHash` reste une fonction **pure de (phase ⊕ surface)** — **sans profile**. Le miroir l'épingle pour **tous** les profiles : choisir `git`, `core` ou `full` ne change **rien** à l'app servie (`ServedMatchesEmitted` tient), ni à l'URL, au sous-domaine, au nom de stack. Seul l'**amorçage** (`SequenceHash`, et donc l'`ID` du plan) varie avec le profile.

### Pas de re-émission DP05 câblée — par design

Aucun `EmitStack` (DP05) n'est câblé dans `BuildPlan` : la **re-émission** est l'affaire de l'**exécuteur gaté** (le doc y pointe). Le miroir prouve le **PLAN** + le **hash** ; le serveur web-preview sert l'app — **pas de vrai docker**, exactement comme S94.

## Méta

- **Le miroir Go est l'épreuve `hash-preview = hash-phase`, ∀ profiles.** Le miroir property mesure le cœur déterministe : `TestDP25HashInvariantAcrossProfiles` épingle l'invariant capital — ∀ profile, l'`EmittedAppHash` est celui de la baseline S94 ; `TestDP25Reproducible` pin la reproductibilité byte-identique (même phase + profile ⇒ même plan, même `SequenceHash`, même teardown) ; `TestDP25LeanVsFull` prouve que `git` boote moins que `full` **sans** toucher l'app-hash ; `TestDP25TeardownDeterministic` pin le démontage en ordre inverse du boot. Le miroir fixture (N2, `state → command → events`) épingle le cycle de vie complet (build→probe→teardown) et les **4 refus**. Que la preview soit *invariante au profile sur le résultat émis* et *déterministe sur l'amorçage* n'est pas une promesse — c'est une propriété prouvée.

- **Déterminisme-first (§6/§8) : filtrer, amorcer, démonter, hacher sont des fonctions pures, donc du code.** DP25 n'invite **aucun** LLM : le filtrage par profile est DP11 (set-membership sur `ServiceProfiles`), la séquence d'amorçage est DP12 (émission déterministe), le `SequenceHash` est une adresse de contenu, le `TeardownOf` est un renversement pur de l'ordre de boot, l'`EmittedAppHash` est une fonction pure de (phase ⊕ surface). Même entrée ⇒ même sortie (le miroir `TestDP25Reproducible` le pin). Construire un preview par profile est une **composition de moteurs purs**, pas un jugement flou.

- **Réutiliser plutôt que réinventer (ADR 0007), sur DP11 + DP12.** DP25 n'invente **ni** filtrage par profile **ni** amorçage one-shot : il **réutilise verbatim** `composeemit.FilterByProfile` (DP11, composé jamais forké) et `bootstrap.EmitBootstrapSequence` (DP12, importé jamais re-frappé). Et il **étend** S94 — il ne le **duplique pas** : pas de seconde preview à côté, mais 5 champs optionnels + 2 champs de plan, avec l'invariant capital intact. Un seul moteur de preview, un seul filtrage par profile, un seul amorçage dans tout AIDOS.

## Méta-méta

- **Below-the-line : la preview ne grave aucune vérité.** C'est le mur (§2) : prévisualiser l'app n'écrit **rien** dans `kernel`, `mirrors` ou `fitness`, et ne **persiste rien** en Postgres (l'amorçage de preview est éphémère — *bootstrap exception*, `WroteKernel` toujours `false`). La preview est une **re-émission PURE** depuis la **phase content-adressée** : elle ne déclare aucune vérité nouvelle, elle re-projette ce que la phase fige déjà. L'agent n'a aucun GRANT pour graver une vérité ; la preview n'en a pas besoin — elle vit **en dessous de la ligne**.

- **DP25 ÉTEND S94, il ne le DUPLIQUE pas — l'anti-overwrite gravé dans l'adresse de contenu.** L'enjeu porteur, c'est de prévisualiser l'app *par profile* **sans** faire dériver l'empreinte ni casser les IDs de plan existants. La règle (§9) est nette : quand le `Manifest` est absent, la forme S94 est **byte-inchangée** ; quand `Bootstrap` est `nil`, ses clés sont **OMISES de l'adresse de contenu** — les IDs de plan S94 ne bougent **pas**. C'est l'anti-overwrite poussé jusqu'au hash : on **ajoute** un comportement, on n'**altère** rien de l'existant.

- **DP25 ouvre l'EPIC F — la prévisualisation par stack de l'app émise.** La loi de complétude (Mandat A, §5) veille : un geste sans miroir serait un **monstre** — l'extension ne vit que parce qu'elle porte sa preuve vivante (property + fixture, RED-first). Et c'est *load-bearing* : sans le profile, la preview servait une stack fixe ; avec lui, elle amorce **exactement** les services que le profile retient, déterministement, et les démonte proprement — tout en gardant l'invariant capital. La couche de prévisualisation par stack est posée, et l'**EPIC F s'ouvre**.
