## Implémentation

**Le twin de pipeline `lib/v2/workflows.ts`** — la source unique de la LOGIQUE, PUR (aucun React/DOM, aucun LLM, aucune horloge, aucun aléa) :

- Types : `WorkflowNodeKind` (`start | step | gate | decision | end`) ; `EndOutcome` (`success | denied`) ; `NodePos` (`{x, y}`) ; `WorkflowNode` (`id`, `kind`, `label`, `position`, `outcome?`) ; `WorkflowEdge` (`id`, `source`, `target`, `label`, `branch?: "allow" | "deny"`) ; `WorkflowGraph` (`fixtureId`, `nodes`, `edges`).
- `workflowGraph(fixture)` : **le cœur**. Réutilise le twin WB2-12 — `frames(fixture)` (sans la frame −1 idle) pour la vérité du déroulé et `verdict(fixture)` pour savoir si le scénario refuse. Déroule les frames : `start` (le nom de la commande) → pour chaque verbe, un `step`, sauf le `authorize` qui devient un **`gate`** suivi d'un nœud **`decision`** ; la décision émet la branche **`deny`** vers un `end{denied}` (décalé en `x = DENY_X = 220`) et marque (variable LOCALE `pendingAllowFrom`) que la prochaine arête est la branche **`allow`** ; le flux se termine sur un `end{success}`. Les ids sont content-adressés par position (`w0`, `w1`, …), le layout vertical déterministe (`STEP_Y = 90`). PURE & TOTALE & déterministe : deux appels → graphe byte-identique.
- `moveNode(graph, id, pos)` : l'**édition proposée**, PURE & IMMUABLE. Renvoie un nouveau graphe avec la `position` du nœud `id` remplacée ; le graphe d'origine est intact (`nodes.map`), les `edges` et `fixtureId` inchangés ; un id inconnu laisse le graphe identique (totalité). Aucune écriture — un layout local.
- `nodeKindCounts(graph)` : le décompte par type (`Record<WorkflowNodeKind, number>`).
- Registre : `WORKFLOWS = FIXTURES` (réutilise les fixtures Operation DSL de WB2-12, mêmes ids/slugs), `WORKFLOW_HAPPY = CREATE_ORDER_HAPPY`, `WORKFLOW_DENIED = CREATE_ORDER_DENIED`. Routage : `workflowSlug(id)` (`/` → `--`), `workflowBySlug(slug)` (`--` → `/`, undefined pour un inconnu — totalité → 404), `workflowSlugs()`. `STEP_SLUG = "wb2-13-workflows"`.

**Le client `app/v2/workflows/WorkflowClient.tsx`** (`"use client"`) :

- `toFlow(graph)` projette le twin vers les formes `@xyflow/react` (`Node[]`/`Edge[]`) ; `nodeStyle(kind)` style chaque type de nœud via les **tokens CSS** (ADR 0010, jamais de hex) — le `gate` bordé `--primary`, la `decision` en tireté, les bornes arrondies, la branche `deny` en `--destructive`.
- React Flow est **uncontrolled** (`defaultNodes`/`defaultEdges`) : React Flow possède le drag. Le composant est wrappé dans `ReactFlowProvider` (`PipelineControls`) pour utiliser `useReactFlow().setNodes` — le **déplacement déterministe par bouton** déplace impérativement `w0` à `{x:160,y:0}` puis remonte la proposition ; le **déplacement souris** remonte la position au commit (`onNodesChange`, `c.type === "position" && c.dragging === false`).
- L'**édition proposée** vit dans un état découplé `proposed: Record<id, NodePos>` (jamais le store interne de React Flow). L'indicateur « un nœud a-t-il bougé ? » est CALCULÉ : le graphe affiché `= proposed.reduce(moveNode, base)`, puis on cherche un nœud dont la position diffère de `base` (`data-moved`, `v2-wf-proposed-pos`). **Réinitialiser** vide `proposed` et remonte React Flow (`key={flowKey++}`) pour reprendre le layout d'origine. Rien n'est jamais écrit (le mur §2).

**Les pages** : `app/v2/workflows/page.tsx` (l'index — liste `WORKFLOWS`, badge PASS/FAIL via `verdict`, lien vers `[wf]`), `app/v2/workflows/[wf]/page.tsx` (résout `workflowBySlug`, `notFound()` sur slug inconnu, `generateStaticParams` = `workflowSlugs()`, passe les strings i18n au client). **Reachability** : lien `v2-grille-gesture-workflows` depuis `/v2/grille` (le niveau operation), clé i18n `v2Grille.gestureWorkflows`. Namespace bilingue `v2Workflows` (FR + EN), ADR 0011.

## Méta

- **Determinism-first (CLAUDE.md §6/§8).** Tout ce qui peut être une fonction pure l'EST : la projection du pipeline (`workflowGraph`), le déplacement (`moveNode`), le décompte (`nodeKindCounts`), le routage (`workflowSlug`/`workflowBySlug`) — code, jamais LLM. React Flow n'est que du **rendu** ; XState n'entre même pas (pas de curseur ici, contrairement à WB2-12 — le pipeline est statique, le seul état est le *layout proposé*). Le miroir de reproductibilité (`lib/v2/workflows.test.ts`, fast-check + fixtures) épingle : graphe déterministe (deux appels identiques), pipeline bien formé (un `start`, ≥ 1 `end`, le gate suivi d'une décision branchée allow/deny), la branche deny → `end{denied}` (§93), cohérence des arêtes, ids uniques content-adressés, et `moveNode` pure & immuable (property : déplacer ne change QUE la position du nœud visé).
- **Réutilisation, pas de fork (ADR 0007).** Le twin ne réinvente pas l'exécution : il réutilise `frames`/`verdict` de WB2-12, qui réutilisent l'interpréteur S10 `lib/operation.ts` (`run`, `CREATE_ORDER`). WB2-13 n'ajoute QUE la **re-projection** des frames en pipeline branché — la vérité du déroulé reste l'interpréteur. Le registre `WORKFLOWS` réutilise directement `FIXTURES`.
- **Le mur (§2).** Afficher + déplacer = LECTURE/PROPOSITION. L'édition proposée est un layout local (état React découplé) ; `moveNode` est immuable ; aucune route d'écriture n'existe. L'e2e surveille le réseau (`POST/PUT/PATCH/DELETE`) et exige zéro écriture.
- **WB2-12 vs WB2-13.** WB2-12 = la vue **linéaire exécutable** (rejeu pas-à-pas, events qui s'émettent, machine XState). WB2-13 = la vue **structurelle** (le pipeline branché, étape/gate/décision, édition de layout proposée). Même fixture, deux projections — additif, anti-overwrite §9.

## Méta-méta

- **Pourquoi un twin séparé et non une option de l'écran WB2-12 ?** Parce que les deux répondent à des questions différentes (« qu'est-ce qui s'émet, et dans quel ordre ? » vs « comment le flux se ramifie ? ») et que séparer maintient chaque twin PUR et minimal. Le pipeline est une **fonction de la fixture**, donc il appartient à `lib/v2/` (testable seul, sans DOM) — l'écran n'est qu'une projection.
- **Pourquoi React Flow uncontrolled + un état proposé découplé ?** Un mode *controlled* (nodes pilotés par l'état React) entre en conflit avec le drag interne de React Flow (réinitialisations de position, courses de rendu). En laissant React Flow posséder le drag (`defaultNodes`) et en n'OBSERVANT que les positions (au commit) dans un état `proposed` séparé, on garde l'indicateur « moved » **calculé** par le twin pur (`moveNode`) tout en laissant l'interaction fluide. Le mur tient sans effort : l'état proposé n'est jamais persisté.
- **Pourquoi dessiner les DEUX branches même quand le scénario passe (ou refuse) ?** Parce qu'un pipeline est une **structure**, pas un chemin. Montrer seulement la branche prise cacherait la garde. La branche deny est toujours présente (et l'invariant le prouve), exactement comme le miroir d'un workflow prouve le comportement complet, pas un cas isolé.
- **La limite assumée (OpenQuestion).** L'« édition proposée » s'arrête au layout : déplacer un nœud ne PROPOSE pas encore une *modification du workflow lui-même* (ajouter/retirer une étape) via une idée → miroir → /goal. C'est par conception (le mur), et ce sera le rôle des étapes AI Lab (WB2-15+) où une proposition de structure passe par le ChangeSet. Aujourd'hui, déplacer ne fait que ré-agencer la lecture.

## Place dans le cliquet KRD

WB2-13 est une **dent du cliquet de l'outil** : il **lit** un workflow gelé (la fixture N2, §S10) et le projette en pipeline branché, sans écrire aucune vérité — déplacer un nœud reste une **édition proposée immuable** (le mur). Sa construction a cliqueté red → green — le miroir `lib/v2/workflows.ts` (fast-check sur `workflowGraph`/`moveNode`, les deux branches allow/deny toujours dessinées) rouge d'abord, puis vert, plus l'e2e de déplacement. Il **réutilise** la phase stable de WB2-12 (`frames`/`verdict`, donc l'interpréteur S10) et **laisse** une phase stable où le pipeline complet est lisible, branches comprises. La propagation d'une vraie modification de structure reste, par conception, le chemin idée → miroir → /goal des étapes AI Lab.
