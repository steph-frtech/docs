### Le réducteur pur

`front/web/lib/env-binding-cockpit.ts` — zéro I/O, zéro horloge, zéro LLM, et **zéro fork** : il compose les contrats publiés des étapes amont.

- `validateDraft(d)` : `validateDatastore` (DP06, la A1 verbatim) → datastores autorisés déclarés → ensemble clos `NETWORKS` (`traefik_default|default|managed`) → `classifyLiteral` (DP08) sur le `url_pattern` (le `localhost_literal` reste légal pour `local` seulement — la forme de la table déclarée) ;
- `proposeBinding(d)` : matérialise le binding effectif (les `allowed_datastores` restent déclarés — les élargir est idée → miroir → /goal), id = sha256 des octets canoniques (`records.Canonicalize`/`Hash`, motif S02), enveloppe = le type S20 `ChangeSet` de `lib/changeset.ts` **réutilisé tel quel** ;
- `approveBinding(cs)` : `verifyProposal` (anti-tamper — re-calcule l'adresse, refuse `PROPOSAL_ADDRESS_MISMATCH`) puis `apply` **de la machine S20** (seul un DRAFT applique), `appliedAt` = l'estampille déterministe `phase-cockpit+1` (le jumeau pur ne lit jamais d'horloge) ;
- `effectiveBindings` / `resolveWith` / `cockpitMatrix` / `hashCockpitMatrix` : la table DP06 superposée des deltas APPLIED, re-résolue par le jumeau paramétré-par-binding de `resolveConnection` — la parité ∀ (loi 1) et l'épingle du cockpit vide (loi 2) garantissent que c'est LE calcul DP07 ;
- `sensorStatus()` : re-`sense` de l'arbre émis canonique DP08 + l'adresse du verdict — le bac à sable action-capable (injecter/retirer/mesurer) reste sur `/endpoints-fitness` (l'écran de DP08).

## Méta

- **La verticale DP06→DP09 se referme en un seul écran.** DP06 a déclaré, DP07 a résolu, DP08 a surveillé — DP09 ne crée presque aucun calcul neuf : il **compose** les quatre contrats (la A1, la résolution, le classifieur, l'enveloppe S20) et ajoute la seule pièce manquante, la porte d'édition légale. Le coût marginal d'un cockpit est faible précisément parce que chaque étape amont a publié un contrat pur.
- **La parité ∀ remplace la duplication interdite.** `resolveWith` ressemble à un fork de `resolveConnection` — il ne l'est pas, parce que la loi 1 épingle l'équivalence sur tout le domaine déclaré et la loi 2 épingle l'adresse Go au cockpit vide. Quand on ne peut pas éditer le code d'une autre étape, on **prouve l'identité** au lieu de la promettre.
- **L'anti-tamper est une adresse, pas une session.** Entre propose et approve, l'enveloppe voyage par le formulaire (l'écran reste sans état serveur) ; ce qui empêche l'altération n'est pas un stockage mais le re-calcul de l'adresse de contenu — le motif content-addressed (S02) appliqué au flux d'approbation lui-même.

## Méta-méta

- **« Tout se fait par écran » et « le mur » ne se négocient pas l'un contre l'autre.** La tentation classique est de sacrifier l'un : un écran read-only (capacité headless) ou un écran qui écrit (mur percé). La forme propose → ChangeSet → approbation est la **troisième voie systématique** — et DP09 la rend littéralement visible : le bouton qui essaie d'écrire le Kernel existe à l'écran, et montre son refus.
- **Un refus est une pédagogie.** Chaque porte refuse avec un code clos + un message qui nomme le chemin légal (« élargir l'ensemble est idée → miroir → /goal »). Le cockpit enseigne le KRD à son utilisateur à chaque erreur — le BlockReason actionnable comme interface, pas comme exception.
- **OpenQuestions.** (1) L'apply réel (écrire le binding dans le schéma `changesets` Postgres et faire avancer la tête) reste porté par la porte changeset/CLI — le cockpit applique dans le bac à sable et retourne l'enveloppe exacte ; le câblage bout-en-bout au truth-store est l'affaire des étapes DP aval (DP12/DP13 activent les outils MCP stack.*). (2) Le miroir vitest est matérialisé fichier (exception bootstrap S06 inchangée). (3) Le suivi Linear de l'étape n'a pas pu être poussé depuis l'exécuteur (MCP linear-server non authentifié dans cette session) — à refléter au prochain passage authentifié.
