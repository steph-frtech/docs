## Implémentation

**Le twin `lib/v2/deploy.ts`** ajoute la chaîne **specs → app web → prod** (ADR 0052) par **réutilisation** du twin émetteur WB2-21 (`lib/v2/emetteurs.ts`, lui-même ré-export byte-identique de S35) — aucun émetteur recodé :

- **Réutilise & ré-exporte** (depuis `./emetteurs`) : `emitView(entity)`, `appPreview(entity)`, `entityId(e)`, `isBlockedView`, `ENTITY_CASES`, et les types `Entity` / `EmitView` / `AppPreview` / `BlockReason` / `EntityCase`.
- **Ajoute** (le neuf de WB2-22) :
  - `BASE_DOMAIN = "sagedesk.fr"` : le domaine de base (le même que l'AI Lab, ADR 0052). `DEFAULT_RATE_LIMIT = 5` : le quota de déploiements par fenêtre, **déclaré** au-dessus de la ligne.
  - `deployGate(ctx: DeployGateContext) → GateVerdict` : **la parenthèse sécurité fermée**. Une fonction **pure, totale, fail-closed et ordonnée** : `!authenticated` → un `GateVerdict` refusé avec le `BlockReason` `DEPLOY_GATE_UNAUTHENTICATED` ; sinon `deploysInWindow >= rateLimitPerWindow` → refus `DEPLOY_GATE_RATE_LIMITED` ; sinon `{allowed:true, reason:null}`. Chaque refus porte `code` / `severity:"blocking"` / `explanation` / `how_to_fix[]` (le shape `BlockReason` de S13).
  - `CONTAINER_SERVICES` : le jeu **clos & déclaré** de services docker-compose — `{postgres, postgres:16, db}`, `{app, aidos/emitted-app, web}`, `{traefik, traefik:v3, ingress}`.
  - `subdomainOf(table) → string` : la dérivation **totale** du sous-domaine — minuscules, `[^a-z0-9]+ → "-"`, sans tiret de bord ; une table vide/dégénérée → `"app"` (jamais un sous-domaine vide). Le twin de `alphashop → alphashop.sagedesk.fr`.
  - `buildDeployPlan(entity, gate: GateVerdict) → DeployPlan | BlockReason` : ordonné & **fail-closed**. (1) Si `!gate.allowed` → renvoie `gate.reason` (le `BlockReason` de la garde, **aucun plan**). (2) `view = emitView(entity)` ; un AST malformé → le `BlockReason` de l'émission. (3) Le plan content-adressé : `appBytes = view.targets.map(t => t.bytes).join(" ")`, `appHash = hash32(appBytes)` (FNV-1a 32-bit, le même schéma que S35), `planId = "d-" + appHash`, `route = { subdomain: subdomainOf(preview.table), baseDomain: BASE_DOMAIN, host, url: "https://" + host }`, `preview = appPreview(entity)`. Renvoie `{entity, sourceHash, appHash, planId, view, services, route, preview}`.
  - `reDeployStable(entity, gate, rounds = 16) → ReDeployReport` : la **preuve** de re-planification reproductible. Calcule `first = buildDeployPlan(...)` ; un plan bloqué → `{stable:false, planId:"", …}` (fail-closed). Sinon recalcule `rounds` fois et compare `planId` / `route.url` / `appHash` ; `stable` est `false` au moindre écart. Renvoie `{rounds, planId, url, appHash, stable}`.
  - `isBlockedPlan(x) → x is BlockReason` : le garde de type, discrimine sur le champ `code` (présent seulement sur un `BlockReason` ; un `DeployPlan` n'en a jamais).

**L'écran `app/v2/deploy/`** (route neuve, aucune route existante touchée) :

- `page.tsx` (Server Component) : charge le namespace `v2Deploy` via `getTranslations`, projette les clés en `strings`, monte `<DeployClient cases={ENTITY_CASES} t={strings} />`. En-tête + note du mur (`v2-deploy-wall-note`) + note de déterminisme.
- `DeployClient.tsx` (`"use client"`) : états `selectedId` / `authenticated` / `deploysInWindow` / `deployed` / `reDeployed`. Mémos : `gate = deployGate({authenticated, deploysInWindow, rateLimitPerWindow: DEFAULT_RATE_LIMIT})`, `result = deployed ? buildDeployPlan(selected.entity, gate) : null`, `plan` / `blocked` dérivés par `isBlockedPlan`, `report = reDeployed ? reDeployStable(selected.entity, gate, 16) : null`. `onDeploy()` met `deployed=true` et, si la garde passe, incrémente `deploysInWindow` (le rate-limit avance). Actions : `v2-deploy-auth-toggle` (porte `data-authenticated`), `v2-deploy-sample-<id>`, `v2-deploy-deploy`, `v2-deploy-redeploy`, `v2-deploy-reset`. Rend : `v2-deploy-blocked` (porte `data-code`, + `v2-deploy-blocked-code` + `how_to_fix`) quand la garde refuse ; sinon `v2-deploy-plan` avec `v2-deploy-plan-id`, `v2-deploy-url` (porte `href` + `data-host`), `v2-deploy-services` (un `v2-deploy-service-<name>` par service), `v2-deploy-preview` (une ligne `v2-deploy-preview-<name>` portant `data-nullable` / `data-pk`), et `v2-deploy-redeploy-report` (porte `data-stable`). ## Méta

**Pourquoi `deployGate` est une fonction et pas un middleware deviné (§8).** La parenthèse sécurité d'ADR 0052 — « auth + rate-limit » — est exactement le genre de règle qu'on serait tenté de confier à un agent (« est-ce que ce déploiement est sûr ? »). C'est interdit : la sûreté ici se **vérifie**, elle ne se **juge** pas. `deployGate` inspecte **deux faits booléens/numériques** (authentifié ? sous le quota ?) et tranche déterministiquement. L'ordre est **explicite** (auth d'abord) : un appelant anonyme se voit refuser pour la **bonne** raison, même s'il a aussi dépassé un quota fictif. Le test `(6)` verrouille cet ordre. Le verdict est un `BlockReason` **actionnable** (`how_to_fix`), pas un simple `false` — l'utilisateur sait quoi faire.

**Le plan est content-adressé, donc reproductible par construction.** `planId = "d-" + hash(octets de l'app émise)`. L'URL dérive de la **table**, qui dérive de l'**entité**. Il n'y a **aucune** source d'entropie : pas d'horloge, pas de compteur global, pas d'aléa. La même entité (même garde) → le même plan, à l'octet près. Le test `(1)` le prouve sur des milliers d'entités aléatoires ; `reDeployStable` le rejoue. C'est ce qui distingue un **plan** (déterministe, vérifiable) d'un **déploiement impératif** (un effet de bord opaque) : on peut comparer deux plans et savoir s'ils sont identiques **avant** de toucher la machine.

**`buildDeployPlan` réutilise l'émetteur, il ne ré-émet pas (ADR 0007).** L'app que le plan déploie est **exactement** `emitView(entity)` — les mêmes octets DDL/Go/TS que `/v2/emetteurs`. L'`appHash` est calculé **sur ces octets**. Donc le plan déploie **ce que l'écran émetteur montre**, sans seconde sémantique de rendu. Le test `(13)` épingle `plan.view ≡ emitView(entity)`. C'est la cohérence de bout en bout : une vérité (l'entité) → des projections (S35) → une app émise (WB2-21) → un plan de déploiement (WB2-22), chaque maillon une fonction pure.

## Méta-méta

**WB2-22 ferme une parenthèse sécurité — c'est de la dette honnête réglée, pas de la fonctionnalité.** L'ADR 0052 avait **écrit noir sur blanc** que le bouton « Déployer » était dangereux non gaté (« doit être gaté avant une vraie exposition »). C'était une **limite honnête** consignée, pas masquée. WB2-22 ne fait pas semblant d'avoir « ajouté la sécurité » : il **transforme cette limite déclarée en garde testée**. La parenthèse était une dette ; le `deployGate` fail-closed + son miroir la remboursent. C'est le cycle d'AIDOS : on **déclare** ce qui manque (OpenQuestion / limite d'ADR), puis un step **le ferme** avec une preuve. Une capacité puissante n'est jamais livrée nue : elle est livrée **gatée**, et la garde a son miroir de panne (un appelant anonyme **doit** être refusé — c'est testé).

**Le déploiement reste sous la ligne : émettre + planifier n'écrit aucune vérité.** On pourrait croire que « déployer en prod » franchit forcément le mur. Non. Les **entités** sont la vérité (au-dessus de la ligne) ; l'app émise, son conteneur, son URL sont des **projections** — régénérables, jetables, content-adressées. Déployer, c'est **projeter** une vérité vers un système qui tourne, jamais **modifier** la vérité. L'e2e le prouve avec `writes === []`. Et **changer** la source — ajouter une entité, modifier un champ — ne se fait pas depuis l'écran de déploiement : ça **propose** un `/goal`. L'écran déploie ce qui **est** ; c'est l'humain qui change ce qui **doit être**.

**Une source → une app en ligne : la promesse d'AIDOS rendue tangible.** WB2-21 montrait les fichiers ; WB2-22 montre l'**adresse**. C'est l'aboutissement visible de la chaîne « specs → prod » : à partir d'une intention typée (une entité), on obtient une **vraie app web, en https, joignable** — déterministiquement, sans une ligne de code écrite à la main, et **sans jamais laisser un anonyme appuyer sur le bouton**. La boucle est complète et **sûre** de bout en bout.

## Place dans le cliquet KRD

WB2-22 est **le dernier cran de la chaîne** : une dent gravée (l'entité) → émise (WB2-21) → **déployée** en prod (ADR 0052). Le plan de déploiement est content-adressé (`planId = "d-" + hash(octets de l'app émise)`), donc **reproductible** comme une dent : même entité → même plan, à l'octet près (`reDeployStable`). L'écran reste sûr et au-dessus du mur : la garde `deployGate` est fail-closed et ordonnée (auth d'abord, puis rate-limit), et la proposition passe par /goal (data-proposes=goal). Sa construction a cliqueté red → green — le miroir `lib/v2/deploy.ts` (fast-check, 16 tests : plan reproductible, garde fail-closed, URL dérivée de la table) rouge d'abord, puis vert, plus l'e2e « déploiement → URL live + le bouton refuse sans auth ». Il **réutilise** le twin émetteur WB2-21 et **clôt** la verticale V2 : de l'intention (WB2-03) à l'app en ligne, chaque dent prouvée par son miroir.
