## Implémentation

### Le paquet — `back/runtime/connectorinfra` (3 fichiers) + un blockreason additif

DP23 pose l'**infra de connecteurs de l'app émise** en quatre fragments StackManifest déterministes, **calqué sur** DP15/DP16/DP18 (le motif « fragments below-the-line par projet ») et **réutilisant** S73/DP16 (async) + DP20 (connector) **sans forker**. Tâche **backend-only** ; le mur tient (aucun GRANT).

Trois fichiers neufs (anti-overwrite respecté, §9) :

- `back/runtime/connectorinfra/connectorinfra.go` — l'implémentation : `SubstrateConnectorInfraFragments`, `Keys`, `CanonicalFragment` / `HashFragment`, le `ServiceFragment` local, `RouteTool` / `ToolRegistry` / `Decision`, et `RealizeInboundWebhook` / `InboundWebhook`.
- `connectorinfra_property_test.go` — le **miroir property ∀** (rapid), **écrit RED-first**.
- `connectorinfra_fixture_test.go` — le **miroir fixture N2** (`state → command → events`), **écrit RED-first**.

Et **un** fichier modifié — `back/runtime/blockreason/blockreason.go` (modification **additive**) : un nouveau code d'erreur

```go
CodeToolNotRegistered Code = "TOOL_NOT_REGISTERED"
```

avec son entrée au registre (severity **blocking**, explanation **FR**, **3** entrées `how_to_fix`) et son ajout à `codeOrder`. Le **miroir property existant** de `blockreason` le couvre **automatiquement** : il tire de `Codes()`, donc `TestEveryCodeHasNonEmptyResolutionPath` et `RenderRoundTrips` restent **verts** avec le nouveau code (un code n'existe que s'il porte un chemin de résolution non vide).

### `SubstrateConnectorInfraFragments` — les quatre fragments byte-stables

```go
func SubstrateConnectorInfraFragments(
  projectID string,
  env scope.Environment,
) ([]ServiceFragment, error)
```

Elle rend les **quatre** fragments — un jeu **clos** — sous le profile **`connectors`**, role **`connector`**, **image vide** (le code est **émis**, l'image *built* n'est pas pinnée), healthcheck **`/health`**, et un **volume bind isolé par le token DP15** (`datafragments.IsolationToken`) : deux projets A et B sont **byte-distincts**. Sur un `env` inconnu, elle **fail-closed** (`UNKNOWN_ENVIRONMENT`). Le câblage des dépendances est gravé : **mcp-gateway** `dependsOn [tool-registry]`, **webhook-gateway** `dependsOn [nats]`.

```go
type ServiceFragment struct {
  Key       string             // mcp-gateway | connector-registry | tool-registry | webhook-gateway
  ProjectID string
  Service   stackmanifest.Service // {Name, Role="connector", Image="", InternalPort, Profile="connectors", Healthcheck, DependsOn}
  Volumes   []stackmanifest.Volume // [{Name=key-<token>, DeviceVar=KEY_<TOKEN>_DATA_PATH}]
}

func (ServiceFragment) WritesTruth() bool { return false } // le mur (§2)
```

`ServiceFragment` est une struct **LOCALE** (pas un alias), exactement comme `appservicefragments` (DP18). Sa méthode `WritesTruth()` rend **toujours `false`** — le mur, asserté à la source. `Keys()` rend l'ordre canonique `[mcp-gateway, connector-registry, tool-registry, webhook-gateway]`. `CanonicalFragment(f)` / `HashFragment(f)` sont les **oracles S02** (`records.Canonicalize` / `records.Hash`) : un fragment re-émis est **byte-identique**.

### `RouteTool` — le MCP-Gateway, un routage pur set-membership

```go
type ToolRegistry struct {
  ProjectID string
  Tools     map[string]struct{}
}
func NewToolRegistry(projectID string, names []string) ToolRegistry

type Decision struct {
  Admitted bool
  Code     blockreason.Code
}

func RouteTool(registry ToolRegistry, toolName string) (Decision, *blockreason.BlockReason)
```

`RouteTool` est le routage du **MCP-Gateway** — **pur**, par **appartenance ensembliste** (*set-membership*), **zéro LLM**, **fail-closed** :

- `toolName` **dans** `registry.Tools` ⇒ `Decision{Admitted: true}`, `*BlockReason = nil` ;
- `toolName` **absent**, **ou** registre **vide** ⇒ `Decision{Admitted: false, Code: TOOL_NOT_REGISTERED}` + le `*BlockReason` rendu.

Le registre est un simple **set** de noms d'outils ; le routage est un **test d'appartenance**, pas une interprétation. C'est le déterminisme-first (§6/§8) : router un outil est une décision **pure**, donc **code**, jamais un agent. Un registre vide refuse **tout** (la propriété `L6EmptyRegistryRefusesEverything`).

### `RealizeInboundWebhook` — webhook entrant → opération async (réutilise S73/DP16)

```go
type InboundWebhook struct {
  Source    string
  Operation string
  Payload   map[string]any
}
var ErrWebhookOperationMismatch error
type DispatchEvent = asyncfragments.DispatchEvent // réutilisé, jamais redéfini

func RealizeInboundWebhook(
  webhook InboundWebhook,
  op operation.Operation,
  async operation.Async,
  outbox operation.Outbox,
  sink operation.Sink,
) ([]DispatchEvent, error)
```

Le **Webhook-Gateway** transforme un webhook entrant en **opération asynchrone**, dans l'ordre :

1. **match l'op** — `webhook.Operation` doit correspondre à `op` ; sinon **refusé** (`ErrWebhookOperationMismatch`, fail-closed) ;
2. **`ValidateAsync`** (la validation S73) ;
3. **écrit les effets dans l'outbox S73** (via `asyncfragments.OutboxWriter`) ;
4. **Dispatch** — délivrance **exactly-once** (relative), portée par une **clé d'idempotence content-addressed** : un rejeu du même webhook ne produit **aucun doublon**.

C'est **S73/DP16 réutilisé verbatim** : le `DispatchEvent` est `asyncfragments.DispatchEvent` (un alias de type, pas une copie), l'outbox est l'outbox de S73, la garantie exactly-once est celle de DP16. **Aucun fork async** — il n'existe **qu'une** mécanique d'outbox + dispatch dans AIDOS.

## Méta

- **Le miroir property prouve les invariants de l'infra de connecteurs.** Écrit RED-first, il mesure que les fragments sont **reproductibles** (`L1ByteIdentique` — re-émission byte-identique), **clos** (`L2PaletteClose` — quatre, pas un de plus), **sans gate d'env caché** (`L3NoEnvGate` — l'env ne fait que fail-closer sur l'inconnu), **isolés par projet** (`L4Isolation` + `L5SharedToken` — le token DP15), et que le **routage est pur** (`L6RouteToolIsPureSetMembership` + `L6EmptyRegistryRefusesEverything`). C'est le déterminisme-first (§6/§8) : émettre un fragment, le hacher, router un outil sont des **fonctions pures**, donc du **code**, jamais un agent — le routage MCP-Gateway n'invite **aucun** LLM.

- **Le miroir fixture épingle les sept formes d'action comme `state → command → events`.** `ConnectorInfraPaletteIsFour` et `KeysAreTheClosedSet` ancrent le jeu clos ; `RegisteredToolRoutes` / `UnregisteredToolRefused` ancrent le routage fail-closed ; et le trio webhook — `InboundWebhookTriggersAsyncOp`, `InboundWebhookReplayNeverDuplicates`, `WebhookForWrongOperationRefused` — ancre la transformation webhook→op async avec sa garantie exactly-once. Chaque cas est un workflow N2 (`state` = le registre / le webhook + l'op + l'outbox, `command` = `RouteTool` ou `RealizeInboundWebhook`, `events` = la décision admise/refusée ou les `DispatchEvent` produits). Un webhook rejoué ne produit **aucun** doublon — la fixture le prouve, ce n'est pas une promesse.

- **Réutiliser plutôt que réinventer (ADR 0007), sur l'async et le connector.** DP23 n'invente **aucune** mécanique d'async : il **réutilise** S73 (l'outbox + le pattern exactly-once) et DP16 (`asyncfragments.OutboxWriter`, `asyncfragments.DispatchEvent`) **verbatim** — `DispatchEvent` est un alias de type, jamais une copie. De même, `ServiceFragment` reprend le motif **local** de DP18 (`appservicefragments`), et l'isolation par projet réutilise le `datafragments.IsolationToken` de DP15. Le `blockreason` n'ajoute qu'un code, couvert automatiquement par le miroir property existant (qui tire de `Codes()`). Un seul outbox, un seul `DispatchEvent`, un seul token d'isolation dans tout AIDOS.

## Méta-méta

- **L'infra de connecteurs est de l'infra émise below-the-line — jamais une vérité Kernel.** Le mur (§2) tient avec une ligne nette : chaque fragment porte `WritesTruth() == false`, et le paquet n'écrit **rien** dans `kernel`, `mirrors` ou `fitness`. C'est de l'**infra de l'app construite**, pas un truth-store. L'agent n'a **aucun GRANT** pour graver une vérité ; DP23 émet les briques qui font tourner les connecteurs de l'app émise, il ne crée aucune vérité d'AIDOS.

- **L'app émise reçoit SES PROPRES MCP + Skills, distincts d'AIDOS (ADR 0040 + 0009).** La règle est structurelle, pas une convention : les MCP de l'app construite **ne sont pas** ceux d'AIDOS. Un connecteur de l'app, par sa porte d'entrée (le MCP-Gateway), ne peut atteindre **que** les outils enregistrés **de l'app** — jamais les outils de l'OS. La règle « un op = un outil MCP » (ADR 0009) vaut pour les deux plans : chaque opération de l'app émise est exposée comme un **outil MCP additif** distinct, derrière le MCP-Gateway, qui n'admet que l'enregistré (`TOOL_NOT_REGISTERED` sur tout le reste). C'est l'ADR 0040 gravé en infra : les MCP + Skills de l'app émise sont **additifs et distincts** d'AIDOS.

- **Réutiliser S73/DP16 + DP20 est de l'anti-duplication — et chaque connecteur exécutable est load-bearing.** Deux plans d'async qui forkeraient chacun son outbox divergeraient un jour (un fix de doublon corrigé d'un côté, pas de l'autre). En **réutilisant** la même mécanique (l'outbox + l'exactly-once de S73, le `DispatchEvent` de DP16, le connector de DP20, le token d'isolation de DP15), DP23 garantit qu'il n'existe **qu'une** mécanique d'async et **qu'un** motif de fragment dans AIDOS — l'anti-duplication du déterminisme-first. Et la loi de complétude (Mandat A, §5) veille : une infra sans miroir serait un **monstre**. L'enjeu porteur de DP23 est que **chaque connecteur de l'app émise soit exécutable et gouverné** — c'est *load-bearing* : sans cette infra (la porte unique du MCP-Gateway, les registries, le webhook→op async), les connecteurs de DP20-DP22 resteraient des sources sans moteur, et une source sans moteur ne fait rien.
