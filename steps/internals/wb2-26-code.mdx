## Implémentation

**Le twin pur `lib/v2/code-graph.ts`** — **CLIENT-SAFE** (aucun import `typescript` ; importable par n'importe quel composant client) :

- `CodeNode` : `{ id, kind: "file"|"class"|"function"|"method" (jeu clos), name, file, span: {start, end} (lignes 1-based inclusives), version (hash content-adressé du corps — change ssi le texte change), parentId (la contenance method→class→file, même forme « liste plate + parentId » que l'arbre composes / kernel-tree) }`.
- `CodeEdge` : `{ from, to, kind: "calls"|"imports", confidence: "extracted"|"inferred" }` — le tag de **confiance** vient de graphify : `extracted` = prouvée par l'AST dans le fichier, `inferred` = résolue inter-fichiers via les imports.
- `validateCodeGraph(nodes, edges)` : **fail-closed** — ids uniques, parents existants, arêtes membres, spans cohérents ; un graphe douteux est refusé, jamais accepté par défaut.
- `impactOf(nodes, edges, id) → ImpactItem[]` (`{id, depth}`) : la **vague de rouge (S22) au grain code** — la clôture des **dépendants inverses** (le `rdeps` de Bazel) par BFS **ordonné** (déterministe même sur cycles, termine toujours), **plus la remontée de conteneur** (le fichier d'un impacté est touché), self exclu.
- `actionKey(nodes, edges, id)` : la clé d'invalidation **à la Bazel** — hash(version propre + versions des deps **directes**). Si rien de tout cela n'a changé, la clé est identique : l'invalidation est **fine**, jamais globale.
- `diffGraphs(beforeN, beforeE, afterN, afterE) → {changed, added, removed, redWave}` : deux instantanés extraits du source → les symboles changés (version différente), ajoutés, retirés, et la **redWave** des appelants des changés.
- `codePath(nodes, id) → CodeNode[]` : le chemin racine→soi (fichier → classe → méthode) — l'adresse de descente.
- `anchorSymbols(tree, nodes, edges, requirementPath)` : l'**ancrage requirement→code** — pour un chemin de l'arbre `composes` (résolu via `nodeByPath`, réutilisation WB2-03), un **score lexical déterministe** classe les symboles candidats (score > 0 seulement). Une **suggestion** ; l'humain tranche (§49).
- `godNodes(nodes, edges, k)` : les k symboles au plus fort **degré entrant** — les points chauds (graphify).

**L'extracteur `lib/v2/code-extract.ts`** — importe **`typescript`** (l'API compilateur, déjà dans l'arbre : réutilisation ADR 0007 ; graphify utilise tree-sitter, même principe — AST **local**, zéro appel réseau). **SERVEUR/TEST SEULEMENT**, jamais importé par un composant client :

- `extractFromSource(filePath, sourceText) → ExtractedFile` : **PURE** (texte → données, zéro E/S ; `ts.createSourceFile` est tolérant aux erreurs et ne jette pas) — relève fonctions, classes, méthodes (spans + versions), les appels intra-fichier (`extracted`), les imports et les appels vers des noms importés (`PendingCall`, à résoudre).
- `assembleGraph(files) → {nodes, edges}` : **PURE** — la résolution inter-fichiers des chemins relatifs (`.ts`/`.tsx`) sans `fs` ; un import **non résolu** ne produit **aucune arête pendante** (fail-closed) ; les arêtes inter-fichiers sont `inferred`.

**Le miroir** (Vitest + fast-check) : `lib/v2/code-graph.test.ts` (**17 tests**) + `lib/v2/code-extract.test.ts` (**10 tests**) = **27/27 verts**. Il épingle : la validation fail-closed ; l'impact **total / membre / déterministe / terminant sur cycles** ; la profondeur de vague ; la clé Bazel (sensible au corps **et** aux deps directes, insensible au reste) ; le diff (graphes identiques → vide ; corps changé → la vague des appelants) ; l'ancrage requirement→code ; les god nodes ; et côté extracteur la **reproductibilité** (même texte → même graphe, même version).

**L'écran `/v2/code`** (`app/v2/code/page.tsx` + `CodeClient.tsx`, enregistré dans `lib/v2/screens.ts` — la nav complète WB2-25 reste verte) : la page serveur est la **seule couche impure** (fs) — elle **ré-extrait le graphe du source réel à chaque rendu** (le périmètre : `lib/v2/*.ts`, les twins purs eux-mêmes — collecte triée `readdirSync + sort`, reproductible), l'assemble, et le sérialise au client. Le client : le requirement (`v2-code-req`) → les ancrages (`v2-code-anchor`) ; l'arbre des fichiers (`v2-code-tree`) → le panneau symbole (`v2-code-pane` : version, span de lignes, clé Bazel) ; la simulation d'impact (`v2-code-impact-btn` → `v2-code-impact` / `v2-code-impact-item`, profondeurs directe/transitive, reset) ; les god nodes (`v2-code-god`) ; le graphe 3D (`v2-code-graph-3d`, ADR 0053) ; et l'ouverture **VS Code** (`v2-code-vscode`) via `vscode://file<chemin absolu>:<ligne de début>:1` — la ligne exacte. Bilingue (namespace dédié, fr/en), thème ccup (ADR 0010/0011).

## Méta

**Pourquoi deux twins et pas un (la frontière client/serveur).** L'API compilateur TypeScript pèse lourd et n'a rien à faire dans un bundle client. La coupe est **structurelle** : `code-graph.ts` (tout le **calcul** — impact, clé, diff, ancrage) est pur et client-safe ; `code-extract.ts` (la seule **lecture du source**) importe `typescript` et vit côté serveur/test. L'écran consomme le graphe **sérialisé**. La frontière n'est pas une convention de prudence : un import de l'extracteur depuis un composant client casserait le build — la contrainte est mécanique.

**L'extraction est un parseur, jamais un LLM (§8).** « Comprendre quel code appelle quel code » sonne comme une tâche de compréhension — donc tentante pour un agent. C'est refusé : l'AST **prouve** les appels intra-fichier, la résolution d'imports **déduit** les appels inter-fichiers, et la différence est **affichée** (le tag `extracted`/`inferred`, l'honnêteté de graphify). Même texte → même graphe, prouvé par le miroir. Un LLM aurait des opinions ; un parseur a des faits — et quand il ne sait pas résoudre, il ne **fabrique rien** (aucune arête pendante, fail-closed).

**La version content-adressée est ce qui rend tout le reste possible.** Sans elle, « ce symbole a-t-il changé ? » exigerait de comparer des textes ; avec elle, c'est une comparaison d'empreintes. `actionKey` (corps + deps directes) en découle : l'invalidation à la Bazel n'est pas une optimisation, c'est la **forme calculable** de « quoi re-vérifier après cette modification ». Et `diffGraphs` en découle aussi : deux extractions, une comparaison d'empreintes, la vague. Tout le « quoi touche quoi » repose sur ce seul choix : **le hash du corps est l'identité de la version**.

**L'ancrage suggère, l'humain tranche.** `anchorSymbols` est un score lexical — délibérément simple, délibérément **pas** un embedding ni un agent. Il propose un classement ; il ne fige rien. Figer un ancrage requirement→code serait écrire une vérité (un lien dans le kernel) — c'est l'affaire d'une idée et d'un `/goal`, pas d'un score.

## Méta-méta

**La feuille n'était pas le fond.** ADR 0055 a établi que l'échelle fractale est une position dans un arbre qui pousse — mais l'arbre s'arrêtait là où le code commençait. WB2-26 montre que la **même structure** (contenance + adresses + identités content-adressées) continue **sous** la feuille : le fichier contient la classe qui contient la méthode, exactement comme la racine contient ses nœuds qui contiennent le besoin le plus fin (des positions topologiques — racine, feuille, profondeur `nN` — jamais des noms de niveaux, addendum ADR 0055). Ce n'est pas une analogie décorative : c'est la **même forme de données** (liste plate + `parentId`), les **mêmes gestes** (descendre, adresser, hasher), le **même calcul d'impact** (la vague de rouge). La fractale est réellement fractale — elle ne change pas de nature en changeant de grain.

**« Quoi touche quoi » est LA question du cliquet, posée au code.** Tout AIDOS repose sur « rien ne casse silencieusement ce qui précède » — et pour le garantir, il faut savoir ce qu'une modification **touche**. Au niveau des vérités, c'est la vague de rouge S22 ; au niveau du code, c'était un angle mort. WB2-26 le comble avec le même algorithme : les dépendants inverses, transitifs, calculés. Le jour où un hook ré-extraira le graphe à chaque écriture (OpenQuestion de l'ADR 0056), « modifier une fonction » déclenchera la même discipline que « modifier une vérité » : on saura, **avant** de casser, ce qui rougit.

**Réutiliser les yeux des autres (ADR 0007).** Rien ici n'est inventé : graphify a montré l'extraction AST locale, les tags de confiance et les god nodes ; Bazel a montré le content-addressing des actions, le `rdeps` et l'invalidation fine ; l'API compilateur TypeScript était déjà dans l'arbre. WB2-26 **compose** ces idées éprouvées dans la forme KRD (twins purs, miroir de reproductibilité, le mur) au lieu de réinventer un analyseur — le concept est neuf, chaque pièce est mûre.

## Place dans le cliquet KRD

WB2-26 grave la dent « **la descente continue sous la feuille** » : il consomme la phase stable laissée par WB2-25 (la nav complète, le registre des écrans — où `/v2/code` est déclaré, sans quoi la cohérence cardinale serait rouge) et par WB2-03/ADR 0055 (l'arbre `composes` vivant, que l'ancrage réutilise via `nodeByPath`). Sa construction a cliqueté red → green — le miroir (27 tests : fail-closed, impact déterministe et terminant sur cycles, clé Bazel, diff, ancrage, god nodes, reproductibilité de l'extraction) rouge d'abord, vert ensuite. C'est un cran du **cliquet-outil** : le code qui code AIDOS devient lisible par AIDOS — adressable (fichier/classe/fonction/ligne), versionné (content-adressé), impactable (la vague). Les OpenQuestions de l'ADR 0056 (le hook PostToolUse de ré-extraction continue, la persistance Postgres des instantanés pour le diff historique, l'extension Go via `go/ast`) sont l'exception bootstrap (§6) — documentées, jamais des échecs. Le mur reste intact : l'écran lit et simule ; figer un ancrage ou promouvoir un refactor de god node passe par idée → miroir → `/goal`.
