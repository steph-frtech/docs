## En une phrase

BA20 crée un **NOUVEAU rôle Postgres** `aidos_scheduler` — le seul à pouvoir transitionner un `RedWorkItem` (`open→claimed`) en écrivant exactement quatre colonnes de `runtime.red_work_queue` (`status`, `owner_agent`, `lease_until`, `lease_epoch`) et à SELECT `kernel.agent_layer` (lire les specs des couches-agent pour `MatchRole`, gap E4) — tandis que le rôle agent reste `INSERT+SELECT` only (le mur, inchangé). La file gagne une colonne `lease_epoch` monotone (le jeton de fencing, gap E2). Le miroir migration-roundtrip+GRANT prouve la posture end-to-end sur un vrai Postgres.

## Implémentation

La migration vit dans `back/migrations/scheduler_role_baseline.sql` ; le cœur pur dans `back/runtime/scheduler/scheduler.go`.

- **La migration (expand-contract, forward-only)** — elle (1) `ADD COLUMN IF NOT EXISTS lease_epoch BIGINT NOT NULL DEFAULT 0` + `CHECK (lease_epoch >= 0)` sur `runtime.red_work_queue` (le jeton de fencing ; 0 = jamais baillé) ; (2) crée le rôle `aidos_scheduler` (NOLOGIN, gardé) ; (3) lui donne SON UNIQUE porte d'écriture : `GRANT UPDATE (status, owner_agent, lease_until, lease_epoch) ON runtime.red_work_queue` — un GRANT *scopé colonne*, le moindre-privilège mécanique : il ne peut pas réécrire `target`/`reason`/`wave_id`/`dependencies`/`created_at` (l'identité immuable de l'item) ; (4) lui donne `SELECT ON kernel.agent_layer` (gap E4 : lire les specs pour `MatchRole`) ; (5) REVOKE tout INSERT/UPDATE/DELETE sur `kernel.agent_layer` + CREATE sur le schéma — l'assertion positive que l'ordonnanceur n'est PAS un 2ᵉ writer privilégié ; (6) re-state la posture S22 de l'agent (INSERT+SELECT, jamais UPDATE) pour être auto-suffisante et order-indépendante dans la suite Testcontainers. Elle n'ALTÈRE ni ne DROP rien (S04/S22/S52 intacts).
- **Le cœur pur `scheduler.Claim(item, owner, leaseUntil)`** — la transition `open→claimed` totale et déterministe : aucune horloge (`leaseUntil` est SUPPLIÉ), aucun rng, aucune I/O. Elle estampille `owner_agent`, `lease_until` et un `lease_epoch` BUMPÉ (`prev+1`, le jeton de fencing — une règle DÉCLARÉE, jamais apprise), et retourne l'item transitionné PLUS l'`AgentAssignment` épinglé au même epoch (statut `leased`). Elle REFUSE (erreur, jamais panic) un item non-`open`, un owner vide, un bail vide. L'`AgentAssignment` porte `LeaseEpoch` (gap E2) et — par construction — AUCUN champ `Version`/`Mirror` (un bail est un événement runtime, pas une couche).
- **`UpdateColumns`** — la constante Go listant les quatre colonnes transitionnables, le miroir côté code du GRANT scopé-colonne : le shell impur (BA22) ne peut écrire honnêtement que ces colonnes.
- **Le miroir migration-roundtrip+GRANT** (`migration_roundtrip_test.go`, Testcontainers, vrai Postgres) — le red set central : `TestEpochColumn_ExistsWithDefault` (la colonne existe, défaut 0, le CHECK refuse un epoch négatif) ; `TestSchedulerRole_Exists` (le rôle existe) ; `TestScheduler_ClaimsButAgentCannot` (l'ordonnanceur UPDATE `open→claimed`+epoch++, mais l'agent NE PEUT PAS — il garde son INSERT) ; `TestScheduler_ReadsAgentLayer` (gap E4 : l'ordonnanceur SELECT `kernel.agent_layer`) ; `TestScheduler_NoTruthWrite` (INSERT/UPDATE/DELETE sur `kernel.agent_layer` tous refusés — l'ordonnanceur n'est pas un 2ᵉ writer).
- **Le miroir de reproductibilité** — `scheduler_property_test.go` (rapid : `Claim` déterministe+total, bump d'epoch monotone, `open→claimed` only, exactement les 4 colonnes, `AgentAssignment` pas-une-couche) et son jumeau front `front/web/lib/scheduler.test.ts` (fast-check, 6 propriétés).
- **Le jumeau front** (`front/web/lib/scheduler.ts`) — `claim(item, owner, leaseUntil)` reflète `Claim` verbatim ; `agentCanTransition()` retourne toujours `false` (le mur projeté, fait structurel) ; `UPDATE_COLUMNS` reflète la constante Go + le GRANT.
- **L'UI action-capable** (`front/web/components/SchedulerSection.tsx`, section `scheduler-fencing` sur `/agents`) — « Claim (rôle ordonnanceur) » bound à `claim` (un bail sous la ligne, exécuté directement) : l'item passe `open→claimed`, le jeton 0→1, l'AgentAssignment s'affiche ; « Tenter le claim côté agent » montre `agentCanTransition() = false` (refusé en place, le mur). Thémé (ADR 0010), bilingue FR/EN (ADR 0011). L'e2e Playwright (`tests/e2e/agents.spec.ts`, bloc BA20) prouve les trois cas : contrôles présents (item `open`@0) ; claim ordonnanceur → `claimed`@1 + bail rendu ; claim agent refusé en place.

## Méta — pourquoi c'est construit ainsi

Le choix structurant est le **GRANT scopé colonne** plutôt qu'un `GRANT UPDATE` table-large. L'ordonnanceur ne réécrit JAMAIS l'identité immuable d'un item de travail ; lui donner UPDATE seulement sur les quatre colonnes de transition rend ce moindre-privilège *mécanique*, pas conventionnel. Symétriquement, on REVOKE explicitement chaque écriture de vérité (et CREATE) au lieu de simplement « ne pas grant » : le miroir GRANT peut ainsi *asserter positivement* que l'ordonnanceur n'est pas un 2ᵉ rôle `aidos`. « Scheduler » ne doit jamais devenir un writer privilégié par dérive de droits.

Le `lease_epoch` arrive maintenant (BA20) alors que l'enforcer de fencing au write-path est BA22 : on OUVRE la colonne + le droit de l'ordonnanceur à la bumper, mais le planner/enforcer est différé — exactement l'exception bootstrap (un substrat ouvert au pas qui en a besoin). BA21 portera l'algorithme `MatchRole` (déterministe, sur rôles déclarés, jamais un prompt LLM) qui consomme le SELECT `kernel.agent_layer` ouvert ici. BA20 ne fait que la primitive : rôle + migration + fencing.

## Méta-méta — l'invariant que ça garde vivant

> **« Drainer la file » est un pouvoir nommé, fail-closed, séparé de « être un agent » — et l'ordonnanceur n'est jamais un 2ᵉ rôle de vérité.**

La file de travail rouge est, depuis S22, *en écriture seule* pour l'agent : il ne peut pas se réclamer son propre travail. BA20 ne brèche pas cette posture — il la *complète* en créant le seul rôle qui transitionne, et en l'enfermant dans un surface minimal asserté par le miroir GRANT sur un vrai Postgres : UPDATE de quatre colonnes + SELECT des specs, et rien d'écrivable au-dessus de la ligne. Le fencing (`lease_epoch` monotone) garde l'invariant « zéro lost-update » : un epoch est une règle déclarée (`prev+1`), jamais apprise ; le cœur `Claim` est une fonction pure totale sans horloge, et son miroir de reproductibilité rejoue « même entrée ⇒ même sortie » — un ordonnanceur qui jugerait par LLM ce qu'un compteur monotone et un GRANT décident serait un trou de déterminisme qui **bloque le pas**.
