<Note>Côté concept — aucune ligne de code. Pour le détail des décisions, du miroir et de l'algorithme de tracé, voir [Pour moi → FN06](/steps/internals/fn06-graphe-fonctionnel).</Note>

## En une phrase

FN06 **dessine** le graphe fonctionnel de l'app émise sur le Workbench — chaque fonction un nœud, chaque appel une arête — comme une **fonction pure** de l'index FN05 (même graphe → même tracé), et **surligne** le sous-graphe affecté par un changement, exactement ce que le **ContextRouter** (S33) rechargerait.

## Le problème que ça résout

FN05 a construit l'**index** du graphe d'appel du code émis — qui-appelle-qui — et l'a rendu sous forme de **liste** (`fonction → appelés`) + empreinte + sous-graphe affecté. Une liste se lit, mais ne se *voit* pas : pour comprendre d'un coup d'œil la structure d'une app émise (« chaque fonction = une couche + un nœud », l'intention Understand-Anything), il faut la **carte dessinée**.

FN06 transforme l'index en un **graphe visuel** : un canevas SVG où l'on voit les couches empilées, les appels qui descendent, et — d'un clic — les couches qu'un changement ferait recharger. C'est la facette *visualisation* de la même vérité que FN05 indexe.

## Les idées-clés

<CardGroup cols={2}>
  <Card title="Le tracé est une fonction pure de l'index">
    Les positions des nœuds (par **profondeur d'appel** : les feuilles en bas, les appelants au-dessus) et les arêtes sont **calculées** par <code>layoutCallGraph</code>, jamais par un « LLM qui dessine le code ». Même graphe + même sélection affectée → tracé **byte-identique**. Le graphe affiché porte la **même empreinte** que l'index FN05 (content-addressé).
  </Card>
  <Card title="On voit le sous-graphe affecté">
    Un clic sur « Surligner le sous-graphe affecté » marque, en couleur d'accent, les nœuds qu'un changement de la première fonction ferait recharger — la **clôture des dépendants** de FN05. C'est la sélection du **ContextRouter** (S33), rendue visible : l'agent ne recharge que ces couches, pas tout l'arbre <code>gen/</code>.
  </Card>
  <Card title="Le code émis, pas le Go d'AIDOS">
    Le graphe porte sur l'**app de l'utilisateur** (le « code émis » en style fonctionnel — fonctions pures, zéro globale mutable, graphe acyclique, le mandat FN02). L'échantillon dessiné est le slice checkout fonctionnel : <code>total → applyDiscount → priceLine</code>.
  </Card>
  <Card title="Hors-portée / illisible → graphe vide (honnêteté)">
    Seul un code émis portant le marqueur « CODE GENERATED BY AIDOS » a un graphe à dessiner (ADR 0036 §3). Une source non marquée, ou illisible, rend un **graphe vide** : FN06 n'invente jamais un nœud ni une arête (la règle d'honnêteté, fail-closed).
  </Card>
</CardGroup>

## Ce que vous voyez à l'écran

Sur le panneau **/emitters** du Workbench, une section **« Graphe fonctionnel de l'app émise »** porte deux boutons. **« Visualiser le graphe fonctionnel »** dessine le graphe SVG : chaque fonction est une boîte, chaque appel une flèche, posées par profondeur. **« Surligner le sous-graphe affecté »** met en évidence, en couleur d'accent, les fonctions qu'un changement de la première fonction ferait recharger. Sous le graphe, l'**empreinte** (même code → même graphe) et la liste du sous-graphe affecté. Le tracé est **thémé** (tokens ADR 0010) et **bilingue** (FR/EN, ADR 0011). Tout est **calculé**, jamais déclaré.

## Le mur

FN06 n'écrit **aucune vérité**. Le tracé est du code *sous la ligne* : il **lit** l'index (lui-même dérivé du code émis) et **dessine** le graphe ; il ne touche ni `kernel`, ni `mirrors`, ni `fitness`. L'écran *montre* le graphe ; il ne fait jamais écrire de vérité.
