## En une phrase

S74 apprend aux **émetteurs** d'AIDOS à générer une app **multi-entités** : des entités qui **se référencent** (FK, tables de liaison N-N), une **navigation typée** entre elles, et des **workers** pour le travail de fond — le tout rendu de façon **déterministe**, à partir de votre schéma.

## Le problème que S74 résout

Avant S74, les émetteurs d'AIDOS (S35) savaient projeter **une seule entité à la fois**, sans liens entre elles, sans fichiers, sans travail asynchrone. C'était le **plafond** du système de types : une app réelle a besoin que ses entités **se parlent** — un livre a un auteur, un article a des tags, une commande a des lignes.

S71 a ajouté le **nœud de relation** (1-1 / 1-N / N-N), S72 le **type blob/fichier**, S73 l'**operation asynchrone**. Mais ces nœuds restaient des *sources* : personne ne les **transformait encore en code**. S74 est l'émetteur qui les **réalise** — il lit le schéma complet et rend le SQL, le TypeScript et les workers de l'app émise.

Deux pièges qu'AIDOS refuse :

- **Inventer une FK vers une table qui n'existe pas.** Chaque clé étrangère du DDL référence une **vraie** table déclarée, avec sa vraie clé primaire. Une relation vers une entité non déclarée est **refusée** (`UNKNOWN_RELATION_TARGET`), jamais devinée.
- **Confier la génération à une IA.** Rendre du SQL/TS à partir d'un AST est un **calcul pur et reproductible**. C'est du **code**, jamais une IA : le même schéma rend toujours les **mêmes octets** (le hash le prouve).

## Ce que S74 apporte

## Comment ça marche, vu de l'écran

Le panneau **Workbench → Émetteurs relation-aware** vous laisse projeter un schéma de démo : `author` (1) ──< `book` (N) ──N-N── `tag`, plus une operation async cron `sendReminder`.

1. Vous **choisissez une cible** : DDL Postgres, modèle TS, ou worker async.
2. Vous **émettez**. Pour le **DDL**, le panneau déroule les tables, la colonne FK `author_id REFERENCES "author"("id")` (une **vraie** table), la **table de liaison** `book_tags` pour le N-N, et — schéma async — une table `outbox`.
3. Pour le **TS**, le panneau montre les **types** avec leurs associations (`author?: Author`, `tags?: Tag[]`) et les **loaders** de navigation.
4. Pour le **worker**, le panneau montre la fonction `dispatchSendReminder` qui draine l'outbox et l'**échéance** cron baked-in.
5. À chaque émission, une **adresse de contenu** (le hash de la source) est affichée : ré-émettre rend **exactement** les mêmes octets.

<Note>Tout cela se fait **par écran** (la loi d'ui-completeness) : le contrôle est lié au vrai moteur et exécutable depuis la page, prouvé par un test Playwright.</Note>

## Le mur — ce que S74 ne fait PAS

Émettre **n'écrit aucune vérité**. Le code rendu (SQL, TS, worker) est une **projection** — régénérable à volonté à partir de la source, et appartenant à l'app émise, pas au truth-store d'AIDOS. Le nœud de relation, le nœud async restent des **sources** au-dessus de la ligne ; les promouvoir passe par `idée → miroir → /goal → approbation humaine`, jamais par cet écran. L'émetteur **rend** ; il ne **fige** rien.

## La cible : TS / Hono (ADR 0040)

À partir de S74, la cible backend de l'app émise n'est plus Go : les handlers, les workers et la navigation deviennent du **TypeScript fonctionnel** (Hono), avec un client Postgres TS. Le `EmitDDL` (dialecte Postgres) reste **inchangé**. La reproductibilité byte-identique est **préservée** sur toutes les cibles.
