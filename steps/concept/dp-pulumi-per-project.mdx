## En une phrase

**Chaque projet** qu'AIDOS déploie = sa **full-stack complète**, levée **POUR DE VRAI** par **Pulumi** (provider `@pulumi/docker`) — **un stack par projet×env**, ses propres conteneurs + volume + réseau `traefik_default` + labels Traefik, **déployable partout** (Docker aujourd'hui, cloud demain). L'**émetteur** du programme reste une **projection PURE** byte-stable du `StackManifest` ; l'**exécuteur** (`pulumi up`/`down`) est le **geste gaté** qui exécute ce programme — preuve **live** : `demoshop-dev`.

## Le problème que ça résout

Jusqu'ici, AIDOS savait **émettre** l'infra de déploiement (l'EPIC F), mais le **provisioning réel par projet** restait à finir : un émetteur `docker-compose.yml` (l'intérim) décrivait la stack, sans la **lever vraiment** par projet, dans un vrai langage IaC.

L'exigence utilisatrice du 2026-06-13 tranche : **« du Pulumi qui fait les docker par projet ».** Chaque projet doit être sa **full-stack complète**, déployée **réellement** par Pulumi — **un stack par projet×env** (`<project>-<env>`), avec ses propres conteneurs, son volume, son réseau, ses labels Traefik et un vrai certificat HTTPS. Et ce, **déployable partout** : Docker aujourd'hui, n'importe quel cloud demain, sans changer le code — seules les vars d'env (et le provider) changent.

## La preuve à généraliser — le GOLD

La forme a d'abord été **prouvée à la main**. Le programme `/.deploy-pulumi/demoshop-dev/{index.ts, Pulumi.yaml, package.json}` a **réellement levé** le stack `demoshop-dev` :

```text
demoshop-dev-db    Postgres healthy (volume demoshop-dev-pgdata, pg_isready)
demoshop-dev-app   l'app émise, DATABASE_URL → demoshop-dev-db
réseau             traefik_default (EXTERNE, partagé)
route              https://demoshop-dev.sagedesk.fr  ←  VRAI cert Let's Encrypt
```

C'est **exactement** la forme que l'émetteur produit désormais — **généralisée** par projet×env. Le GOLD n'est pas une maquette : c'est un stack **live** que rien dans la généralisation ne casse.

## Le geste capital — un stack par projet×env, vraiment levé

Le cœur, c'est qu'**un projet n'est pas une ligne de YAML** : c'est une **full-stack** qui prend vie. La généralisation pose, par projet×env :

```text
nommage        stack <project>-<env> ; conteneurs <project>-<env>-<service> ; volume <project>-<env>-<vol>
réseau         attaché au réseau EXTERNE traefik_default — JAMAIS recréé
datastore      Postgres : POSTGRES_DB/USER/PASSWORD + healthcheck pg_isready + volume mount
serveur        DATABASE_URL → <stack>-db (le datastore par son nom de conteneur)
route HTTPS    labels Traefik complets : Host(`<stack>.sagedesk.fr`), websecure, tls, certresolver=le, priority=1000
images         RemoteImage{keepLocally:true} par image distincte
```

Deux choses sont **capitales** :

- **`priority=1000` PRIME le wildcard dev-preview.** La preuve a *révélé* qu'un placeholder wildcard (`aidos-dev-preview`, HostRegexp `*-dev.sagedesk.fr`) capte la requête **avant** le routeur du projet. La parade : le routeur du serveur porte `traefik.http.routers.<stack>.priority=1000`, qui **prime** le wildcard. Sans cette découverte, le projet ne serait jamais routé.
- **Le réseau externe est ATTACHÉ, jamais créé.** Quand `Network.External=true`, l'émetteur attache `networksAdvanced: [{ name: "traefik_default" }]` **inline**, **sans** `new docker.Network` — Traefik **possède** ce réseau. Un réseau **non-externe**, lui, est bien **créé**. La preuve a montré que recréer `traefik_default` casserait tout.

## L'émetteur pur, l'exécuteur gaté — le mur tient

C'est la frontière `déterminisme-first` (le mur §2/§6/§8), et elle est nette :

- **L'ÉMETTEUR est une fonction PURE.** `EmitPulumiStack(project, env, manifest)` projette le `StackManifest` en un programme Pulumi/TS **byte-stable** : même manifest + env ⇒ programme **byte-identique** (FN02-pur — pas d'horloge, rng, IO, global mutable). C'est du **CODE**, garanti par un **miroir de reproductibilité** (7 tests property+fixture). Aucun LLM n'écrit jamais ce programme.
- **L'EXÉCUTEUR est le geste GATÉ.** `aidospulumi up`/`down` ne **juge rien** : il **matérialise** les artefacts byte-stables de l'émetteur, puis pilote `pulumi up`/`pulumi destroy`. C'est exactement le rôle que tenait `docker compose up -d` dans `ai-lab` — un geste side-effectant gaté, jamais un juge. Il **n'écrit aucune vérité** (projection below-the-line).

L'agent écrit le code d'infra **au build** ; il n'est **jamais** dans la boucle runtime à faire ce qu'une fonction ferait mieux.

## Une seule source, N cibles — le compose reste une projection

Le `StackManifest` AST (au-dessus du mur, content-adressé) reste la **source unique**. Le programme **Pulumi/TS** (cette cible) **et** le **`docker-compose`-emit** (DP03/DP05) sont **deux projections déterministes** de cette même source — aucune ne supplante l'autre, aucune n'est réécrite (anti-overwrite §9). Le compose reste une **projection dérivable**, l'interim devenu une vue parmi d'autres. Et **demain**, la cible `future_cloud` (DP33) est **le même programme** avec un provider **cloud** (k8s / Fly / RDS / DNS managé) : *le code ne change pas, seules les vars d'env + le provider changent.*

## Ce que ça autorise

À partir de maintenant, **déployer un projet = lever sa full-stack pour de vrai**, en un geste : `aidospulumi up --project <p> --env <e>` matérialise le programme émis byte-stable et le fait exister — Postgres healthy, app émise routée en HTTPS avec un vrai cert, tout isolé par projet×env. **Déployable partout** : Docker aujourd'hui, cloud demain, sans toucher au code. Ce que ça **préserve intact** : le `StackManifest` reste la seule vérité, le `docker-compose`-emit reste une projection dérivable, l'émetteur preview (DP25) reste byte-stable, et le GOLD `demoshop-dev` n'est pas touché. L'**ADR 0043 est amendé** (addendum 2026-06-13) à **deux têtes** : la cible self-hosted **actuelle** est Pulumi + `@pulumi/docker` par projet (preuve `demoshop-dev`), et la cible `future_cloud` (DP33) est Pulumi avec un provider cloud — **un seul programme, plusieurs cibles**.
