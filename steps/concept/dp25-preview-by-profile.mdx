## En une phrase

DP25 grave le **preview éphémère par profile** de l'app émise : une **preview de l'app servie à une URL éphémère**, où l'humain choisit le **profile de stack** (DP11) à amorcer, où l'**amorçage est déterministe** (DP12) et où le **démontage l'est tout autant** — et tout cela en gardant l'**invariant capital** : le **hash de la preview reste le hash de la phase**. DP25 **étend** la fonction `preview.BuildPlan` de S94, ne la **duplique** pas, et **ouvre l'EPIC F**.

## Le problème que ça résout

S94 a posé la **preview** : l'app émise depuis une phase stable, servie à une URL éphémère, avec la garantie capitale que **ce qui est servi est exactement ce qui a été émis** (`ServedMatchesEmitted`) et que l'**empreinte de l'app émise** (`EmittedAppHash`) est une fonction **pure de la phase**. Mais cette preview tournait sur une **stack fixe** : elle ne demandait jamais *quels services* amorcer autour de l'app — la base, le cache, le bus async, l'observabilité.

L'EPIC D avait pourtant déjà appris à raisonner par **profile** : DP11 a posé le **filtrage par profile** d'un manifest de stack (quels services sont retenus pour un profile donné), et DP12 l'**amorçage one-shot** déterministe de ces services. Restait à **brancher** ces deux moteurs sur la preview : *prévisualiser l'app avec un profile choisi*, amorcer **exactement** les services que ce profile retient, et pouvoir **démonter** proprement, dans l'ordre inverse.

Le réflexe naïf serait d'écrire une **seconde** preview à côté de S94 — une « preview avec amorçage ». Ce serait dupliquer un moteur, et faire dériver deux empreintes. DP25 pose la règle inverse : **étendre** S94, additivement, sans toucher d'un octet ni la forme S94 ni — surtout — l'invariant capital.

## Le geste capital — l'invariant `hash-preview = hash-phase`

Le cœur de DP25 est une **promesse préservée** : l'empreinte de l'app émise (`EmittedAppHash`) reste une fonction **pure de (phase ⊕ surface)** — elle est **sans profile**. Choisir `git`, `core` ou `full` ne change **rien** à l'app servie : même empreinte, même URL, même sous-domaine, même nom de stack.

```text
EmittedAppHash(phase, surface)              // profile-FREE — ∀ profile, même hash
ServedMatchesEmitted == true                // ce qui est servi = ce qui a été émis
URL / Subdomain / StackName                 // profile-indépendants
```

Ce qui **varie** avec le profile, c'est uniquement l'**amorçage** autour de l'app : *quels services* sont mis en route, et donc le `SequenceHash` (l'adresse de l'amorçage) et l'`ID` du plan. Mais l'**app elle-même** est invariante. C'est la frontière capitale : le profile gouverne le **substrat**, jamais le **résultat émis**. Le miroir l'épingle pour **tous** les profiles.

## La forme étendue — 5 champs optionnels, S94 byte-inchangé

DP25 ajoute à l'`Input` de la preview **cinq champs OPTIONNELS**, et à `PreviewPlan` **deux champs**. La règle d'anti-overwrite (§9) est nette : quand le `Manifest` est **absent**, la preview est un **pur plan S94** — aucun amorçage, forme byte-inchangée.

| Ce qui s'ajoute | Rôle | Quand absent |
|---|---|---|
| `Profile` | le profile de stack à amorcer (défaut `core`) | ignoré (plan S94) |
| `Manifest` | la source de stack DP02 dont les services sont amorcés | **aucun amorçage** — pur plan S94 |
| `Host` / `Secrets` | l'état hôte + les secrets pour l'amorçage DP12 | non consultés |
| `Env` | l'environnement (défaut `dev`), seulement pour le gate doltgres-en-prod DP11 | non consulté |
| `PreviewPlan.Profile` | le profile retenu, rendu à l'écran | omis |
| `PreviewPlan.Bootstrap` | l'amorçage filtré + sa séquence (`nil` pour un plan S94) | `nil` |

Le point décisif pour l'anti-overwrite : quand `Bootstrap` est `nil`, les clés `profile`/`bootstrap` sont **OMISES de l'adresse de contenu** — donc les **IDs de plan S94 existants restent byte-inchangés**. DP25 n'altère **rien** de l'existant ; il ajoute un comportement **quand on lui donne un manifest**.

## L'amorçage déterministe — DP11 + DP12 réutilisés verbatim

Quand un `Manifest` est fourni, la preview construit son **amorçage** (`PreviewBootstrap`) en **réutilisant verbatim** les deux moteurs de l'EPIC D (ADR 0007 — réutiliser, jamais réinventer) :

1. **Filtrer par profile (DP11)** — `composeemit.FilterByProfile` retient les services que le profile sélectionne ;
2. **Amorcer (DP12)** — `bootstrap.EmitBootstrapSequence` émet la séquence d'amorçage one-shot déterministe de ces services.

Le `PreviewBootstrap` porte le profile, la séquence, son `SequenceHash` (l'adresse **dépendante du profile**, qui se replie dans l'`ID` du plan) et la liste des services. Un **manifest cross-app** (qui mélangerait deux projets) est **refusé** (`ErrManifestProjectMix`) — un amorçage ne traverse jamais la frontière d'un projet.

## Le démontage déterministe — l'ordre inverse du boot

DP25 ajoute une fonction **pure** de démontage : `TeardownOf(plan)` rend un `TeardownPlan` où les services se **dénouent dans l'ordre INVERSE** de leur amorçage. C'est la propriété qu'on attend d'un démontage propre : on défait dans l'ordre contraire de ce qu'on a fait. Et un **démontage complet** (profile large) est un **sur-ensemble** d'un démontage **lean** (profile étroit) — le profile qui amorce moins démonte moins, exactement les mêmes services, dans l'ordre inverse.

## Le finding DP11 — `core` est la baseline, pas une restriction

DP25 documente honnêtement une **sémantique DP11** qu'on aurait pu mal lire : une sélection `core` **garde tous les services**. Pourquoi ? Parce que le filtrage DP11 ajoute `core` au jeu de profiles de **chaque** service (`ServiceProfiles`) — `core` est la **baseline toujours-active**, le socle commun, **pas** une restriction. En nombre de services amorcés, `core ≡ full`.

Le profile qui **réduit vraiment** est un profile spécifique qu'aucun service optionnel ne déclare (le miroir utilise `git`) : là, l'amorçage est plus **lean** que `full` (l'observabilité `otel`, par exemple, est exclue). La doc et le miroir reflètent cette sémantique **réelle** plutôt que la lecture naïve « core boote moins que full ».

## Le mur — la preview ne grave aucune vérité

DP25 reste **below-the-line** : prévisualiser l'app n'écrit **aucune** vérité. La preview ne consulte ni n'écrit `kernel`, `mirrors` ou `fitness` ; elle ne **persiste rien** en Postgres (l'amorçage de preview est éphémère — *bootstrap exception*). C'est le **déterminisme-first** (§6/§8) : filtrer un manifest, émettre une séquence d'amorçage, calculer un démontage et une empreinte sont des décisions **pures**, donc du **code**, jamais un jugement d'un LLM — **aucun LLM n'entre**. Le miroir prouve le **plan** et son **hash** ; le serveur web-preview sert l'app (pas de vrai docker, exactement comme S94).

## Ce que ça autorise — et l'EPIC F qui s'ouvre

DP25 transforme la preview en un **preview par profile** : ce que ça **autorise**, c'est de prévisualiser l'app émise avec le **profile de son choix**, d'**amorcer** déterministement exactement les services que ce profile retient, et de **démonter** proprement dans l'ordre inverse — tout en gardant l'invariant capital `hash-preview = hash-phase`. Ce que ça **préserve intact**, c'est S94 dans son entier : sans `Manifest`, la preview est byte-identique à S94, et les IDs de plan existants ne bougent **pas**. La loi de complétude veille : le geste ne vit que parce qu'il porte sa preuve vivante — le miroir Go (hash-invariant ∀ profiles, reproductibilité byte-identique, lean vs full à app-hash identique, `core` baseline, démontage déterministe, cycle de vie complet + refus). Avec ce preview par profile, l'**EPIC F s'ouvre** : la couche de prévisualisation par stack de l'app émise est posée, prête pour la suite.
