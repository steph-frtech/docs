## En une phrase

DP30 grave les **docs de l'app émise** — pas les docs d'AIDOS, mais celles que **chaque app** qu'AIDOS construit pour vous **porte avec elle** : un **site de documentation** (Fumadocs), une **référence API** (Scalar, lue depuis l'**OpenAPI émis par S90**) et une **recherche statique** (Pagefind). C'est une **projection PURE et déterministe** (la `DocsProjection`) — **distincte** des docs Mintlify d'AIDOS (le journal de build) ; les docs sont une **projection**, jamais une vérité ; DP30 **ouvre l'EPIC G**.

## Le problème que ça résout

Quand AIDOS construit votre app, elle en émet le code, le schéma, l'API (S90 émet la surface API complète + un document OpenAPI 3.1) et son infrastructure de déploiement (l'EPIC F, clos par DP29). Mais une app sans **documentation** est une app qu'on ne sait pas lire : à quoi sert l'entité `Order` ? quels sont ses attributs ? quel endpoint pour créer une commande, lequel pour les lister ? Jusqu'ici, rien ne projetait ces réponses pour l'app construite.

Le piège le plus dangereux serait de **confondre deux docs** : les docs d'**AIDOS** (le *journal de build*, sur `aidos.mintlify.app` — la page que vous lisez en ce moment), et les docs de **votre app émise** (la doc *de votre produit*). Ce sont deux choses radicalement différentes. DP30 pose la frontière : il grave les docs **de l'app émise**, et **uniquement** elles — Fumadocs pour le site, Scalar pour l'API, Pagefind pour la recherche — sans jamais toucher aux docs Mintlify d'AIDOS.

Le second piège serait d'**inventer** le contenu de cette doc : faire écrire à un agent une description « plausible » de l'API, une page « probable » par entité. Ce serait une doc qui **diverge** de l'app qu'elle est censée décrire. DP30 pose la règle inverse : la doc est une **projection PURE** du Kernel et de l'OpenAPI déjà émis par S90 — un endpoint Scalar par operation **réellement** émise, une page Fumadocs par entité **réellement** dans le domaine, **jamais** un endpoint ni une page inventés.

## Le geste capital — les docs sont une PROJECTION, jamais une invention

Le cœur de DP30, c'est `EmittedDocs(spec)` : une **fonction PURE** qui **projette** le Kernel + l'OpenAPI de S90 en trois briques, sans rien inventer :

```text
référence API (Scalar)   →  un endpoint par operation SYNCHRONE de S90 (apisurface.PathOf, openapi.json)
                            createOrder, listOrders…  →  rendus ; archiveOrder (async)  →  EXCLU
site de doc (Fumadocs)   →  une page-concept par ENTITÉ distincte du domaine (termes = entité + attributs)
recherche (Pagefind)     →  un enregistrement par page (1:1) — le « trouve » déterministe
adresse des docs          →  DocsID content-adresse le corps canonique ; SourceHash == apisurface.SourceHash(spec)
```

Deux propriétés sont **capitales** :

- **Scalar consomme CHAQUE endpoint de S90, sans en inventer aucun.** La projection lit le chemin `openapi.json` (`apisurface.EmitOpenAPI`, `apisurface.PathOf`) et rend **un** endpoint Scalar par operation **synchrone** de la surface — `createOrder`, `listOrders` sont présents ; une operation **asynchrone** comme `archiveOrder` est **exclue** (elle ne fait pas partie de la surface synchrone). Et `SourceHash == apisurface.SourceHash(spec)` : la doc API **est** la surface S90, à la même adresse — jamais une seconde source de vérité.
- **Même Kernel ⇒ mêmes docs, à l'octet près.** `EmittedDocs` est totalement déterministe : aucune horloge, aucun rng, aucun ordre de map, aucun chemin absolu, **aucun LLM**. Le même Kernel produit la même `DocsProjection`, byte-identique. La doc ne **dérive** jamais de l'app : elle en est la projection.

## Une seule rangée « docs », trois fragments constituants

La palette mesurée du provisioning (DP14) déclare déjà, côté front (`substrate-palette.ts`), **une** rangée `docs` — Fumadocs + Scalar + Pagefind, en GO. DP30 fait, côté backend, ce que cette rangée annonce : il la **casse en ses trois fragments constituants** via `SubstrateDocsFragments(projectID, env)` :

- **Fumadocs** — port `3400`, `role docs`, `profile docs` ; le **site** de documentation ;
- **Scalar** — port `3500` ; la **référence API** ;
- **Pagefind** — port `3600` ; la **recherche statique** (`depends_on fumadocs`).

Tous portent des **images émises** (la convention DP02) et un **volume bind par-projet** isolé via `datafragments.IsolationToken` — le **token DP15 réutilisé** (les docs d'un projet ne fuient jamais dans un autre). Le paquet **calque DP15/16/17/18** pour la mécanique des fragments et **ne fails-close** que sur `UNKNOWN_ENVIRONMENT` — il n'y a **aucun env-gate** : une app a sa doc dans tous ses environnements.

## Le mur — les docs LISENT, elles n'écrivent aucune vérité

DP30 respecte le mur (§2). `WritesTruth()` renvoie **`false`** sur **chaque** fragment **et** sur la `DocsProjection` ; **aucune** capability `docs:*` ne matche `IsTruthWriteCapability`. Les docs sont une **projection** (`IsProjection=true`, `WroteKernel=false`), jamais une **vérité** — c'est ce que la fixture `DocsAreAProjectionNeverATruth` épingle. Et elles sont **distinctes** des docs Mintlify d'AIDOS : projeter la doc de votre app n'écrit **rien** dans `kernel`, `mirrors` ou `fitness`, et ne touche **pas** au journal de build.

La validation n'est **pas re-frappée** : DP30 la **délègue** à `apisurface.EmitOpenAPI` (S90). Si la spec est malformée, le `BlockReason` de S90 est **surfacé verbatim** via un `*DocsRefusal` — le code ne réinvente ni ne masque le refus (`MalformedSpecRefused`). Et c'est le **code** qui juge : `EmittedDocs`, `SearchIndex`, `SubstrateDocsFragments` sont des **fonctions pures**, jamais un LLM.

## Ce que ça autorise

DP30 donne à chaque app qu'AIDOS construit sa **propre documentation** : un **site** (Fumadocs) avec une page-concept par entité du domaine, **thème ccup** (ADR 0010) et **bilingue FR-défaut** (ADR 0011) hérités ; une **référence API** (Scalar) fidèle à l'octet à l'OpenAPI émis par S90 ; et une **recherche statique** (Pagefind) qui **trouve** un terme du domaine et n'en invente aucun. Ce que ça **préserve intact**, c'est tout le reste : DP30 **réutilise** S90 (la projection Scalar consomme `apisurface.PathOf` + `apisurface.EmitOpenAPI`, `SourceHash == apisurface.SourceHash`) et **calque** DP15/16/17/18 pour les fragments (images émises, volume bind par-projet via le **token DP15**, `depends_on fumadocs`) — il **ne duplique** ni ne **re-frappe** rien (ADR 0007). La rangée `docs` du front existe déjà ; le backend la casse en ses trois fragments — **aucun changement front en périmètre**, les types de projection sont JSON-taggés et **prêts** pour un futur panneau `/v2` docs. La loi de complétude veille : les docs ne vivent que parce qu'elles portent leur preuve vivante — le miroir Go (property : byte-identique, palette ccup, aucun env-gate, isolation par-projet, token partagé, n'écrit aucune vérité, **même Kernel ⇒ mêmes docs**, **Scalar consomme chaque endpoint S90**, Pagefind indexe chaque page ; fixture : substrat émis, Scalar rend chaque endpoint sync, Fumadocs rend les concepts du domaine, Pagefind indexe et trouve, docs = projection jamais vérité, spec malformée refusée). Avec DP30, **l'EPIC G est ouvert** : votre app n'est plus seulement construite et déployée — elle est **documentée**.
