## En une phrase

DP32 **branche** le **secret store par projet** (S91) sur le provisioning : chaque app qu'AIDOS construit a ses **secrets** — un credential DB, une clé API tierce, un secret OAuth, un certificat — stockés **chiffrés au repos**, **scopés projet** (les secrets d'une app ne fuient **jamais** dans une autre), **jamais** dans le truth-store, git ou le source émis. Au boot, l'**ordre de merge gravé** — références (`.env.example`, DP04) → valeurs (store S91) → overrides — alimente le **`.env` concret** par variables d'environnement. Le `.env.example` émis ne porte **que des références** (zéro valeur) ; une référence requise non résolue est **fail-closed** (`MISSING_SECRET_AT_BOOT`, clés nommées) ; la **rotation** enregistre une décision **append-only par empreinte** (jamais la valeur) ; et **jamais** la valeur n'apparaît à l'écran.

## Le problème que ça résout

Une app qu'AIDOS émet ne tourne pas sur du vide : pour parler à sa base, à une API tierce, à un fournisseur OAuth, elle a besoin de **secrets**. Un credential de connexion, une clé d'API, un secret de signature, un certificat. Ces secrets posent une question dangereuse : **où vivent-ils** ?

Le piège serait de les écrire **là où ils ne doivent jamais aller**. Dans le **truth-store** (le kernel/mirrors) — un secret n'est pas une vérité, c'est un matériau d'exécution. Dans **git** — un secret commité est un secret fuité, pour toujours, dans l'historique. Dans le **source émis** de l'app — un `.env` rempli de valeurs en clair, recopié dans le dépôt. Chacun de ces chemins est une porte d'exfiltration.

Le second piège serait de démarrer une app avec un **credential blanc ou deviné** quand un secret requis manque — l'app boote, parle à la base avec un mot de passe vide, et échoue de la pire façon (silencieusement, à moitié). Le troisième serait d'**afficher la valeur** d'un secret à l'écran, ou de la recopier dans un log, dans une décision de rotation, dans un message d'erreur.

DP32 pose la règle inverse sur tous ces fronts. Les secrets vivent dans un **store chiffré au repos, scopé projet** (le geste S91, déjà construit) ; ils alimentent un **`.env` concret** au boot **par variables d'environnement** ; le `.env.example` émis ne porte que des **références** ; une référence requise manquante **refuse le boot** ; la rotation s'enregistre **par empreinte**, jamais par valeur ; et la valeur ne sort **jamais** à l'écran.

## Le geste capital — l'ordre de merge gravé, références → valeurs → overrides

Le cœur de DP32, c'est `MergeBootEnv(envExample, store, projectID, overrides)` : la résolution du `.env` **concret** d'une app, dans un **ordre de merge gravé**.

```text
1. références   →  .env.example (DP04) — la base : CHAQUE clé + ses placeholders (${VAR} / <<from-secret-store>>)
2. valeurs      →  store S91 (Get, scopé project_id) — chaque référence de secret résolue à sa valeur chiffrée-au-repos
3. overrides    →  les overrides de déploiement — la DERNIÈRE couche : un override de n'importe quelle clé gagne
                →  même entrée → même .env concret, à l'octet près (fonction PURE, totale)
```

Trois propriétés sont **capitales** :

- **L'ordre est gravé, jamais improvisé.** Les trois couches — `références`, `store`, `overrides` — sont une **liste déclarée** (`BootMergeOrder`), pas un `sed` interactif. Une couche plus tardive gagne sur une plus ancienne (last-write-wins). Le Workbench peut **rendre** cet ordre, pour que le merge soit lisible, jamais une boîte noire.
- **La fonction est pure et totale.** `MergeBootEnv` n'a **pas** d'horloge, **pas** de RNG, **pas** de fuite d'ordre d'itération : la même entrée produit le **même** `.env` concret, à l'octet près — c'est le **miroir de reproductibilité**. Le `.env.example` **émis** n'est jamais muté : les valeurs concrètes ne vivent qu'en **mémoire** au boot, jamais recopiées dans les bytes.
- **Une référence requise non résolue refuse le boot.** Si une référence de secret n'est résolue **ni** par le store **ni** par un override (la différence d'ensemble `requises − (store ∪ overrides)`), le boot est **refusé** avec `MISSING_SECRET_AT_BOOT`, les clés manquantes **nommées** dans l'explication actionnable. Jamais un credential blanc, jamais une valeur devinée (honnêteté §8).

## Scopée projet — un secret de l'app A ne fuit jamais dans l'app B

Le store est **strictement** scopé projet. `secretstore.Get` / `Has` sont scopés `project_id` (un `scopeKey` + un `AES-GCM AAD bind`, S91) : un secret du projet A est **invisible** sous le projet B — le déchiffrer sous un autre scope échoue, par construction de la crypto. Et à la persistance, **S55** (RLS + `project_id`) empêche la fuite cross-projet en base. La défense est **en profondeur** : la crypto isole à la lecture, la RLS isole au stockage.

C'est ce que la fixture `TestDP32_E_SecretOfANeverLeaksToB` et la property `TestProp_DP32_CrossProjectIsolation` épinglent : un secret écrit pour A n'est **jamais** lisible par B, ∀ couple de projets.

## Le mur — les secrets jamais dans le truth-store, git ou le source émis

DP32 grave la frontière du mur (§2). Les secrets vivent dans le **store chiffré au repos**, scopé projet — et **nulle part ailleurs** : jamais dans le **truth-store** (`kernel`/`mirrors`/`fitness`), jamais **git**, jamais le **source émis** de l'app. Le `.env.example` émis (DP04) ne porte **que des références** (zéro valeur, une property ∀), et un **scan déterministe** (`secretstore.ScanEmission` — du code, gitleaks-style, **jamais** un LLM) est **vert** sur l'émission : aucune valeur de secret n'a fui dans les bytes émis. La valeur concrète n'existe qu'en **mémoire** au boot et en **variable d'environnement** dans l'appliance qui exécute l'app.

Deux preuves l'épinglent : `TestDP32_D_EmittedSourceIsReferencesOnly_ScanGreen` (le source émis est références-only, scan vert) et `TestProp_DP32_NoSecretInEmittedSource` (∀ secret, aucune valeur dans le source émis).

## La rotation — une décision enregistrée par empreinte, jamais la valeur

Tourner un secret n'est **pas** un écrasement silencieux. `RotateSecret(store, projectID, name, newValue)` tourne par la porte S91 (`secretstore.Rotate`) : l'ancienne valeur est **invalidée** (S91 la supersède — `Get` ne la renvoie **plus jamais**) et le **prochain** boot injecte la nouvelle. La rotation **enregistre** une `RotationDecision` **append-only** (§9), **content-adressée par empreinte** : qui a tourné quel secret, sous quel projet, et l'**empreinte** (`StoreFingerprint`) **avant** et **après** — **jamais** la valeur en clair. Une empreinte changée **prouve** que la valeur a bougé, **sans** l'exposer.

Et rotater un secret **absent** est **refusé** (`ErrNotFound`) : on **Set** ce qui n'existe pas, on **Rotate** ce qui existe — pas de création-silencieuse-à-la-rotation. La fixture `TestDP32_C_RotationInvalidatesOldSecretAndRecordsDecision` et `TestDP32_C_RotateAbsentIsRefused` les épinglent.

## Le branchement de DP12 — le vrai store remplace le mock

DP12 avait posé le bootstrap d'une app émise avec un **mock** de la présence des secrets (une liste de **noms** présents passée en donnée). DP32 **branche pleinement** le vrai store : `EmitBootstrapSequenceWithStore` consomme le **vrai** store S91 au rung « secrets vérifiés » — `SecretsStateFromStore` dérive la présence du store **réel** (via `Has`, scopé projet) et **remplace** le mock. La loi `MISSING_SECRET_AT_BOOT`, le set ordonné fermé des événements, la résolution de port pure et le mur tiennent **inchangés**. Et `EmitBootstrapSequence(mock)` reste **intact** (anti-overwrite §9 — les 11 tests DP12 restent verts) : DP32 ne touche qu'à la **source** de la présence (du mock au store réel), pas à la projection.

## Ce que ça autorise

DP32 donne à chaque app qu'AIDOS construit son **secret store par projet**, branché sur le provisioning : des secrets **chiffrés au repos**, **scopés projet** (jamais de fuite A→B), **jamais** dans le truth-store/git/source émis ; un `.env` **concret** alimenté au boot par l'**ordre de merge gravé** (références → valeurs → overrides) ; un `.env.example` émis **références-only** (scan vert) ; un boot **fail-closed** sur tout secret requis manquant (`MISSING_SECRET_AT_BOOT`, clés nommées) ; une **rotation** enregistrée **par empreinte** (jamais la valeur) ; et **jamais** la valeur à l'écran. Ce que ça **préserve intact**, c'est tout le reste : DP32 **réutilise** S91 (`secretstore` — Get/Has/Rotate/ScanEmission/StoreFingerprint), DP04 (`envemit` — `.env.example`/`SecretPlaceholder`/`Keys`), DP12 (`EmitBootstrapSequence` réutilisé verbatim), S55 (RLS), S02 (content-address) — il **ne forke** ni ne **re-frappe** rien (ADR 0007). La loi de complétude veille : le branchement ne vit que parce qu'il porte sa preuve vivante — le miroir Go (fixture : merge en ordre gravé, overrides gagnent en dernier, référence manquante bloque le boot, rotation invalide l'ancien + enregistre la décision, rotater-absent refusé, source émis références-only scan-vert, secret de A ne fuit pas vers B, le bootstrap consomme le vrai store, le bootstrap branché reproductible ; property : merge déterministe, isolation cross-projet, référence manquante fail-closed, override gagne en dernier, aucun secret dans le source émis ; soit **14 tests DP32**, 14 PASS — et le package `bootstrap` compte **25 tests** avec les 11 DP12 préexistants, tous verts). Backend-only : la persistance Postgres du store + le log de rotations append-only restent un OpenQuestion non-bloquant (concern du deploy track) ; reste, pour plus tard, un futur écran `/secret-store` qui *poserait* et *tournerait* les secrets et *montrerait* l'empreinte — **jamais la valeur** — *tout se fait par écran*.
