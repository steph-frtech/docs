## En une phrase

WB2-27 ouvre l'écran `/v2/builder` : **un seul chat qui porte le cycle de vie complet d'une appli** — capturer, greffer, promouvoir, **générer**, **déployer en gravissant l'échelle test → staging → prod** (le cliquet généralisé), **voir les deltas jusqu'aux fonctions exactes**, **déclencher le déploiement réel** d'un clic gaté, et **ouvrir n'importe quel écran du Workbench** — et « tout » passe par une **grammaire d'intentions fermée**, classée par un algorithme, réduite par une fonction pure, **jamais** par la magie d'un modèle.

## Le problème que ça résout

Vous voulez parler à votre projet : « greffe les pommes sous le catalogue », « capture cette idée », « promeus la dernière idée », **« génère l'application »**, **« déploie l'application en test »**, **« … en staging »**, **« … en prod »**, **« montre le delta depuis la prod »**, **« ouvre l'écran code »**. Un seul endroit, une seule conversation — de la première idée jusqu'à la prod, et retour.

Le danger, c'est le **chat-magie** : un grand modèle qui « comprend » votre phrase, décide seul, et exécute — la prod avant le test, un « build » qui diverge de ses vérités, une dérive « estimée » au doigt mouillé, une navigation inventée vers un écran qui n'existe pas. WB2-27 prend le chemin inverse : le chat fait tout — **dans les limites exactes de ce qui est déclaré**, et le cycle de vie obéit à une **loi prouvée**.

## La grammaire fermée : neuf intentions, rien d'autre

Le chat sait faire **neuf choses**, déclarées noir sur blanc (ADR 0057 + 0058 + 0059) :

- **capturer une idée** — votre besoin devient un candidat-vérité, placé automatiquement dans l'arbre du projet ;
- **greffer** — faire pousser l'arbre des besoins (« greffe pommes sous app/catalogue ») ;
- **promouvoir** — geler la dernière idée en kernel **proposé** (un brouillon, jamais appliqué) ;
- **générer** — « génère l'application » : l'app **entière**, projetée des kernels proposés — une **projection pure**, recalculée, jamais stockée, avec une version content-adressée `app:<hash>` ;
- **déployer** — « déploie l'application en test | staging | prod » : le barreau est lu dans la phrase, et l'échelle est gardée par **le cliquet généralisé** ;
- **delta** — « montre le delta depuis la prod » (ou un autre barreau) : l'**écart calculé** entre ce qui tourne et ce qui a changé depuis — jusqu'aux **fonctions exactes** ;
- **impacter** — « si je modifie ça, quoi est touché ? » : la vague, calculée ;
- **interroger** — lire l'état du projet (l'arbre, les idées, les kernels proposés) ;
- **ouvrir** — « ouvre l'écran code » : atteindre **n'importe quel écran** du Workbench depuis la conversation (la couverture totale).

Rien d'autre. Une phrase qui ne s'accroche à aucune intention est **incomprise** — le chat le dit, il n'invente jamais.

## L'app générée est une projection, jamais un stock

« Génère l'application » ne fabrique pas un artefact rangé quelque part : l'app est **recalculée** depuis les kernels proposés — une entité par kernel, une route par entité, et une version `app:<hash>` qui ne dépend **que du contenu** (le hash des versions de kernels, jamais l'horloge). Même état → même app, même version. Il ne peut pas exister de « build » qui diverge de ses vérités : la divergence n'a nulle part où vivre.

## L'échelle d'environnements : le cliquet généralisé

C'est **la loi du cycle de vie**, prouvée par le miroir. L'échelle est **déclarée** — `test → staging → prod` — et la loi est une seule, à tous les barreaux :

- « déploie l'application en **test** » exige au moins un kernel proposé — on ne déploie pas le vide ;
- déployer à **n'importe quel barreau supérieur** est **REFUSÉ** tant que la version courante **exacte** de l'app n'est pas posée au barreau d'en dessous — jamais de prod directe, jamais de staging sauté ;
- et **toute nouvelle promotion ré-arme TOUS les barreaux supérieurs** : un kernel de plus change la version de l'app, et chaque barreau au-dessus du test redevient refusé tant que cette nouvelle version n'a pas **regravi** l'échelle, barreau par barreau.

Le refus n'est pas un silence : c'est un événement explicable, qui nomme son barreau — « prod REFUSÉ : la version courante n'est pas passée en staging (le cliquet — chaque barreau, dans l'ordre, toujours) ». C'est le cliquet KRD appliqué aux environnements : il ne mord que dans le bon sens. Et **ajouter un barreau** (une préprod ?) n'est pas du code : c'est **déclarer une donnée** dans l'échelle — la loi le couvre déjà.

## Le déploiement réel : le clic humain est l'approbation

Gravir l'échelle in-model ne lance ni docker ni Traefik : le chat **séquence et prouve**. Mais l'écran porte un bouton « **Déploiement réel** » qui ferme la boucle : il **ne s'arme que lorsque l'échelle est gravie jusqu'au sommet** (la prod in-model posée), et **le clic humain EST l'approbation** — pas un agent, pas une heuristique : votre geste. L'action réutilise **le pipeline gaté d'ADR 0052** (celui de l'AI Lab — réémission, `docker compose up`, URL live) : **jamais un second chemin de déploiement**. Trois portes, donc : l'échelle (le cliquet), le clic (l'humain), le pipeline (gaté). L'émission réelle de l'app *née de la conversation* reste une question ouverte documentée (S45) — aujourd'hui le bouton redéploie l'app émise des specs du projet.

## Le delta : un écart compté, jamais estimé — jusqu'aux fonctions exactes

« Montre le delta depuis la prod » ne demande pas son avis à un modèle : le système **compte** les kernels qui ne sont pas dans l'ensemble déployé. Juste après un déploiement, le delta est **0** ; promouvez une idée de plus, il devient **1** — exactement. Sans aucun déploiement, le delta est **total** (tout est écart), jamais une erreur.

Et depuis l'ADR 0059, le delta **descend au grain code** : pour chaque kernel d'écart, le système croise la dérive d'environnement avec le **graphe de connaissance du code** (ADR 0056) et nomme **quelles fonctions exactes** sont concernées — les ancres (telle classe, telle fonction, tel fichier) et la **taille de la vague** de rouge code qu'une modification déclencherait. La dérive est une donnée, pas une opinion — et elle a désormais des noms de fonctions.

## La couverture totale : chaque écran atteignable, et la loi qui le prouve

« Ouvre l'écran code », « navigue vers le goal » : le chat sait **aller partout**. La résolution ne devine jamais — elle score votre phrase contre l'**inventaire déclaré** des écrans : le registre V2 (toujours couvert) et les écrans V1, **injectés en données** (l'inventaire vient d'un scan, jamais d'un code en dur). Aucune accroche → un refus explicable, **jamais une route inventée**.

Ce n'est pas une promesse : c'est **la loi de couverture, prouvée au miroir** — ∀ écran du registre, « ouvre \<titre\> » résout vers SA route. Tous les écrans, pas un échantillon.

Et une subtilité **déclarée** la rend possible : la règle « **l'impératif de navigation commande** » — un message qui *commence* par « ouvre », « ouvrir » ou « navigue » est toujours l'intention d'ouvrir. Pourquoi ? Parce que les **titres d'écrans citent le vocabulaire de la grammaire** : « ouvre l'écran goal » contient « goal », qui accrocherait la promotion ; « ouvre l'écran déployer » accrocherait le déploiement. Sans la règle, la loi de couverture serait fausse. Avec elle — déclarée, déterministe, épinglée au miroir — l'impératif de navigation l'emporte, toujours, et jamais en silence.

## L'attente et les types de réponse possibles

À chaque message, l'écran rend le raisonnement **visible** :

- « **l'attente** » — ce que le système a compris : l'intention en tête, ou le constat d'une ambiguïté, ou l'aveu d'incompréhension ;
- « **les types de réponse possibles** » — **tous** les candidats, classés par score : vous voyez ce que le chat aurait pu comprendre d'autre ;
- « **la réponse** » — pas de la prose libre : des **événements typés** d'un jeu clos (« idée capturée », « arbre greffé », « kernel proposé », « app générée », « déploiement » — qui porte son barreau —, « delta calculé », « écran ouvert », « refus »…) ;
- « **les impacts** » — la **vague calculée** : quels nœuds de l'arbre, quelles idées, quels kernels sont touchés par ce tour.

Le classement n'est pas une opinion d'IA : c'est un **algorithme à lexiques déclarés** — les mêmes mots donnent toujours le même classement. Les boutons de l'écran ne court-circuitent rien : chacun **envoie un message canonique** qui repasse par le même circuit — le chat reste l'unique source de gestes.

## L'ambiguïté est offerte, jamais tranchée en silence

« Greffe et déploie le paiement » : deux intentions s'accrochent à égalité. Un chat-magie choisirait pour vous, en silence. L'IA Builder **détecte** l'ambiguïté, la **dit**, et vous **offre le choix** : les candidats deviennent des boutons — vous cliquez celui que vous vouliez, et la demande repart, désambiguïsée, dans le même circuit. Le système ne devine jamais à votre place.

## L'IA, exception gatée — le code a l'autorité

Et Claude, alors ? Il n'entre qu'à **un seul endroit**, et comme **exception** : sur un message ambigu, un bouton « Reformuler » lui demande de réécrire votre phrase en **une** intention claire. Mais sa phrase ne commande rien : elle **repasse par le même pipeline déterministe** — le même classement, la même réduction. Le modèle **propose**, le code **juge**. Si Claude est en panne, rien ne casse : les boutons de choix déterministes restent là.

## Le mur, prouvé sur toutes les phrases

Le chat **propose** ; il n'écrit **aucune vérité** et n'exécute **aucune infrastructure**. Une idée capturée n'a pas de miroir ; un kernel promu est un **brouillon** (ChangeSet DRAFT) ; un déploiement est un **événement du jeu clos** — le vrai pipeline (ADR 0052) reste gaté par l'échelle, le clic humain et l'approbation. Et ce n'est pas une promesse : c'est une **propriété prouvée sur toutes les suites de messages possibles** — quoi que vous tapiez, dans n'importe quel ordre, aucune écriture-vérité ne part. La promotion réelle reste le chemin légal : idée → miroir → `/goal` → approbation humaine.

## Comment savoir que c'est juste

- Le miroir du builder (**29 propriétés et exemples**) prouve : le jeu des intentions est **clos** (les neuf, ni plus ni moins) ; **l'échelle d'environnements est déclarée, close, ordonnée** ; le classement est **total et déterministe** ; un message clair est **compris**, une égalité est **ambiguë**, une phrase sans accroche est **incomprise** ; le réducteur est **pur** et le journal **append-only** ; chaque intention canonique fait exactement ce qu'elle dit ; la version d'app est **stable** (même état → même `app:<hash>`) ; **∀ barreau, sauter un barreau est refusé**, le chemin test → staging → prod passe (la même version monte chaque barreau), et **le cliquet re-mord sur toute l'échelle** après chaque nouvelle promotion ; le delta compte **exactement** l'écart (total sans déploiement, 0 juste après, 1 après une promotion) et **chaque kernel d'écart s'ancre sur ses fonctions** ; **la loi de couverture tient** (∀ écran du registre, « ouvre \<titre\> » résout vers SA route, et les écrans V1 injectés sont atteignables aussi) ; la résolution d'écran est **fail-closed** (introuvable → refus, jamais une invention) ; et **le mur tient ∀ messages** — aucune écriture-vérité, jamais.
- Étendre le chat, c'est **déclarer** : une nouvelle intention + son lexique + sa réduction + ses tests — jamais « le modèle improvisera ». Les trois intentions du cycle de vie (générer, déployer, delta) puis la navigation totale (ouvrir) et l'échelle à trois barreaux sont nées exactement comme ça (ADR 0058, ADR 0059).
