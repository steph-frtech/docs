## En une phrase

**Fractal Kernel Engineering** : le vibe donne l'idée, le kernel donne le contrat, le harness donne le cadre, la police donne les limites, l'evidence donne la confiance, la conscience donne l'alignement. Ce n'est pas du *prompt-to-code* — c'est du **vibe-to-kernel-to-evidence**.

## Le code n'est pas la vérité

Dans FKE, toute demande adressée à une IA — créer, corriger, refactorer, documenter, tester, sécuriser, migrer, déployer — est d'abord transformée en **kernel** : une unité typée de sens, contrat, comportement, preuve, sécurité et liens. Le code n'est qu'une **projection exécutable** d'un kernel d'intention validé. La vraie sortie du système n'est pas un fichier : c'est un **graphe vivant de kernels** qui sait expliquer pourquoi chaque artefact existe, quel contrat il respecte, quelles preuves le valident et quelle décision l'a promu.

## L'anatomie symétrique — le mur comme plan de miroir

Chaque kernel a dix emplacements (« slots »), **symétriques autour du mur** : tout ce que l'humain déclare au-dessus a son **reflet vérifiable** en dessous.

| Au-dessus (l'humain possède) | | En-dessous (l'agent reflète) |
|---|---|---|
| s1 · La spec textuelle | ↔ | s10 · La documentation finale |
| s2 · Les use cases (BDD) | ↔ | s9 · La doc **dérivée du code** |
| s3 · Le modèle de donnée *au sens humain* | ↔ | s7 · La projection en données |
| s4 · Les scénarios + preuves attendues | ↔ | s5 · Le code du test · s6 · Le résultat |
| — | | s8 · **Le code lui-même — optionnel** |

Trois lectures de cette table :

1. **Le miroir se généralise en quatre familles de paires.** Le test n'est qu'une des quatre : il y a aussi le **doc-miroir** (la doc dérivée du code doit re-dire le use case déclaré — la dérive documentaire devient mécaniquement détectable), le **data-miroir** (la donnée réelle doit refléter le modèle humain) et le **spec-miroir**. Une paire qui diverge = soit un bug en bas, soit une vérité à faire évoluer en haut — jamais un écart silencieux.
2. **Le code est optionnel par émission, jamais orphelin.** Dans la vue effondrée ci-dessus, le code (s8) semble sans partenaire ; la forme stricte (plus bas) le réconcilie : le code reflète le **Contrat**. Pour un kernel déclaratif (vue, policy), le contrat est satisfait par **pure projection** — le code est généré, pas écrit à la main (le code est une projection).
3. **Le mur est aussi une frontière de langue.** Tout ce qui se lit — y compris les *retours* d'en bas (résultats, doc dérivée, données) — parle la **langue ubiquitaire** de votre domaine. Seuls les deux slots de code parlent machine. Vous ne lisez jamais une autre langue que la vôtre.

Et tout est **fractal** : la même anatomie vaut pour un projet, une feature, une API, une fonction, un agent, une migration — un kernel-feuille peut « s'effondrer » (slots dérivés), mais jamais en dessous de l'incompressible : **une intention + sa paire de preuve**.

## L'anatomie EST un pipeline (le cœur fractal)

Ces dix slots ne sont pas une fiche statique : c'est une **traversée**. Une **entrée textuelle** (un besoin, un chat, un ticket) s'éclate en les slots du dessus, chacun se reflète en dessous, la conscience compare les paires, puis on promeut — ou la divergence remonte. **C'est exactement le pipeline VIBE AI LAB, à l'échelle d'un seul kernel** :

Le 1-pour-1 est **strict** : huit paires-miroir, chaque vérité déclarée a exactement un reflet prouvé.

```text
              ENTRÉE (textuelle) — besoin · chat · ticket · incident
                        │  DÉCLARÉ (cerveau gauche)
   ┌──── FONCTIONNEL ────────────────┐   ┌──── SÉCURITÉ ───────────────────────┐
   │ Spec · Comportement · Scénarios │   │ Spec séc. · Abuse cases · Scén. séc. │
   │ Modèle · Contrat · Evidence att.│   │ Threat model · Contrat séc. · Evi.séc│
   └────────────────┬─────────────────┘   └────────────────┬────────────────────┘
                    ↓   VALIDATION — Decision Card (accept · reject · amend · defer)
══════════════════════════ MUR D'INTENTION ══════════════════════════
                    ↓   PROUVÉ (cerveau droit) — reflet 1-pour-1
   ┌──── FONCTIONNEL ────────────────┐   ┌──── SÉCURITÉ ───────────────────────┐
   │ Documentation ◀ Spec            │   │ Doc séc. ◀ Spec séc.                 │
   │ Résultats     ◀ Comportement    │   │ Résultats séc.(denials) ◀ Abuse cases│
   │ Tests         ◀ Scénarios       │   │ Tests séc.(+evals) ◀ Scénarios séc.  │
   │ Projection    ◀ Modèle          │   │ Sécurité implém.(authz) ◀ Threat mdl │
   │ Code          ◀ Contrat         │   │ Police + scans ◀ Contrat séc.        │
   │ Evidence obs. ◀ Evidence att.   │   │ Evidence séc.obs. ◀ Evidence séc.    │
   └────────────────┬─────────────────┘   └────────────────┬────────────────────┘
                    ↓   EXÉCUTION (lance Code + Tests → Résultats + Evidence)
═════════════════════ MUR SÉCURITÉ / POLICE ═════════════════════
   ↓  POLICE (allow · block · audit · approval — ambiante)
   ↓  CONSCIENCE — compare les 12 paires (6 fonctionnelles ∧ 6 sécurité)
   ├─ aligné → PROMOTION (vérité stable → Kernel Graph)
   └─ divergence (fonctionnelle OU sécurité) → LOOPBACK CIBLÉ vers le slot exact
```

Le kernel a **deux facettes parallèles** — fonctionnelle et sécurité — chacune une anatomie 1-pour-1 complète (six paires + six paires = douze).

**Facette FONCTIONNELLE :**

| Déclaré (dessus) | ↔ | Prouvé (dessous) |
|---|---|---|
| Spec | ↔ | Documentation |
| Comportement | ↔ | Résultats |
| Scénarios | ↔ | Tests |
| Modèle | ↔ | Projection données |
| Contrat | ↔ | Code |
| Evidence attendue | ↔ | Evidence observée |

**Facette SÉCURITÉ (le même squelette, lu en menaces) :**

| Déclaré (dessus) | ↔ | Prouvé (dessous) |
|---|---|---|
| Spec sécurité (finalité, classification des données) | ↔ | Doc sécurité (threat model, runbook) |
| Abuse cases (comportements d'attaque) | ↔ | Résultats sécurité (denials, blocks) |
| Scénarios sécurité | ↔ | Tests sécurité (+ evals injection / exfiltration) |
| Threat model (surfaces, acteurs) | ↔ | Sécurité implémentée (authz, allowlist, sandbox, redaction) |
| Contrat sécurité (permissions, capabilities) | ↔ | Police + scans (SAST / DAST / SBOM / gitleaks) |
| Evidence sécurité attendue | ↔ | Evidence sécurité observée (scans verts, audit Merkle) |

Le **Contrat** apparie enfin le **Code** (et le Contrat sécurité apparie la Police) : plus aucun slot orphelin. Le code reste optionnel **par émission** (un kernel déclaratif voit son contrat satisfait par pure projection), jamais par absence de partenaire.

## Huit lentilles, un seul squelette

La sécurité n'est pas la seule facette. Le **même squelette de six paires** se lit à travers **huit lentilles canoniques** — c'est l'unification de FKE :

| Lentille | La question qu'elle pose | Preuve dominante |
|---|---|---|
| **Fonctionnel** | fait-il ce qu'on veut ? (par l'exemple) | tests, code, résultats |
| **Invariants ∀** | est-ce vrai sur TOUS les chemins ? | property / fuzz / mutation |
| **Sécurité** | résiste-t-il aux attaques ? | tests séc, police, scans |
| **Performance / Budgets** | assez rapide, pas trop cher (charge normale) ? | benchmark, load test, métrage |
| **Fiabilité / Résilience** | survit-il aux **pannes** (dégradation, reprise) ? | chaos / fault-injection, failover, restore |
| **Évolutivité / Migration** | la vérité tient-elle dans le temps, sur de vraies données ? | migration, backfill, restore, `as-of` |
| **Maintenabilité & Architecture** | la structure est-elle saine (design déclaré ↔ structure réalisée) ? | arch-fitness, le second cliquet structurel |
| **Expérience / Utilisabilité** | est-il **bon à utiliser** ? (vérité molle, falsifiable) | ExperienceClaim : usabilité, A/B, télémétrie |

Chaque lentille a les six mêmes paires (Spec → Comportement → Scénarios → Modèle/Domaine → Contrat → Evidence ↔ leurs reflets), lues sous son angle. La **maintenabilité** est le **second cliquet** de KRD (« tests verts, système pourri »). La **fiabilité** demande « survit-il à une dépendance morte / un crash ? » — orthogonale à la performance (rapide ≠ résilient) et à l'évolutivité (durable au changement ≠ tolérant à la panne). L'**expérience** est une **vérité molle** (§13.6) : prouvée expérientiellement (usabilité, A/B, télémétrie), falsifiable par la réalité — elle **informe** la décision sans la **bloquer** comme un invariant dur (sous-contraindre l'UX serait l'erreur symétrique).

**Pourquoi huit — et comment je l'ai vérifié.** Croisement au modèle de qualité canonique **ISO 25010** : il valide F, S, B (efficiency), M ; sa Compatibility = nos arêtes (Pact) ; sa Portability ⊂ V ; et il révèle **deux oublis** que j'avais repliés à tort — **Usability → Expérience (X)** et **Reliability → Fiabilité (R)**. (Note : nos **Invariants ∀** ne sont pas un attribut ISO mais un axe de *rigueur de preuve*, ∃ vs ∀.) L'octuor : **correct par l'exemple · vrai partout · sûr · viable · résilient · durable · sain · utilisable.** Au-delà, un test de décision classe tout autre candidat :

- **dimension latérale** (une **arête** entre kernels) : Contrats/Pact, Composition — déjà des liens du graphe avec leur miroir, pas des facettes ;
- **sous-lentille** (raffinement DANS une facette) : Déterminisme & Concurrence ⊂ Invariants ∀ · Conformité/GDPR ⊂ Sécurité · a11y/i18n ⊂ Expérience · Réversibilité/recovery ⊂ Fiabilité · Observabilité ⊂ Fiabilité/Performance · Portabilité ⊂ Évolutivité ;
- **propriété du graphe** (Provenance) ou **du changeset** (Reviewability), pas du kernel.

S'il surgit une question (a) orthogonale, (b) sur les internals d'un kernel, (c) non réductible aux huit — ce sera la 9ᵉ. Après croisement ISO, les candidats sérieux tombent tous ailleurs.

**Les facettes sont effondrables** : un kernel n'instancie une lentille **que s'il porte cette nature de vérité**. La fonctionnelle est toujours là ; une fonction pure porte F + Invariants + Maintenabilité ; un endpoint PII user-facing porte tout (F+I+S+B+R+V+M+X) ; une vue déclarative n'a que F + X. On n'instancie jamais une facette vide.

La **conscience** compare toutes les paires instanciées : **une faille de sécurité, une régression de perf, un invariant non prouvé ou une migration qui perd de la donnée sont des monstres, exactement comme un test fonctionnel manquant.** Et **chaque étage du macro pipeline est lui-même un kernel** avec ce micro pipeline : les couches hautes composent, les basses exécutent, les invariants remontent, les preuves réconcilient.

## Les deux axes — la facette (orthogonale) et la verticale (latérale)

Les facettes ne sont qu'**un** axe : la **nature** de la vérité. Une vérité a une **seconde coordonnée** — son **niveau dans la verticale** (`produit → parcours → vue → contrôle → action → opération → entité`). Toute vérité vit à l'**intersection** d'un niveau et d'une facette : « l'invariant ∀ de l'**opération** checkout », « le contrat de performance de la **vue** panier ».

La différence est profonde : les **facettes sont orthogonales** (régler la sécurité ne touche pas la performance — elles n'interagissent pas, elles **séparent**). La **verticale, elle, n'est pas orthogonale : elle COUPLE.** Une vérité posée bas (sur l'entité) **contraint tous les niveaux qui la composent au-dessus** (l'opération, l'action, le contrôle, la vue) ; et quand elle change, le **red wave remonte cette ligne** et rougit ses consommateurs. **Les facettes isolent ; la verticale relie et propage.** C'était la ligne « non-orthogonale » qu'il manquait.

Le système de coordonnées complet d'une vérité : **niveau** (verticale, latérale/couplante) × **facette** (nature, orthogonale/séparante) × **côté du mur** (déclaré / prouvé) × **échelle** (projet ⊃ feature ⊃ fonction). La conscience compare dans une cellule ; le red wave propage le long de la verticale ; le mur traverse les quatre.

## Nœud et arête — l'anatomie et la pile OSI

Le graphe a deux objets, chacun avec sa structure. Un **nœud** (un kernel) a l'**anatomie** ci-dessus (6 paires × facettes × verticale × mur). Une **arête** — un contrat entre kernels, un connecteur, une API, un outil MCP — a une **pile**, et c'est le **modèle OSI** qui en est le gabarit : **L7 application** (le schéma, le protocole) · **L6 présentation** (sérialisation, encodage, redaction) · **L5 session** (auth, OAuth) · **L4 transport** (HTTP/gRPC ; les transports MCP). Une fonction pure n'a aucune couche OSI ; une API/MCP/connecteur a la pile complète. **L'OSI est à l'arête ce que l'anatomie est au nœud.**

Et le clivage **fonctionnel/technique** n'ajoute aucune rangée : il est déjà porté par la **ligne de flottaison** (métier en haut, technique en bas) et par les **facettes** (F = fonctionnel ; S/B/R/V/M = technique). La « **spécification technique** » et la « **suite de tests techniques** » sont donc des **projections générées** par kernel (assemblant Contrat + Modèle + la pile OSI si réseau + les specs des facettes + les ADR), jamais de nouvelles rangées — comme `CLAUDE.md` est généré, jamais écrit à la main.

## La causalité dans les deux sens (le WhyTree)

La verticale propage la causalité **AVANT** : une vérité change → le **red wave** rougit ses conséquences (« qu'est-ce que je casse ? »). Il manquait le sens **ARRIÈRE** : d'un symptôme, remonter à la **cause racine** (« pourquoi ça a cassé ? »). C'est le **5-pourquoi**, mais redressé pour KRD :

- ce n'est **pas une facette** — c'est un **geste déclenché par un échec** (`/why`), transversal aux 8 facettes ;
- **déterministe d'abord** : on remonte le lien **`caused_by`** (l'inverse de l'`impacts`) là où le graphe connaît la cause ; le LLM ne sert qu'au « pourquoi » hors-graphe, et **chaque cause est reproduite ou rejetée** (anti-confabulation) ;
- un **arbre** (fishbone), pas une ligne — plusieurs causes contributives ;
- **il finit toujours en MIROIR** : la racine → `/learn` → un nouveau miroir d'anti-récurrence. Un WhyTree sans miroir n'est que du storytelling. C'est ce qui transforme « on a compris » en « ça ne peut plus revenir ».

Red wave (avant) + WhyTree (arrière) ferment la causalité du graphe dans les deux sens.

## Le vibe est contenu, jamais interdit

FKE ne rejette pas le vibe coding : il l'enferme dans le **Vibe Lab** — la zone d'exploration rapide (prototypes, spikes, comparaisons d'options) dont tout ce qui sort est `experimental`, jamais production. Le passage vers le durable est un **Promotion Gate** : intention claire, contrat, invariants, sécurité, preuves attendues, décision humaine — et l'artefact est **ré-émis depuis le kernel**, jamais promu tel quel.

## Le pipeline VIBE AI LAB — la traversée canonique

Le flux de bout en bout tient en un dessin : **treize étages, deux traversées de mur**.

```text
VIBE LAB (exploration, prototype, spike — expérimental, jetable)
  ↓
RAW SIGNAL STORE (chat, forum, erreur, doc, idée, log)
  ↓
MEMORY POLICE (trust, scope, privacy, TTL, contradiction)
  ↓
LEFT BRAIN / INTENT COMPILER (intent, contrat, invariants, sécurité)
  ↓
DECISION CARDS / GOVERNORS (accept, reject, amend, defer)
════════════════════ INTENT WALL ════════════════════
  ↓
ACCEPTED KERNEL STORE (vérité intentionnelle validée)
  ↓
CONTEXT PACK BUILDER (contexte minimal, validé, scoped)
  ↓
RIGHT BRAIN / REALIZATION COMPILER (code, tests, agents, MCP, skills, infra)
  ↓
EVIDENCE RUNNER (tests, lint, typecheck, scan, benchmark)
═══════════════ SECURITY / POLICE WALL ═══════════════
  ↓
POLICY ENGINE / POLICE (allow, block, audit, approval)
  ↓
CONSCIOUSNESS / ALIGNMENT GOVERNOR (compare voulu, construit, prouvé, permis)
  ↓
PROMOTION GATE (stable, experimental, rejected, rewrite)
  ↓
KERNEL GRAPH / MEMORY / REGISTRY (apprend, trace, réutilise, explique)
```

Quatre précisions pour bien le lire : le **Raw Signal Store** a plusieurs entrées (le Vibe Lab y verse ses sorties *à côté* de vos chats, erreurs et docs) ; la **Memory Police** filtre même le cerveau gauche (brut-policé) tandis que le droit ne reçoit que du validé ; la **police est ambiante ET une porte** — elle intercepte chaque action dès la réalisation, le mur dessiné marque la traversée sans clearance ; et il y a **deux portes, une par mur** — les Decision Cards (la vérité est-elle acceptée ?) et le Promotion Gate (l'artefact prouvé est-il promu ?). Un seul concept de porte, deux instances.

## Les trois cerveaux et la conscience

Le **cerveau gauche** lit vos signaux bruts (chat, tickets, logs, prototypes) et propose les slots du dessus — il ne code pas. Le **cerveau droit** reçoit uniquement des kernels validés dans un contexte minimal et produit les reflets du dessous — il ne modifie jamais seul le dessus. La **conscience** compare en permanence les paires réfléchies et produit rapports et **decision cards** ; elle est un *agrégateur déterministe* des preuves existantes — jamais un second juge dont il faudrait croire l'avis.

## L'écran AI Lab — le cockpit (trialogue)

La surface principale n'est ni un chat ni un éditeur : c'est un **trialogue** à trois zones où le mur est *visible* et franchi seulement par une décision.

```text
┌──────────────┬──────────────────────────────┬───────────────────┐
│ GAUCHE       │ CENTRE — la couche navigable │ DROITE            │
│ VIBE / CHAT  │ le kernel courant + son      │ À VALIDER         │
│              │ anatomie 1-pour-1            │                   │
│ on chate, on │  ┌ DESSUS (déclaré) ▲proposé │ DECISION CARDS    │
│ discute ;    │  │ Spec Comport. Scénarios…  │ [accept][amend]   │
│ le cerveau   │  ├──── MUR D'INTENTION ──────│ [reject][defer]   │
│ gauche       │  │ Doc Résultats Tests Code… │ blast radius ●●○○ │
│ COMPILE en   │  └ DESSOUS (prouvé) 🟢🟢🔴🟢… │ ─────────────     │
│ slots        │                              │ CONSCIENCE        │
│ PROPOSÉS     │ chaque paire = un voyant     │ 7/8 alignées      │
│ (jamais en   │ 🟢 aligné 🔴 diverge 🟡 sous │ ─────────────     │
│ vérité)      │ ▸ clic paire → la gauche se  │ PROMOTION GATE    │
│              │   scope, la droite montre    │ ⛔ 1 paire rouge  │
│ [Envoyer]    │   ses impacts                │                   │
└──────────────┴──────────────────────────────┴───────────────────┘
 RAW SIGNAL → LEFT BRAIN → [VALIDATION] ═MUR═ RIGHT BRAIN → CONSCIENCE → [PROMOTION]
```

Vos deux idées sont le **même écran à zoom différent** : en **conversationnel** (zoom arrière) vous parlez à gauche et les impacts à valider arrivent à droite ; en **navigationnel** vous sélectionnez une couche/paire au centre, **la gauche se scope dessus** (vous « chatez sur la couche ») et la droite montre *ses* impacts.

La règle d'or : **le chat ne change jamais une vérité.** Il produit des signaux bruts puis des **slots proposés** (au-dessus du mur, en amber) ; la seule façon de muter la vérité est un **clic à droite** (decision card → ChangeSet → approbation). Les écarts affichés sont **calculés** (diff sémantique, blast radius, red wave), jamais l'avis d'un modèle. Le bas du mur est en **lecture seule** : on ne hand-édite pas le code depuis l'écran, on change la vérité d'au-dessus qu'il reflète. Le **Loopback ciblé** se voit : une paire 🔴 surligne le slot exact d'au-dessus à reconsidérer.

## Ce que ça change pour vous

Vous ne « promptez » plus du code : vous **déclarez** des vérités (en votre langue), le système les **prouve** (E0→E7, du typecheck à la preuve runtime), et **rien ne change de sens en silence** — toute divergence remonte vers vous comme une carte de décision claire : accepter, amender, corriger, refuser.
