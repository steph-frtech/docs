How to verify an AIDOS step end-to-end without trusting the executor report.

**Why:** the contract requires re-running everything; the report's "5 passed / green" claims must be reproduced.

**How to apply (commands that work in this repo):**
- Go mirror: `cd /data/dev/aidos/back && go test ./kernel/<step>/ -count=1` + `go vet ./kernel/<step>/` + `gofmt -l kernel/<step>/` (empty = clean). Testcontainers migration tests run inside this same `go test` (they pull postgres:16-alpine; the 15-17s runtime is normal).
- Prior green intact: `cd /data/dev/aidos/back && go build ./...`.
- Front reproducibility mirror: `cd /data/dev/aidos/front/web && npx vitest run lib/<x>.test.ts`; lint with `npx biome check <files>` and `npx tsc --noEmit`.
- Playwright e2e: `cd /data/dev/aidos && npx playwright test tests/e2e/<x>.spec.ts --reporter=line` (config has webServer, auto-starts dev on :3000).
- Docs: pages live in `/data/dev/aidos/.aidos-docs/steps/{concept,internals}/sNN-*.mdx`; internals must have `^## (Implémentation|Méta|Méta-méta)`; registered in `.aidos-docs/docs.json`; `mint validate` from the `.aidos-docs` clone; pushed = `.aidos-docs` is its OWN git clone of steph-frtech/docs — check `git log --oneline` shows the SNN docs commit + `git status -sb` shows `main...origin/main` with no ahead/behind.
- Linear: `mcp__linear-server__get_issue` with id `AID-NN` (S15 = AID-47, S19 = AID-24 — the numbering is NOT sequential with the step number); confirm `status: Done` only if truly green.

**Recurring-pattern note (S15, S19, S20):** kernel/archive steps that ship a pure Go guard/engine + a read-only Workbench projection come in fully green on first verification — the front lib mirrors the Go verdict logic line-for-line (one source, no drift). Expect this clean-first-pass shape. The known limits (no SemanticDiff executor, no PostKernelChange/hook wiring, evidence/validity = presence-only pending a later provenance lookup, illustrative candidate records) are by-design forward-deps owned by later steps = OpenQuestions, NOT residual issues. For a read-only verdict-surface step, the propose→ChangeSet truth-write path is correctly DEFERRED (the screen develops no truth-write op), so its absence is not a ui-completeness gap.
